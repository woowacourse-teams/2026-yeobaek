# 여백 팀 테스트 기준

## 보호하는 동작

- API 명세와 핵심 사용자 흐름을 검증한다. 응답 형식이 바뀌거나 초대 코드·댓글이 잘못 처리되면 사용자가 모임에 참여하거나 기록을 남기기 어렵기 때문이다.
- 대표 성공 사례와 실제로 발생할 수 있는 오류를 검증한다. 실패 응답과 저장 결과까지 확인해야 사용자가 본 오류나 잘못 남은 기록을 발견할 수 있기 때문이다.

## 검증에서 제외하는 대상

- 사용자에게 같은 결과를 주는 내부 구현, 장식용 색상과 미세한 여백은 검증하지 않는다. 내부 구조와 표현이 바뀌어도 동일한 사용자 경험을 제공할 수 있기 때문이다.
- 검증된 라이브러리의 자체 동작과 이미 충분히 보호되는 동일한 계약은 반복해서 검증하지 않는다. 새로 발견할 회귀 없이 실행과 유지 비용이 늘기 때문이다.

## 테스트 수준과 의존성

- 입력과 상태로 판단할 수 있는 초대 코드 정책이나 알림 설정은 단위 테스트로 검증한다. 피드백이 빨라 규칙을 수정할 때 바로 확인할 수 있다.
- 요청 바인딩·응답 형식이나 저장 결과처럼 연결 과정에서 틀어질 수 있는 계약은 슬라이스 또는 통합 테스트로 검증한다. 필요한 구성요소만 실행한다.
- 격리된 테스트 DB는 동시 요청, 트랜잭션, 쿼리·제약 조건처럼 실제 저장소 동작이 결과를 좌우할 때 사용한다. 가짜 저장소로는 저장 경계에서 생기는 회귀를 재현하기 어렵다.
- 일상적인 자동 테스트에서는 외부 API를 테스트 대역으로 대체한다. FCM 장애나 네트워크 상태와 관계없이 필요한 성공과 실패를 재현할 수 있어야 한다.
- 앱과 서버를 함께 띄우는 E2E 테스트는 새로 작성하지 않는다. 기능을 자주 바꾸는 현재 단계에서는 두 환경을 함께 구성하고 유지하는 비용이 커서 각 파트에서 핵심 동작과 경계의 계약을 검증한다.

- 백엔드는 댓글 작성·수정·재조회처럼 여러 요청에 걸쳐 저장 결과가 이어지는 핵심 흐름을 백엔드 범위에서 실제 HTTP E2E로 검증한다. 앱 없이 실행할 수 있어 환경 유지 비용이 작다. [백엔드 테스트 기준](../backend/docs/지침/검증/백엔드_테스트_기준.md) · [댓글 HTTP 테스트](../backend/src/test/java/yeobaek/backend/e2e/CommentE2eTest.java)
