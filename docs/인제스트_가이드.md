# 인제스트 가이드 — 로컬 LLM으로 규격 JSON 만들기

> 기반 문서: [`PRD.md`](PRD.md) 3.3 · 규격 상세: [`API.md`](API.md) 6장 (2026-08-06 M7 확정)
> 흐름: 퍼블릭 도메인 원문 확보 → 로컬 LLM으로 규격 JSON 생성 → 관리자 페이지(`/admin`)에서 업로드

## 1. 콘텐츠 선정 규칙

- **퍼블릭 도메인(저작권 만료) 저작물만** 사용한다 (PRD 3.3). 한국 문학은 공유마당(gongu.copyright.or.kr), 위키문헌 등에서 원문을 얻는다.
- 본문 삽화는 텍스트 인제스트에서 제외한다. 도서 표지는 별도 파일 선택으로 업로드할 수 있다.

## 2. 규격 JSON (요약)

```json
{
  "title": "운수 좋은 날",
  "publisher": "자체 제작",
  "publishedYear": 1924,
  "coverImageKey": null,
  "authors": [{ "name": "현진건", "isni": "0000 0001 2345 964X" }],
  "chapters": [
    {
      "title": "1장",
      "passages": [
        {
          "sentences": [
            { "content": "첫 문장이다. " },
            { "content": "다음 문장이다.\n" }
          ]
        }
      ]
    }
  ]
}
```

- 문단 순서는 책 전체의 **배열 등장 순서**대로, 문장 순서는 각 문단의 배열 등장 순서대로 서버가
  각각 1..N을 부여한다. JSON에 순서 번호를 넣지 않는다.
- 제목·출판사·작가명·목차 제목은 각 1~100자. 각 문단은 문장을 최소 1개 가져야 하며 문장
  `content`는 필수(공백만 불가)다.
- 문단당 문장 수에는 별도 최대 개수 제한이 없다. 원문을 유지하기 위해 임의로 문장을 합치거나
  제거하지 않는다.
- 문장 사이의 공백과 개행은 앞 문장의 `content` 끝에 포함한다. 서버는 문장 `content`를
  `trim()`하지 않는다. 한 문단의 `sentences[].content`를 배열 순서로 연결하면 원래 문단 원문과
  완전히 같아야 한다.
- 목차 0개, 본문 0개인 목차는 거부된다. 목차가 없는 원문은 임시로 "본문" 같은 단일 목차를 만들지 말고 팀에 논의를 올린다 (PRD 6장 미해결 항목).
- `coverImageKey`는 선택값이다. 관리자 페이지에서 표지 파일을 선택하면 S3 업로드 성공 후
  발급된 키를 자동으로 요청에 넣는다. 표지가 없으면 생략하거나 `null`로 둔다.

## 3. 작가 기입 규칙

1. **ISNI를 먼저 찾는다** — [isni.org](https://isni.org) 검색. 있으면 `{ "name", "isni" }`로 기입한다. 같은 ISNI가 서버에 이미 있으면 자동으로 재사용된다 (이름이 다르면 거부되니 등록된 이름 그대로 쓴다).
2. **ISNI가 없으면 관리자 페이지의 "작가 목록 불러오기"로 기존 등록 여부를 확인한다.**
   - 같은 작가가 이미 있다 → `{ "authorId": 12 }`로 참조한다.
   - 없다 → `{ "name": "..." }`만 기입한다 (신규 생성).
3. **작자를 알 수 없는 저작물은 이름을 `"작자 미상"`으로 기입한다** (2026-08-06 결정).

## 4. LLM 프롬프트 템플릿

로컬 LLM에 원문(또는 장 단위 분할본)과 함께 아래 지시를 준다.

```
다음 원문을 아래 JSON 규격으로 변환하라.

규칙:
1. 문단 분할: 원문의 문단(빈 줄 또는 들여쓰기로 구분되는 단위)을 그대로 하나의
   passages 원소로 만든다. 문단을 임의로 합치거나 쪼개지 않는다.
   각 passages 원소에는 sentences 배열을 만들고 원문의 문장을 등장 순서대로 나눈다.
   물리적 페이지 개념은 없다.
2. 원문 텍스트를 요약·수정·현대어 교정하지 않고 그대로 담는다.
   명백한 OCR 오류(글자 깨짐)만 원문 표기에 맞게 복원한다.
3. 문장 경계의 공백과 개행은 앞 문장의 content 끝에 그대로 포함한다. content의 앞뒤
   공백을 제거하지 않는다. 한 문단의 sentences[].content를 순서대로 연결하면 분리 전 문단
   원문과 완전히 같아야 한다.
4. 목차: 원문의 장 구분(1장, 二, 상편 등)을 chapters 원소로 만들고 제목을 그대로 쓴다.
   장 구분이 없는 단편은 변환을 멈추고 그 사실을 보고한다.
5. 등장 순서를 유지한다. 순서 번호는 출력하지 않는다.
6. 이미지·삽화는 제외한다.
7. 출력은 JSON 하나만. 설명 문장을 붙이지 않는다.

JSON 규격:
{ "title": ..., "publisher": ..., "publishedYear": ...,
  "authors": [{ "name": ..., "isni": ... }],
  "chapters": [{ "title": ..., "passages": [
    { "sentences": [{ "content": ... }] }
  ] }] }
```

- **긴 책은 장 단위로 나눠 생성한다.** LLM 컨텍스트를 넘기면 문단이 유실돼도 알아채기 어렵다. 장별로 `passages` 배열을 생성한 뒤 사람이 chapters 배열로 병합한다.
- 생성 후 **문단 수와 문장 순서를 원문과 대조**한다. 각 문단의 `sentences[].content`를 배열
  순서로 연결한 값이 분리 전 문단 원문과 완전히 같은지도 비교한다. 순서·개수·원문 재결합 검증은
  서버가 대신할 수 없는 부분이다(배열 순서와 입력 문자열을 정답으로 취급하므로).

## 5. 업로드와 에러

관리자 페이지(`/admin`)에 토큰을 입력하고 JSON을 붙여 넣는다. 표지가 있으면 JPEG·PNG·WebP
파일(최대 5 MiB)을 선택한 뒤 업로드한다. 화면은 표지를 S3에 먼저 올리고 성공한 경우에만 발급된
`coverImageKey`를 포함해 도서 API를 호출한다. 표지가 없으면 파일을 선택하지 않는다.

도서 데이터 업로드는 단일 DB 트랜잭션이라 실패 시 도서·본문은 저장되지 않는다. 다만 S3 업로드
후 도서 API가 실패하면 표지 객체는 남을 수 있으며, 고아 객체 정리는 후속 백로그다.

| 에러 코드 | 원인 | 조치 |
|---|---|---|
| `UNAUTHORIZED` (401) | 토큰 누락·불일치 | 토큰 확인 |
| `INVALID_REQUEST` | 필드 검증 실패 (길이, 빈 구조, 공백 본문, ISNI 형식 등) | message 참고해 JSON 수정 |
| `AUTHOR_NOT_FOUND` | 없는 `authorId` 참조 | 작가 목록 다시 확인 |
| `AUTHOR_NAME_MISMATCH` | ISNI는 같은데 이름이 기존 등록과 다름 | 등록된 이름으로 통일 |
| `DUPLICATE_AUTHOR` | 한 업로드에 같은 작가 중복 기재 | authors 배열 정리 |
| `DUPLICATE_BOOK` | 제목·출판사·출판연도·작가 구성이 동일한 도서 존재 | 이미 올라간 책인지 확인 |
