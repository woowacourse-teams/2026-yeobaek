# 개발 서버 관측 전환

서버 접속·secret 입력·배포·Better Stack 확인은 개발자가 수행한다. 운영 배포는 포함하지 않는다.
앱 재생성 중 요청 중단이 발생하며 Collector 재시작·SDK 버퍼 종료·재시도 한계로 관측 데이터
공백이나 일부 유실이 생길 수 있다. 이 절차는 무중단·무손실 전환을 보장하지 않는다.

## 적용 파일

| 저장소 | 서버 `DEPLOY_DIR` 안의 파일 | 관리 대상 |
| --- | --- | --- |
| `infra/dev/docker-compose.yml` | `docker-compose.yml` | 앱·MySQL·Collector |
| `infra/dev/otel-collector.yaml` | `otel-collector.yaml` | 기존 인프라 + 앱 세 신호 |
| `infra/dev/.env.example` | `.env`의 참고값 | Compose 값 치환; 기존 파일에 필요한 값만 반영 |
| `infra/dev/otel.env.example` | `otel.env`의 참고값 | Collector 컨테이너의 env_file |
| `infra/dev/backup.sh`, `rollback.sh` | 별도 준비 디렉터리 | 백업·원복 명령 |

예시의 빈 값은 secret이 없다는 뜻이다. 예시 파일로 서버 환경 파일 전체를 덮어쓰지 않는다.
`.env`는 자동으로 앱 환경이 되지 않는다. 최종 Compose의 `app.environment`에 나열된 값만
전달되며 `otel.env`는 Collector에만 전달된다.

| 앱에 전달하는 환경변수 | Spring 설정/효과 |
| --- | --- |
| SPRING_PROFILES_ACTIVE=prod | 기존 DB·S3 런타임 프로필 유지 |
| SPRING_APPLICATION_NAME=yeobaek-api | spring.application.name, 세 신호 resource의 service.name |
| OBSERVABILITY_ENABLED=true | management.logging.export.otlp.enabled, management.tracing.export.otlp.enabled, management.otlp.metrics.export.enabled |
| OBSERVABILITY_OTLP_ENDPOINT=http://otel-collector:4318 | logging/tracing endpoint와 metrics url에 각각 /v1/logs, /v1/traces, /v1/metrics를 붙임 |
| DEPLOYMENT_ENVIRONMENT=dev | management.opentelemetry.resource-attributes[deployment.environment.name] |
| MANAGEMENT_TRACING_SAMPLING_PROBABILITY=1.0 | management.tracing.sampling.probability; 개발 검증 중 100% |
| JAVA_TOOL_OPTIONS | JVM이 직접 읽음. 기존 옵션 중 Agent 관련 옵션만 제거 |
| DB_URL | YEOBAEK_DATABASE_URL 또는 기존 mysql URL을 Compose가 전달 |

이름만 `OTEL_...`인 임의 변수가 Spring에 연결된다고 가정하지 않는다. 새 Compose에는 Agent
전용 변수가 없다. 기존 OTEL_SERVICE_NAME·OTEL_EXPORTER_OTLP_*·OTEL_TRACES_EXPORTER·
OTEL_METRICS_EXPORTER·OTEL_LOGS_EXPORTER·OTEL_INSTRUMENTATION_*와 직접 전송용
LOGGING_CONFIG·BETTER_STACK_SOURCE_TOKEN·BETTER_STACK_INGEST_URL을 앱에서 제거한다.
특히 OTEL_LOGS_EXPORTER=none이 남으면 Boot 4.1 환경 매핑이 로그 전송을 끌 수 있다.
`-Dotel.*`와 `-Dlogging.config=...`가 JAVA_TOOL_OPTIONS에 있으면 함께 확인한다.

Collector `otel.env`에는 기존 infra-dev의 `BETTER_STACK_OTLP_ENDPOINT`,
`BETTER_STACK_SOURCE_TOKEN`, `MYSQL_MONITOR_PASSWORD`를 유지하고, yeobaek-dev의
`YEOBAEK_DEV_OTLP_ENDPOINT`, `YEOBAEK_DEV_SOURCE_TOKEN`을 추가한다. endpoint는 각 소스의
**OTLP base URL**이며 `/v1/logs` 등을 붙이지 않는다. 기존 Logtail ingest URL을 추정해 쓰지 않는다.
Collector가 경로와 `Authorization: Bearer ...`를 붙인다. 앱에는 Better Stack token이 없다.

## 준비: 자동 배포와 수동 전환 충돌 방지

최신 `.github/workflows/backend-dev.yml`은 develop push 후 `~/yeobaek-dev`에서 자동 배포하고
image prune도 수행한다. 이번에 확인된 실제 구성은 `~/yeobaek`이다. **경로를 임의로 바꾸지
않는다.** 전환 동안 GitHub의 backend-dev workflow를 일시 중지하거나 develop 병합을 보류한다.
수동으로 이미지를 준비하는 아래 경로는 develop 병합을 요구하지 않는다. 운영 workflow와 main은
실행하지 않는다. 재개 전 실제 배포 경로와 workflow 경로의 차이를 별도로 해소해야 한다.

이 PR을 체크아웃한 작업 PC에서 필요한 파일만 서버의 별도 준비 폴더에 복사한다.

```bash
# 작업 PC, 저장소 루트에서. SSH_HOST는 본인의 개발 서버 SSH 별칭/주소이다.
SSH_HOST='<개발 서버 SSH 별칭>'
ssh "$SSH_HOST" 'mkdir -p ~/yeobaek-observability'
scp backend/infra/dev/{docker-compose.yml,otel-collector.yaml,otel.env.example,.env.example,backup.sh,rollback.sh} \
  "$SSH_HOST:yeobaek-observability/"
```

이후 1~8번 명령은 같은 서버 셸에서 순서대로 실행한다. 중간 명령이 실패하면 다음 단계로
넘어가지 않는다. `.env`·otel.env·inspect·resolved Compose는 비밀값을 포함하므로 출력·공유하지 않는다.

## 1. 기존 이미지·설정·환경 백업

```bash
set -euo pipefail
umask 077
export DEPLOY_DIR="$HOME/yeobaek"
OBS_FILES="$HOME/yeobaek-observability"
cd "$DEPLOY_DIR"
# 실행 중 컨테이너가 가리키는 실제 경로를 먼저 확인한다.
docker inspect -f '{{index .Config.Labels "com.docker.compose.project.working_dir"}}' yeobaek-app
BACKUP=$(bash "$OBS_FILES/backup.sh")
PROJECT=$(cat "$BACKUP/project")
printf '백업 위치: %s\nCompose 프로젝트: %s\n' "$BACKUP" "$PROJECT"
```

성공 기준: 실제 경로가 DEPLOY_DIR와 일치하고 백업 스크립트가 0으로 종료한다. 백업에는 원본
Compose·Collector·두 환경 파일·Agent JAR 디렉터리·실제 컨테이너 환경·resolved Compose·이미지
ID/태그와 **이전 앱/Collector 이미지 tar**가 있다. 이후 모든 명령에서 기존 PROJECT를 유지한다.
경로가 다르면 DEPLOY_DIR를 실제 값으로 정정한 뒤 처음부터 실행한다.

## 2. 새 앱 이미지 준비와 경로 확인

작업 PC의 이 PR 체크아웃에서 검증된 이미지를 발행한다. 이미 CI가 발행한 정확한 커밋 이미지가
있으면 이 빌드 대신 그것을 사용한다. 현재 workflow는 빌드 뒤 자동 배포하므로 위 준비 조건을
먼저 충족한다.

```bash
# 작업 PC, 이 PR 저장소의 backend에서 실행한다.
./gradlew build
REVISION=$(git rev-parse HEAD)
# 본인의 Docker Hub 계정을 설정한다. docker login으로 인증한다.
DOCKERHUB_USERNAME='<Docker Hub 계정>'
docker buildx build --platform linux/amd64,linux/arm64 -f infra/prod/Dockerfile \
  -t "$DOCKERHUB_USERNAME/yeobaek-backend:$REVISION" \
  -t "$DOCKERHUB_USERNAME/yeobaek-backend:develop" --push .
printf '%s/yeobaek-backend:%s\n' "$DOCKERHUB_USERNAME" "$REVISION"
```

```bash
# 개발 서버의 앞서 사용한 셸로 돌아와, 위에서 발행한 정확한 값을 입력한다.
NEW_IMAGE='<Docker Hub 계정>/yeobaek-backend:<검증된 커밋 SHA>'
docker pull "$NEW_IMAGE"
EXPECTED_IMAGE_ID=$(docker image inspect -f '{{.Id}}' "$NEW_IMAGE")
# 최종 Compose의 develop 태그는 유지하면서 이번에 검증한 이미지로 고정한다.
docker image tag "$NEW_IMAGE" "${NEW_IMAGE%:*}:develop"
cd "$DEPLOY_DIR"
test "$(pwd -P)" = "$(cat "$BACKUP/deploy-dir")"
```

성공 기준: 새 커밋 이미지 pull 성공, EXPECTED_IMAGE_ID 저장, 이전 이미지는 백업 tar와 rollback
태그로 유지된다. NEW_IMAGE는 관측 변경이 포함된 커밋이어야 한다.

## 3. Collector 설정·secret 반영과 검사

```bash
cd "$DEPLOY_DIR"
cp "$OBS_FILES/otel-collector.yaml" ./otel-collector.yaml
# 기존 세 변수는 유지하고 새 YEOBAEK_DEV_* 두 값만 실제 소스 값으로 추가한다.
${EDITOR:-vi} otel.env
chmod 600 .env otel.env
# 구문·receiver·processor·exporter 호환성을 실제 서버의 Linux 이미지로 검사한다.
docker compose -p "$PROJECT" -f docker-compose.yml config -q
docker compose -p "$PROJECT" -f docker-compose.yml run --rm --no-deps otel-collector \
  validate --config=/etc/otelcol-contrib/config.yaml
```

성공 기준: 두 명령 모두 exit 0. otlp receiver는 HTTP 4318을 수신하고 logs/app·traces/app·
metrics/app은 앱 exporter, metrics/infra는 기존 exporter만 사용한다. mysql 및 sqlquery receiver의
사용자·권한·CPU 수집 설정·60초 주기는 기존과 같다. validation은 secret 유효성/외부 수신 성공을
증명하지 않으므로 다음 단계에서도 확인한다.

## 4. Collector만 재생성하고 수신·전송 준비 확인

```bash
docker compose -p "$PROJECT" -f docker-compose.yml up -d --no-deps --force-recreate otel-collector
docker compose -p "$PROJECT" -f docker-compose.yml ps otel-collector
docker compose -p "$PROJECT" -f docker-compose.yml logs --since=3m otel-collector
# 선택: Collector 내부 telemetry를 네트워크 공유 진단 컨테이너로 확인한다.
docker run --rm --network container:yeobaek-otel-collector curlimages/curl:8.16.0 \
  -fsS http://127.0.0.1:8888/metrics > "$BACKUP/collector-after.prom"
grep -E 'otelcol_.*(accepted|sent|failed|refused)' "$BACKUP/collector-after.prom"
```

성공 기준: running, `Everything is ready`와 HTTP 4318 receiver 시작, 401/403·TLS·connection 오류가
없다. 60초 이상 기다려 infra-dev의 기존 EC2·MySQL·mysql.query.* 갱신과 exporter 전송 증가를
확인한다. 준비 시점에는 이전 Agent가 아직 앱 데이터를 보낼 수 있다. 전환 전후 데이터를 섞어
최종 연결·중복 여부를 판정하지 않는다. 토큰·수신 권한 오류가 있으면 앱 전환 전에 해결한다.

## 5. 새 Compose와 앱 환경 적용 준비

```bash
cp "$OBS_FILES/docker-compose.yml" "$DEPLOY_DIR/docker-compose.yml"
# 기존 DB/S3/PostHog/admin 값을 유지한다. JAVA_TOOL_OPTIONS에는 기존 비-Agent JVM 옵션만 남긴다.
# .env의 기존 LOGGING_CONFIG·BETTER_STACK_INGEST_URL·BETTER_STACK_SOURCE_TOKEN은 제거한다.
# otel.env의 기존 infra-dev 토큰은 제거하지 않는다.
${EDITOR:-vi} "$DEPLOY_DIR/.env"
docker compose -p "$PROJECT" -f docker-compose.yml config -q
docker compose -p "$PROJECT" -f docker-compose.yml config --format json > "$BACKUP/compose.new.json"
python3 - "$BACKUP/compose.new.json" <<'PY'
import json,sys
c=json.load(open(sys.argv[1])); app=c['services']['app']; e=app['environment']
assert e['SPRING_PROFILES_ACTIVE']=='prod'
assert e['SPRING_APPLICATION_NAME']=='yeobaek-api'
assert e['DEPLOYMENT_ENVIRONMENT']=='dev'
assert e['OBSERVABILITY_ENABLED']=='true'
assert e['OBSERVABILITY_OTLP_ENDPOINT']=='http://otel-collector:4318'
assert float(e['MANAGEMENT_TRACING_SAMPLING_PROBABILITY'])==1
assert not any(k.startswith(('OTEL_', 'BETTER_STACK_')) or k=='LOGGING_CONFIG' for k in e)
assert '-javaagent' not in e.get('JAVA_TOOL_OPTIONS','')
assert not app.get('volumes')
assert not c['services']['otel-collector'].get('ports')
print('앱 환경 전달과 Agent/직접 전송 제거 확인')
PY
```

성공 기준: prod·DB override·S3·PostHog·develop 태그·MySQL volume·Collector 제한이 유지된다.
Agent JAR 파일은 원복을 위해 디스크에 남겨 두되 app의 볼륨 연결은 없다.

## 6. 앱만 재생성

```bash
docker compose -p "$PROJECT" -f docker-compose.yml up -d --no-deps --force-recreate --pull never app
APP_ID=$(docker compose -p "$PROJECT" -f docker-compose.yml ps -q app)
test "$(docker inspect -f '{{.Image}}' "$APP_ID")" = "$EXPECTED_IMAGE_ID"
test "$(docker compose -p "$PROJECT" -f docker-compose.yml ps -q mysql)" = "$(cat "$BACKUP/mysql-container-id")"
docker inspect "$APP_ID" > "$BACKUP/app.after.inspect.json"
# 핵심 업무 환경변수가 이전과 같은지 비밀값을 출력하지 않고 비교한다.
python3 - "$BACKUP/app.inspect.json" "$BACKUP/app.after.inspect.json" <<'PY'
import json,sys
def env(p): return dict(v.split('=',1) for v in json.load(open(p))[0]['Config']['Env'])
a,b=map(env,sys.argv[1:])
keys={'DB_URL','DB_USERNAME','DB_PASSWORD','ADMIN_TOKEN'}
keys.update(k for k in a if k.startswith(('BOOK_COVER_', 'POSTHOG_')))
assert all(a.get(k)==b.get(k) for k in keys), 'DB/S3/PostHog/admin 환경 차이 확인 필요'
print('기존 DB/S3/PostHog/admin 환경 보존 확인')
PY
curl --fail --retry 20 --retry-delay 3 --retry-connrefused http://127.0.0.1:8080/health
docker run --rm --network "container:$APP_ID" curlimages/curl:8.16.0 \
  -fsS http://127.0.0.1:8081/actuator/health
# 앱 포트에서 관리 메트릭을 노출하지 않는지 확인한다. 200이면 실패이다.
test "$(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/actuator/metrics)" != 200
```

성공 기준: 새 이미지 ID 일치, MySQL 컨테이너 ID 동일, 업무 환경 비교 통과, 두 health 200,
앱 기동/OTLP 오류 없음. 8081·4318·8888은 호스트에 publish하지 않는다. `compose down`이나
볼륨 삭제는 실행하지 않는다.

## 7. 정상·실패 요청과 풀 메트릭

```bash
# 실제 개발 테스트 회원 ID를 입력한다. 새 회원을 만들 필요가 없다.
MEMBER_ID='<개발 테스트 회원 ID>'
TRACE_OK=$(openssl rand -hex 16)
TRACE_FAIL=$(openssl rand -hex 16)
PARENT_SPAN=$(openssl rand -hex 8)
curl --fail -H "X-Member-Id: $MEMBER_ID" \
  -H "traceparent: 00-$TRACE_OK-$PARENT_SPAN-01" http://127.0.0.1:8080/api/books
# 형식 오류: 인증 SQL 후에 의도한 400 오류를 확인한다.
curl -sS -w '\nHTTP %{http_code}\n' -H "X-Member-Id: $MEMBER_ID" \
  -H "traceparent: 00-$TRACE_FAIL-$PARENT_SPAN-01" http://127.0.0.1:8080/api/books/not-a-number
# 후속 익명 요청: memberId가 남으면 안 된다.
curl --fail http://127.0.0.1:8080/health
printf '정상 trace: %s\n실패 trace: %s\n' "$TRACE_OK" "$TRACE_FAIL"
for metric in hikaricp.connections.acquire hikaricp.connections.pending hikaricp.connections.active hikaricp.connections.timeout; do
  docker run --rm --network "container:$APP_ID" curlimages/curl:8.16.0 \
    -fsS "http://127.0.0.1:8081/actuator/metrics/$metric"
done
```

성공 기준: 정상 200·실패 400·후속 health 200. 두 trace에 HTTP와 SQL span이 있고 요청 시작·완료
로그가 같은 trace ID를 사용한다. 두 요청은 다른 trace이고 익명 health에는 memberId가 없다.
풀 획득 timer count가 증가하고 pending/active/timeout 지표가 존재한다. 정상 상태에서
pending·timeout이 0인 것은 정상이다. 실제 타임아웃 발생 검증은 로컬 격리 풀 테스트로 수행하며
개발 공용 DB의 풀을 고의로 고갈시키지 않는다.

이 400 요청은 예상 오류이므로 exception stack을 요구하지 않는다. 예상하지 못한 예외의 타입·
스택, 예외 후 MDC/추적 정리, Collector 503 중 앱 정상 응답은 로컬 통합 테스트가 담당한다.
개발 서버에서 전송 장애까지 재확인하려면 검증 시간에 Collector만 stop하고 정상 요청이 계속
200인지 확인한 뒤 즉시 start한다. 이 동안 텔레메트리가 지연·유실될 수 있다.

## 8. Better Stack 실제 수신과 연결 확인

수집 주기(메트릭 기본 1분) 이상 기다린 뒤 다음을 확인한다. 로컬 출력·Collector ready만으로
실제 원격 수신 성공을 판정하지 않는다.

- yeobaek-dev **Logs & Events**에서 앱 시작 로그와 위 요청 로그가 열린다.
- TRACE_OK·TRACE_FAIL로 검색하고 원본 OTLP trace ID가 실제 HTTP/SQL span과 같다.
  trace ID를 UUID MDC 필드나 `meta.traceId`로 대체하지 않는다. 사후 ID 복사 변환은 필요 없다.
- 요청 시작·완료 로그의 span ID는 HTTP server span이다. SQL 실행 중 로그가 있다면 그 당시
  활성 SQL span과 연결된다. 서비스 로그가 항상 SQL span에 붙어야 하는 것은 아니다.
- operation·result·memberId·resultCount(숫자)·searchUsed(불리언)가 필드로 남는다.
  예외 로그가 있으면 exception.type/message/stacktrace를 확인한다. 시작 로그의 빈 trace는 정상이다.
- 같은 trace에 HTTP server span이 하나이고 같은 SQL이 계측 때문에 이중 생성되지 않는다.
  요청 시작·완료는 의도한 두 로그다. 한 로그 이벤트의 원격 중복과 구분한다.
- yeobaek-dev에 http.server.requests·JVM·Hikari acquire/pending/active/timeout이 갱신된다.
  traceId/memberId 메트릭 태그가 없고 Agent 메트릭이 새 시점에 계속 유입되지 않는다.
- infra-dev에는 EC2·MySQL·mysql.query.*가 계속 들어오고 앱 OTLP metrics는 새로 들어오지 않는다.
  이전 infra-dev의 앱 traces는 과거 데이터로 남는다.
- Collector self metrics의 accepted/sent가 증가하고 refused/send_failed가 지속 증가하지 않는다.

여기까지 개발자가 실제 확인하기 전 보고 상태는 **로컬 검증 완료, 서버 검증 대기**이다.
로컬 통합 검증에 제한이 남았다면 해당 제한을 별도로 표시하며 로컬 완료라고 쓰지 않는다.

## 원복

서버에서 실제 백업 경로를 지정한다. 중간 셸을 잃어도 이 명령으로 복구할 수 있다.

```bash
OBS_FILES="$HOME/yeobaek-observability"
BACKUP='<1단계에서 출력된 절대 백업 경로>'
bash "$OBS_FILES/rollback.sh" "$BACKUP"
```

스크립트는 저장된 이전 앱/Collector 이미지를 load하고 원래 설정·환경·Agent 파일을 복원한 뒤
**이전 이미지로** Collector와 앱만 순서대로 재생성한다. MySQL을 재생성하거나 데이터 볼륨을
삭제하지 않는다. 이미지 pull로 가변 develop 태그를 다시 받지 않는다. `/health` 200, 기존
MySQL 컨테이너 ID 유지, 이전 Agent/직접 로그 경로 복구를 확인한다. 자동 배포 workflow는
원인 해결 전 재개하지 않는다. 기존 로그·트레이스의 ID 불일치도 원복 시 함께 돌아온다.
