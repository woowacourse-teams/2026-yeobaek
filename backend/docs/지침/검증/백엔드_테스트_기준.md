# 백엔드 테스트 기준

[여백 팀 테스트 기준](../../../../docs/팀_테스트_기준.md)을 따른다. API 소비자가 의존하는 동작과 그 동작의 저장 결과를 보호한다. [API 명세](../../../../docs/API.md)와 현행 구현으로 어떤 회귀를 잡아야 하는지 확인한 다음, 그 회귀를 발견할 수 있는 가장 좁은 범위에 작성한다. 명세와 구현의 차이가 제품 동작에 영향을 주면 기대 동작을 팀에 확인한다.

## 테스트 수준 선택

- **단위 테스트**는 기본이다. 모임 참여 자격, 댓글 노출 범위, 진도 계산처럼 입력과 상태로 판단할 수 있는 정책을 검증한다. 서비스가 저장소에 의존하면 조회 결과를 스텁으로 설정하고 공개 메서드의 결과, 업무 오류 또는 의미 있는 상태 변경을 확인한다.
- **웹 슬라이스 테스트**는 HTTP 경로, 입력 바인딩·거부, 상태·헤더·응답 필드처럼 웹 계층에서 성립하는 계약을 확인한다. 업무 정책은 단위 테스트에서 검증하고, JSON API의 작성 방법은 [컨트롤러 테스트 하네스](../코딩/컨트롤러_테스트_하네스.md)를 따른다.
- **통합 테스트**는 MySQL 쿼리·제약·잠금·마이그레이션이나 Spring 트랜잭션·커밋 후 이벤트처럼 실제 구성요소가 있어야 결과를 확인할 수 있을 때 사용한다. 저장 결과 또는 롤백이 관심사라면 트랜잭션이 끝난 뒤의 상태를 확인한다. 신규 통합 테스트를 리뷰할 때 단위나 슬라이스로 재현할 수 없는 실패를 설명한다.
- **백엔드 E2E**는 팀 공통 기준의 예외다. 핵심 사용자 흐름에서 테스트 서버에 실제 HTTP 요청을 보내 앞선 요청의 저장 결과가 후속 요청에 반영되는지 확인한다. 모바일 실행 환경을 구성하지 않아도 요청 간 연결을 검증할 수 있다. 예를 들어 댓글을 작성하고 수정한 뒤 재조회해 새 본문이 표시되는지 확인한다. [댓글 HTTP 테스트](../../../src/test/java/yeobaek/backend/e2e/CommentE2eTest.java)

## 의존성 및 검증 범위

- 실제 DB가 필요한 통합·E2E 테스트는 Testcontainers의 격리된 MySQL을 사용한다. 각 테스트는 독립된 데이터로 실행한다.
- FCM·S3 등 외부 의존성은 테스트 경계에서 스텁으로 제어한다. 필요한 성공·실패 응답만 설정하고 우리 코드가 그 결과를 처리하는 방식을 확인한다.
- 운영·도구의 회귀 기준은 문서화된 계약에 둔다. 예를 들어 [로그의 핵심 필드와 민감 정보 제외](../../로깅_가이드.md), [관측 신호의 상관관계와 전송 실패 격리](../../Better_Stack_연동.md), [OpenAPI 제공 형식](../../../../docs/API.md)을 보호한다.
- 응답이나 저장 상태가 같을 때 바뀔 수 있는 내부 호출 순서와 중간 자료구조, 외부 라이브러리 자체 동작은 검증에서 제외한다. 같은 오류를 여러 계층에서 반복해서 만들기 전에 각 테스트가 새로 잡는 회귀가 있는지 확인한다.

전체 검증은 [커밋 전 게이트](커밋_전_게이트.md)를 따른다.
