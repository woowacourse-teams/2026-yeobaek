# 그릴(/grill-me) 활용 지침

`/grill-me`는 계획·설계를 설명한 뒤 호출하면, 모든 결정이 해소될 때까지 라운드 단위로
질문하는 인터뷰 세션을 시작한다(저장소 루트 `.claude/skills/` 참고). 이 문서는 언제
그릴을 돌리고 언제 생략하는지에 대한 팀 합의다.

## 그릴을 돌리는 시점

1. **새 기능의 설계 초안이 섰을 때.** 그릴은 백지에서 아이디어를 만들어주는 도구가
   아니라 이미 있는 계획의 구멍을 찾는 도구다. 방향을 2~3문단으로 설명할 수 있는
   상태에서 호출한다.
2. **되돌리기 비싼 결정 직전.** 스키마, 외부 노출 API 계약, 동시성 제약 등. 한번
   데모에 나가면 바꾸는 데 다른 사람/시스템이 움직여야 하는 결정이 대상이다.
3. **PRD에 애매한 부분이 있는 채로 구현에 들어가려 할 때.** 명세 공백을 구현 중에
   발견하는 것보다 그릴에서 드러내는 쪽이 싸다.
4. **지침에 기준이 없는 반복 결정을 만났을 때 — 하네스 보강 목적.** 메서드 추출
   같은 가독성 결정처럼, 지침이 기준을 정하지 않아 매번 감으로 판단하는 영역이
   대상이다. 결정 하나를 잘 내리는 것이 아니라 **기준을 도출해 하네스(지침)에
   반영하는 것**이 목적이다. 아래 참고.

## 하네스 보강 그릴 — 기준 세우기

하네스(`docs/지침`)는 팀이 미리 관측한 결정 영역만 커버한다. 메서드 추출을 언제
할지, 가독성을 무엇으로 판단할지 같은 영역은 아직 기준이 없어 매번 암묵적으로
판단하게 되는데, 그릴이 파고드는 것이 바로 그 암묵 지점이다. 질문 방향을 개별
결정의 옳고 그름이 아니라 다음에 맞춘다.

- 이 결정을 지금 어떤 기준으로 내렸는가? 그 기준은 지침 어디에 적혀 있는가?
- 같은 판단이 앞으로도 반복될 영역인가? 반복된다면 러프한 기준이라도 지금
  세워둘 가치가 있는가?
- 도출한 기준은 어느 지침 문서에 들어가야 하는가? (없으면 새 문서를 만든다)

개별 결정은 그릴 없이 지나가도 되돌리기 싸지만, 기준 없이 쌓이면 코드베이스의
일관성이 조용히 무너진다. 프로젝트 초반에 이런 그릴로 하네스가 제대로 동작하는지
확인하고, 관측하지 못한 영역의 기준을 러프하게라도 세워두는 것이 산출물이다.

## 그릴을 생략하는 경우

- **리뷰어 대체 용도.** 토의와 리뷰는 이미 3인이 수행하므로 효용이 없다.
- 지침·명세에 이미 답이 있는 결정.
- 되돌리기 싼 결정 그 자체(변수명, 사소한 코드 배치 등). 단, 되돌리기 싼
  결정이라도 지침에 기준이 없는 채 반복되고 있다면 위 4번 목적으로는 돌릴 수 있다.

## 기본 리듬

태스크 설계 방향을 2~3문단으로 설명 → `/grill-me` → 라운드를 돌며 결정 확정 →
같은 세션에서 확정 내용 기반으로 구현. 세션을 이어가면 결정 사항이 유실되지 않는다.
확정된 결정 중 [피드백_루프_하네스.md](../피드백_루프_하네스.md) 2장 멈춤 기준에
해당하는 것은 여전히 결정 요청서 경로를 따른다 — 그릴은 관문을 대체하지 않는다.
