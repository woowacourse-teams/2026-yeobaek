# 도메인 모델링 지침

> 배경: 코드 리뷰 지적 (2026-08-05)
> - "객체가 본인의 상태를 스스로 책임지지 않고 외부 인프라에 의존해, 세부 구현이 외부에
>   누수되고 이해하기 어려운 코드가 만들어졌다."
> - "TDA를 준수하지 않아서 코드 가독성이 떨어진다."

## 1. 객체는 자기 상태를 스스로 책임진다

- 도메인 의미가 있는 상태 변화는 **엔티티의 도메인 메서드 안에서 완결**한다.
  상태 변화에 따라오는 파생 상태(`updatedAt` 등)도 같은 메서드가 직접 갱신한다.
- 생성 시점에 정해지는 상태(`createdAt` 등)는 생성자가 채운다.
- **도메인 상태를 JPA 생명주기 콜백(`@PrePersist`, `@PreUpdate`)이나 Auditing에 위임하지
  않는다.** 인프라가 상태를 대신 채우면, 그 상태가 언제 갱신되는지 코드만 읽어서는 알 수
  없게 되고 세부 구현이 외부로 누수된다.
- **신호 규칙:** 서비스 코드가 정합성을 위해 `flush()`·`refresh()` 호출을 필요로 한다면
  그 자체가 설계 결함의 신호다. 호출을 추가하지 말고 멈춰서, 인프라에 위임된 책임을
  객체로 되돌리는 방향을 먼저 검토한다.

### 사례 — 이 지적을 만든 실제 코드

```java
// 나쁨: updatedAt을 @PreUpdate가 채우므로, 응답에 갱신 시각을 담으려면
// 서비스가 flush()를 호출해 콜백을 강제로 당겨야 했다.
comment.updateContent(content);
commentRepository.flush();
return CommentResponse.of(comment, memberId);

// 좋음: 도메인 메서드가 상태 변화를 완결한다. flush()가 필요 없다.
public void updateContent(String content) {
    validateContent(content);
    this.content = content;
    this.updatedAt = LocalDateTime.now();
}
```

## 2. TDA — 묻지 말고 시켜라

- 다른 객체의 내부를 getter로 꺼내 와서 **바깥에서 판단·계산하지 않는다.**
  판단·계산은 그 데이터를 가진 객체에 메서드를 만들어 시킨다.
- **위반 신호:** getter 체인이 2단 이상 이어진 뒤 비교·분기·연산이 나오는 코드.
- 객체를 가로질러야 하는 판단은 위임 사슬로 푼다. 각 객체는 자신이 직접 아는 것에만
  답하고, 모르는 것은 자신의 협력 객체에게 다시 시킨다.
- 식별자 동등성 비교(`a.getId().equals(b.getId())`)도 바깥에 노출하지 말고
  해당 객체의 의도가 드러나는 메서드로 감싼다.

### 사례 — 이 지적을 만든 실제 코드

```java
// 나쁨: 서비스가 Passage → Chapter → Book → id 를 전부 꺼내 와 직접 판단한다.
if (!passage.getChapter().getBook().getId().equals(club.getBook().getId())) { ... }

// 좋음: 데이터를 가진 객체에게 시키고, 각 객체는 협력 객체에 위임한다.
if (!club.isReading(passage)) { ... }

// Club
public boolean isReading(Passage passage) { return passage.belongsTo(book); }
// Passage
public boolean belongsTo(Book book) { return chapter.belongsTo(book); }
// Chapter
public boolean belongsTo(Book other) { return book.isSame(other); }
// Book
public boolean isSame(Book other) { return Objects.equals(id, other.getId()); }
```

> **주의 — JPA 프록시에서는 인자로 받은 엔티티의 필드 직접 접근 금지.** 위임 사슬 끝에서
> 식별자를 비교할 때 `other.id`처럼 파라미터로 받은 엔티티의 필드를 직접 읽으면 안 된다.
> 지연 로딩 연관관계로 얻은 참조는 아직 초기화되지 않은 Hibernate 프록시일 수 있고,
> 프록시의 필드는 실제 값이 채워지지 않은 채로 남아 있다(식별자 비교가 항상 실패하는
> 회귀로 이어졌다 — 2026-08-06 리뷰 지적). 이 경우 `other.getId()`처럼 getter를 통해
> 접근해야 프록시가 이미 알고 있는 식별자를 안전하게 얻는다. `this`(메서드를 호출한
> 객체 자신)의 필드 접근은 안전하다 — 메서드 호출 자체가 프록시를 초기화시킨 뒤 실제
> 엔티티에서 실행되기 때문이다.

### 적용 경계

- TDA의 적용 대상은 **판단·분기·계산**이다. 컨트롤러·서비스가 DTO를 조립하기 위해
  값을 읽어 가는 단순 getter 접근은 위반이 아니다.
- 단, DTO 조립 중에도 조건 판단이 끼어들면 그 판단부터는 객체의 메서드로 옮긴다.

## 3. 값 객체 도입 기준

- `null` 체크 이외의 **비즈니스 요구사항**이 존재하는 값은 VO로 만든다. 형식·허용 범위·정규화·
  값 계산처럼 값 자체로 설명할 수 있는 규칙을 VO가 검증하거나 수행하고, 엔티티는 검증을 대신하지
  않고 해당 VO를 실제 필드 타입으로 저장한다.
- 이 기준에서 비즈니스 요구사항은 제품과 도메인이 그 값에 부여한 의미를 뜻한다. DB 또는
  프레젠테이션 계층의 요구사항만 존재하는 값은 VO 도입 대상이 아니다. 컬럼 길이·unique 제약처럼
  영속성 구현에서만 필요한 조건이나 요청 한 번에 보여 줄 개수처럼 화면·전송 경계에서만 필요한
  조건을 도메인 규칙으로 해석하지 않는다.
- DB나 프레젠테이션 제약과 같은 숫자가 코드에 있더라도, 별도의 제품 정책 근거가 확인되면 그
  제품 정책을 VO가 소유한다. 애너테이션이나 DTO 제약만 보고 비즈니스 규칙을 새로 추론하지 않는다.
- 여러 레코드와의 비교가 필요한 전역 유일성, 엔티티 간 소속 관계처럼 값 하나만으로 판단할 수 없는
  규칙은 VO에 넣지 않는다. 해당 규칙을 판단할 수 있는 엔티티·서비스·저장소가 소유한다.

### 값 객체의 전달 경계

- 도메인 계산에 전달하는 값은 VO 타입을 유지한다. 이미 검증한 VO를 원시값으로 풀었다가
  같은 VO로 재생성하지 않는다. 응답 DTO나 원시값을 요구하는 조회 경계에서 값을 변환한다.
- 값의 정규화·검증 진입점은 VO에 둔다. 엔티티에 값 정규화용 정적 우회 메서드를 두지 않는다.
- 2026-09-16 PR #164 리뷰 반영 결정: ISNI 정규화 진입점을 VO로 옮기고, 순서·본문 개수는
  도메인 내부에서 VO로 전달한다.

- 이름·제목·출판사처럼 이미 VO로 보관하는 값을 비교할 때는 원시값으로 풀지 않고 VO의 동등성을 사용한다.
  엔티티의 해당 getter도 VO를 반환하며, 응답 DTO나 저장소 쿼리의 표현으로 변환할 때만 값을 꺼낸다.
- 선택 정보인 ISNI·출판사의 부재는 nullable VO로 유지한다. 부재를 감추기 위해 유효하지 않은 빈 VO를 만들지 않는다.
- 이 반환 타입은 원시값의 무분별한 사용을 줄이지만 `value()` 호출 자체를 금지하지는 않는다.
  변환이 응답·조회 경계에 있는지는 호출부 리뷰와 API 회귀 테스트로 확인한다.

### 중복 판단의 목적과 책임

- 도서 중복 기준은 제목·출판사·출판 연도·작가 ID 집합을 함께 담은 `BookDuplicateCriteria`로 표현한다.
  일부 필드 비교와 작가 집합 비교를 엔티티와 서비스에 나눠 두지 않는다.
- 서비스는 기존 도서와 작가 관계를 조회하고 중복 오류를 처리한다. 기준 값 객체는 조회나 저장소 접근 없이
  전달받은 값의 동등성을 판단한다. 같은 작가 집합이면 순서에 관계없이 같은 기준이다.
- 메서드와 객체의 이름은 비교하는 필드 목록보다 사용 목적을 드러내도록 정한다.
- 결정 원본: 2026-09-16 작업 대화 — 개발자는 중복 판단 책임을 한 곳으로 모으는 방향에 동의했고,
  기존 이름이 이해하기 어려웠던 이유를 메서드의 목적이 명확하지 않았기 때문이라고 설명했다.

### 포함·제외 사례

- 포함: `Isni`의 형식과 정규화, `Email`의 형식과 정규화, 이름·제목의 제품 정책상 허용 길이,
  콘텐츠의 1부터 시작하는 순서, 의미 있는 본문 조회 시작·끝, 최근 읽은 순서와 전체 본문 수로
  계산하는 독서 진도율.
- 제외: MySQL `TEXT` 저장 한도 때문에 적용하는 문장 UTF-8 바이트 제한, 저장소 객체 키 형식,
  업로드 전송의 MIME·파일 크기, 한 요청에서 조회할 수 있는 최대 개수. 각각 DB·인프라·전송 경계의
  책임에 유지한다.
- `JoinCode`는 6자리 대문자·숫자라는 값 규칙과 코드 생성을 소유한다. 발급 코드의 전역 유일성은
  저장된 다른 코드와 비교해야 하므로 서비스와 저장소가 소유한다.

## 적용 시점

- 새로 작성·수정하는 코드에 즉시 적용한다.
- 리뷰에서 확인된 기존 위반(`Comment`의 `@PrePersist`/`@PreUpdate`, `CommentService.update`의
  `flush()`, `CommentService.validatePassageContext`의 getter 체인 등)은 2026-08-06 별도 정비
  작업으로 해소했다. 위 사례는 같은 문제가 재발하지 않도록 판단 기준으로 유지한다.
