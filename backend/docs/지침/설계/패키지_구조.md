# 패키지 구조 지침

> 배경: 코드 리뷰 지적 — "성격이 매우 다른 클래스들이 한 패키지 안에 모여 있다. 패키지에 계층을 도입해 정리했으면 좋겠다." (2026-08-05)

## 레거시 기능의 기본 구조

도메인 우선 분할(`yeobaek.backend.<도메인>`)은 유지하되, 각 도메인 패키지 내부를
계층 하위 패키지로 나눈다.

```
yeobaek.backend.<도메인>
├── controller   웹 어댑터
├── service      응용 서비스
├── repository   저장소
├── domain       엔티티·도메인 규칙
│   └── vo       값 객체
└── dto          요청·응답 객체
```

영역의 역할에 필요한 하위 패키지만 만들며, 위 구조를 맞추기 위한 빈 패키지는 만들지 않는다.
예를 들어 `admin`은 다른 도메인의 모델과 저장소를 사용하므로 현재 `controller`, `service`,
`dto`만 둔다.

## 배치 기준

| 하위 패키지 | 배치 대상 | 현재 코드 기준 예 |
|---|---|---|
| `domain` | `@Entity`, 도메인 규칙을 수행하는 순수 객체·열거형 | `Member`, `ClubMember`, `ClubMemberStatus` |
| `domain.vo` | 값의 검증·정규화·계산을 담당하는 값 객체 | `Nickname`, `BookDeduplicationKey` |
| `repository` | Spring Data 리포지토리 인터페이스, 쿼리 프로젝션 | `ClubRepository`, `ClubMemberCount` |
| `service` | `@Service` 응용 서비스 | `ClubService` |
| `controller` | `@RestController`, 인터셉터·리졸버 등 웹 계층 부속 | `ClubController` |
| `dto` | API 요청·응답 레코드 | `ClubCreateRequest`, `MyClubResponse` |

- 판단이 애매한 클래스는 "이 클래스가 의존하는 방향"으로 정한다. 웹 기술에 의존하면
  `controller`, 영속성 기술에 의존하면 `repository`, 아무 기술에도 의존하지 않으면 `domain`.
- 값 객체는 각 도메인의 `domain.vo`에 배치하고, 해당 값 객체의 테스트도 같은 패키지에 둔다.
  엔티티와 값 객체가 한 패키지에 모여 파악하기 어렵다는 2026-09-16 개발자 요청을 반영한다.
- `dto`는 현 규모에서 request/response로 더 세분하지 않는다.
- 도메인이 아닌 공통 패키지(`support`, `auth`)에는 도메인 계층을 강제하지 않는다. 내부 클래스의
  성격이 섞이면 기술 관심사별로 분리한다. 현재 `support.analytics`, `support.storage`가 이 원칙을
  적용한 사례이며, 규모가 작은 `auth`는 평면 구조를 유지한다.

## 코어 모듈 구조

공간·컨텐츠·감상·독서 기록처럼 여러 제품 기능에서 재사용하는 코어는 다음 경계를 사용한다.

```
yeobaek.backend
├── shared
│   ├── identity        모듈 사이에서 전달하는 강한 타입의 식별자 값
│   └── exception       모듈과 웹 계층이 함께 사용하는 오류 코드·로그 맥락 예외 계약
├── space
│   ├── api             다른 모듈과 상위 유스케이스에 공개하는 진입점
│   ├── internal        공개 계약을 실행하는 서비스와 구현체 공통 계약
│   ├── persistence     공간 루트 영속 어댑터
│   ├── club            독서 모임 구현과 전용 기능
│   └── publicroom      공개방 구현과 전용 기능
├── content
│   ├── api
│   ├── internal
│   ├── persistence
│   └── book            도서 구현과 전용 기능
├── appreciation
│   ├── api
│   ├── internal
│   ├── persistence
│   └── comment         댓글 구현과 전용 기능
├── reading
│   ├── api
│   ├── internal
│   └── persistence
├── collaboration
│   ├── api             연결·맥락 기능의 공개 계약
│   ├── internal        공개 계약 구현
│   ├── service         모듈 사이 관계의 기능
│   └── persistence     공간–컨텐츠·감상 맥락 관계 영속 어댑터
├── bootstrap           구현체를 종류별 맵으로 조립하는 Spring 설정
├── query               공개 모듈 API를 조합하는 상위 조회 서비스
└── application
    └── <유스케이스>   공개 모듈 API를 조합하는 트랜잭션 경계
```

- `Book`, `Club`, `PublicRoom`, `Comment`의 전용 기능과 저장소·응답 구현은 각각의 소유 도메인 안에 캡슐화한다. `content.book`, `space.club`, `space.publicroom`, `appreciation.comment`는 독립된 형제 모듈이 아니라 내부 구현 패키지다.
- 반환값도 소유 모듈의 공개 계약으로 정의한다. 공통 호출자는 구현 응답으로 다운캐스팅하지 않고 계약이 제공하는 속성을 사용한다. 여러 도메인의 조회를 조합할 때도 소유 모듈의 공개 조회 계약을 호출한다.
- 다른 모듈은 `api`와 `shared.identity`, `shared.exception`의 공통 계약만 사용한다. 형제 모듈의 `domain`이나
  `persistence`를 직접 참조하지 않는다.
- 구현체를 조립하는 `bootstrap`은 소유 모듈의 내부 Provider·Capability 계약을 사용한다. 이 조립 예외를
  일반 기능 호출자에게 적용하지 않으며, 모듈 서비스는 `bootstrap`을 참조하지 않는다.
- `application`은 여러 모듈이 협력하는 유스케이스를 조정한다. 개별 모듈은 `application`을
  역으로 의존하지 않는다.
- 여러 모듈의 공개 API를 조합하는 상위 조회 기능은 `…QueryService`라는 구체 서비스로 둔다.
  현재 단일 구현체만 있는 조회 서비스에는 별도 인터페이스를 만들지 않는다. 교체 가능한 조회 구현이나
  계약만 공개할 명확한 경계가 필요해지면 그때 추상화를 검토한다.
- 공간–컨텐츠 연결과 감상의 공간·컨텐츠·위치 맥락은 한 도메인에 귀속하지 않고
  `collaboration`이 소유한다.
- 모든 구현체가 지원하지 않는 동작을 하나의 범용 인터페이스에 넣지 않는다. 참여·방문처럼
  구현체마다 다른 기능은 책임을 소유한 모듈의 `api`에 작은 계약으로 나눈다. 타입별 구현 등록과
  중복 등록 거부 같은 기술 조립은 bootstrap/composition 경계가 맡는다.
- 기존 v1 컨트롤러와 DTO는 호환 웹 어댑터로 기존 경로에 둘 수 있다. 이 어댑터가 레거시 요청·응답·
  오류를 모듈 API로 변환하며, 레거시 DTO나 플래그를 코어에 전달하지 않는다.
- 패키지 경계 전용 자동 검사는 이번 리팩터링의 완료 조건에 포함하지 않는다. 위 의존 방향을
  구조 계약으로 먼저 적용하고, 검사 도구 도입은 후속 작업에서 결정한다.

## 공개 계약의 탐색 구조

- 같은 기능의 조회와 명령은 기능의 대표 공개 API에서 함께 찾을 수 있게 한다. 읽기 모델에서 쓰기
  메서드도 보이는 단점을 감수하더라도, 조회 전용 중복 계약을 추가해 공개 진입점을 흩뜨리지 않는다.
- 여러 기능이 섞인 `api`는 `metadata`, `body`, `club`, `publicroom`, `comment`처럼 기능별 하위 패키지로 묶는다. 호출 계약과 반환 계약·실패 타입을 같은 기능에서 찾을 수 있게 한다.
- 모듈 공통 계약은 `api` 바로 아래에 유지한다. 같은 기능의 소수 계약만 있는 패키지에는 형식적으로 계층을 추가하지 않는다.
- Provider·Capability처럼 구현체가 공유하는 계약은 소유 모듈의 `internal`에 둔다. 일반 기능 호출자는 `api`를 사용한다.
- `bootstrap`이 구현체를 종류별 불변 맵으로 조립하고 같은 종류의 중복 등록을 거부한다. 내부 서비스는 해당 맵에서 구현체를 선택하며, 단순 조회만을 위한 별도 Registry 계약을 두지 않는다. 상위 유스케이스·웹 어댑터의 Registry에는 이 정리 기준을 기계적으로 적용하지 않는다.
- 한 반환 계약에서만 사용하는 작은 하위 계약은 해당 반환 계약의 중첩 인터페이스로 둔다. 재사용되는 값 객체와 독립 기능 계약은 억지로 합치지 않는다.
- 선언한 클래스 밖에서도 사용하는 예외는 소유 기능 패키지의 독립 파일에 둔다. 클라이언트와 웹
  계층이 분기하는 실패 분류는 공통 `ErrorCode`로 표현하고, 같은 코드 안에서 로그로만 구분할 세부
  원인은 예외 발생 지점의 로그 맥락에 기록한다.
- 내부 도메인 객체와 JPA 엔티티를 통합한 구현체는 `Book`, `Club`, `PublicRoom`, `Comment`처럼 도메인 이름을 사용한다. JPA 매핑 역할은 패키지와 애너테이션으로 표현한다.
- 현재 같은 기능의 조회와 명령을 모은 대표 진입점은 `ClubApi`, `PublicRoomApi`,
  `PublicRoomVisitApi`, `ReadingProgressApi`, `AppreciationContextApi`다. 모임 가입처럼 독립된 관계 기능은
  `ClubMembershipApi`가 조회와 명령을 함께 소유한다.

## 적용 시점

- **새 도메인 패키지는 처음부터 이 구조로 생성한다.**
- 재사용 코어에 속하는 새 코드는 `코어 모듈 구조`를 처음부터 적용한다.
- 기존 평면 패키지였던 `club`, `comment`, `book`, `member`는 2026-08-06 별도 정비 작업에서
  이 구조로 재배치했다. 이후 추가된 `preregistration`도 같은 구조를 따른다.
