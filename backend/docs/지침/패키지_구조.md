# 패키지 구조 지침

> 배경: 코드 리뷰 지적 — "성격이 매우 다른 클래스들이 한 패키지 안에 모여 있다. 패키지에 계층을 도입해 정리했으면 좋겠다." (2026-08-05)

## 기본 구조

도메인 우선 분할(`yeobaek.backend.<도메인>`)은 유지하되, 각 도메인 패키지 내부를
계층 하위 패키지로 나눈다.

```
yeobaek.backend.<도메인>
├── controller   웹 어댑터
├── service      응용 서비스
├── repository   저장소
├── domain       도메인 모델
└── dto          요청·응답 객체
```

## 배치 기준

| 하위 패키지 | 배치 대상 | 현재 코드 기준 예 |
|---|---|---|
| `domain` | `@Entity`, 값 객체, 도메인 규칙을 수행하는 순수 객체 | `Club`, `ClubMember`, `JoinCodeGenerator` |
| `repository` | Spring Data 리포지토리 인터페이스, 쿼리 프로젝션 | `ClubRepository`, `ClubMemberCount` |
| `service` | `@Service` 응용 서비스 | `ClubService` |
| `controller` | `@RestController`, 인터셉터·리졸버 등 웹 계층 부속 | `ClubController` |
| `dto` | API 요청·응답 레코드 | `ClubCreateRequest`, `MyClubResponse` |

- 판단이 애매한 클래스는 "이 클래스가 의존하는 방향"으로 정한다. 웹 기술에 의존하면
  `controller`, 영속성 기술에 의존하면 `repository`, 아무 기술에도 의존하지 않으면 `domain`.
- `dto`는 현 규모에서 request/response로 더 세분하지 않는다.
- 도메인이 아닌 공통 패키지(`support`, `auth`)는 현행 유지한다. 내부 클래스 수가 늘어
  성격이 섞이기 시작하면 동일한 원칙으로 계층화를 제안한다.

## 적용 시점

- **새 도메인 패키지는 처음부터 이 구조로 생성한다.**
- 기존 평면 패키지(`club`, `comment`, `book`, `member`)의 재배치는 별도 정비 작업으로
  수행한다 (2026-08-05 개발자 결정: 지침 우선 작성, 리팩터링은 추후).
- 정비 전에 기존 평면 패키지에 새 클래스를 추가해야 한다면, 배치 위치를 임의로 정하지
  말고 해당 패키지 정비를 같은 작업에서 함께 할지 개발자에게 확인한다.
