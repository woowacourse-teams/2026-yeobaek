# 피드백 루프 하네스

구현 결과를 바꾸는 중요한 미정을 개발자와 확인하기 위한 지침이다.
사용자가 이미 결정했거나 구현 방법을 지정한 내용은 다시 승인받지 않는다.

## 확인할 결정

다음 영역에 미정인 선택이 있고 대안에 따라 동작이나 유지보수 비용이 달라지면 확인한다.

- 데이터 모델·스키마·저장 방식·외부 API 계약
- 새 라이브러리·프레임워크·외부 서비스 도입
- 모듈·계층 경계와 추상화
- 캐시·잠금·큐·비동기 처리
- 재시도·폴백·오류 전파
- 기존 컨벤션에서 벗어나는 구현이나 새 제품 정책·경곗값

오타, 명백한 버그, 이름·배치 같은 구현 세부는 요청 범위 안에서 진행한다.
요구사항이 모호하면 먼저 코드와 문서를 조사하고, 남은 미정 중 결과를 가장 크게 바꾸는
질문부터 묻는다. 무관한 작업은 계속 진행한다.

## 질문과 구현

- 갈리는 선택, 필요한 이유, 각 대안의 실제 차이와 영향 범위를 짧게 제시한다.
- 관찰한 사실과 예상·추천을 구분한다. 측정이 필요하면 그 사실을 밝힌다.
- 답변으로 확정된 범위는 구현한다. 같은 결정을 별도 양식으로 다시 승인받지 않는다.
- 확정된 결정과 다르게 구현해야 하면 해당 부분을 확인하고, 무관한 부분은 진행한다.

## 결정의 설명

- 개발자의 선택과 이유는 의미를 보존해 정리한다. 없는 이유를 만들어 개발자에게 귀속하지 않는다.
- 이유가 불명확하면 필요한 부분만 질문한다. 이유가 없다는 이유로 형식적인 기록을 요구하지 않는다.
- PR과 완료 보고는 현재 변경·필요한 이유·검증을 설명한다. 대화 날짜나 선택지 기호를 붙이는
  대신 실제 선택 내용을 쓴다. 출처나 변경 경위를 요청받았을 때 관련 원문을 참조한다.
- 공식 결정 원문을 수정해 달라는 요청에서는 수정안을 보여 주고 확정받는다.
