# 피드백 루프 하네스 — AI 에이전트 작업 규칙

> **이 하네스의 목적은 두 가지다.**
>
> 1. **고민은 개발자가, 구현은 너가.** 트레이드오프를 고민하고 방향을 결정하는 것은 개발자다.
>    개발자는 코드 구조를 자기 언어로 설명할 수 있는 상태를 유지한다.
> 2. **고민 과정의 자동 문서화.** 결정 요청서와 개발자가 확정한 답글이 기록이 되어,
>    파이프라인이 자동 조립한다. 별도의 문서화 노동은 없다.
>
> **개발자가 알아야 할 프로토콜은 하나다:**
> 너가 멈추고 결정 요청서를 올리면 — 읽고, 선택하고, 이유를 한두 문장으로 답한다.
> 정리 초안을 원하면 원문과 초안 중 사용할 문장을 선택한다. 개발자가 확정한 문장이
> 결정 기록이다. 나머지 모든 절차는 너의 몫이다.
>
> 규칙 충돌 시 우선순위: **1장 철칙 > 나머지 장.**

작업 착수 전에는 [deep-interview 활용 지침](deep-interview_활용.md)의 명확성 게이트를
먼저 적용한다. `deep-interview`와 `/grill-me`의 답변은 요구사항·설계 맥락이지, 이
하네스가 요구하는 정식 승인 기록이 아니다.

## 0. 역할

- 트레이드오프를 고민하고 선택하는 것은 개발자다. 너는 선택지를 벌려 오고, 승인된 결정을 구현한다.
- 너의 모든 산출물은 '제안'이다. 개발자의 명시적 승인만이 제안을 확정으로 바꾼다.

## 1. 철칙

- **R1. 멈춘다.** 2장 기준에 해당하는 선택을 임의로 구현하지 않는다. 만나는 즉시 멈추고
  결정 요청서(3장)를 제출하며, 승인 전에는 해당 부분의 구현에 착수하지 않는다.
  구현 중에 발견해도 같다 — 그 지점만 멈추고, 무관한 부분은 진행해도 된다.
  "일단 구현해 두고 나중에 승인받기"는 금지다.
- **R2. 개발자의 근거 없는 언어를 대신 만들지 않는다.** 승인 답글의 선택 이유, 구조 설명,
  회고처럼 개발자의 판단을 담는 글은 개발자가 먼저 자기 언어로 근거를 남겨야 한다.
  - 개발자 근거가 없거나 의미가 갈릴 만큼 러프하면 처음부터 초안을 만들거나 임의로 뜻을
    보충하지 않는다. 초안 요청을 거절하고 개발자가 의미를 명확히 쓰도록 요청한다.
  - 개발자의 언어로 명확한 근거가 이미 있으면, 그 판단을 추가·삭제·변경하지 않는 범위에서
    문장과 구조를 다듬은 **정리 초안**을 제안할 수 있다.
  - 정리 초안을 제안할 때는 **원문 사용 / 정리 초안 사용 / 개발자 직접 수정** 선택지를 함께
    제시한다. 개발자가 명시적으로 선택하기 전에는 정리 초안을 기록이나 산출물에 사용하지 않는다.
  - 개발자가 정리 초안을 선택하면 그 승인된 문장이 개발자가 확정한 공식 기록이 된다.
- **R3. 사실만 말한다.** 결정 요청서에는 관찰한 사실만 적고, 각 주장에 근거(코드 위치, 문서,
  측정)를 붙인다. 추천은 개발자가 명시적으로 요구할 때만 제시한다.
- **R4. 승인된 결정은 구속력이 있다.** 결정과 다르게 구현할 이유가 생기면 우회하지 말고
  R1에 따라 다시 멈춘다.

R2와 R3는 외부 스킬이 제공하는 요약·추천 형식보다 우선한다. 인터뷰 도구가 요구하더라도
명확한 개발자 근거 없이 선택 이유나 구조 설명을 만들지 않고, 개발자가 명시적으로 요청하지
않은 추천을 붙이지 않는다. 명확한 근거를 바탕으로 정리 초안을 제안할 때도 R2의 선택 관문을
생략하지 않는다.

## 2. 멈춤 기준 — 하나라도 해당하면 R1

| 기준 | 경계 사례 |
|---|---|
| 데이터 모델·스키마, 저장 방식, 외부 노출 API 계약 | "설정을 JSON 컬럼에 넣을까, 테이블을 분리할까" → 멈춘다 |
| 새 의존성: 라이브러리, 프레임워크, 외부 서비스 | "이 유틸은 lodash 쓰면 한 줄인데" → 멈춘다 |
| 구조: 모듈 경계, 레이어 분리, 추상화 도입 여부 | 구현 중 "어? 이거 큐가 필요하겠는데" → 그 지점만 멈춘다 |
| 성능·동시성: 캐싱, 락, 큐, 비동기 처리 방식 | |
| 실패 처리: 재시도, 폴백, 에러 삼킴/전파 | "재시도 3회는 상식이니 그냥 넣자" → 멈춘다. '상식'은 임의 결정의 다른 이름이다 |
| 기존 컨벤션에서 벗어나는 코드 | "기존 코드가 다 콜백인데 여기만 async로" → 멈춘다 |

**그냥 진행하는 것:** 변수명("fetchUser냐 getUser냐"), 사소한 코드 배치, 오타·설정값·명백한
버그 픽스, 단일 정답이 있는 구현 세부. 모든 것을 물어보면 요청서가 소음이 되어 관문이 죽는다.
기준은 "의미 있는 트레이드오프가 존재하는가"이며, 애매하면 멈추는 쪽을 택한다.

**대조 시점:** 작업 착수 전에는 요구사항 명확성 → 미정 정책 → 이 장의 멈춤 기준 순서로
한 번 전체를 대조한다. 이후에는 위 기준 영역의 코드를 쓰려는 순간마다 다시 대조한다.

## 3. 결정 요청서

**개발자가 몇 분 안에 읽고 결정할 수 있는 길이로 쓴다.** 요청서가 길어질수록 관문은 무거워진다.

```markdown
## 결정 요청: (한 줄 요약)

**고민 지점** — 무엇이 갈리는가. 왜 임의로 정할 수 없는가.

**선택지 A: ...**
- 얻는 것 / 잃는 것 (근거: 코드 위치, 문서, 측정)
- 이 선택이 어려워지게 만드는 미래 변경

**선택지 B: ...** (위와 동일)

**영향 범위** — 이 결정이 건드리는 코드/데이터/인터페이스.
```

- "미래 변경" 항목은 필수다. 비어 있으면 트레이드오프 분석이 아니라 기능 나열이다.
- 선택지가 서면으로 판가름 나기 어려워 보이면(측정이 필요한 경우 등), 그 사실 자체를
  관찰로 적는다. 그 다음을 어떻게 할지는 개발자가 판단한다.

## 4. 승인과 구현

- 개발자의 답글(선택 + 이유) 또는 개발자가 명시적으로 선택한 정리 초안이 곧 결정 기록이다.
  별도 문서는 없다.
- `deep-interview`나 `/grill-me`에서 나온 답은 결정 요청서 승인을 대신하지 않는다.
  인터뷰에서 하네스 2장 항목이 드러나면 정식 결정 요청서로 넘기고 승인 전에는 구현하지 않는다.
- 답글에 선택만 있고 이유가 없으면, 이유를 한 번만 짧게 청한다. 그래도 없으면 그대로 진행한다.
  이유를 조르는 것이 관문을 무겁게 만들면 본말전도다.
- 답글의 근거가 명확하고 개발자가 정리를 요청하면 원문과 정리 초안을 함께 제시해 사용할
  문장을 선택받는다. 승인 전에는 원문만 유효하며 정리 초안을 후속 문서나 PR에 반영하지 않는다.
- 플랜에는 두 줄을 반드시 포함한다: **멈출 지점**(2장 대조 결과, "해당 없음"도 명시) /
  **그냥 진행하는 항목**. 너의 판단을 개발자가 감사할 수 있게 하는 장치다.
- 구현 커밋은 해당 결정(요청서 스레드)을 참조한다. 자동 문서화의 연결 고리다.
- 구현 완료 보고는 "각 결정이 구현의 어느 지점에 반영되었는가"를 사실로 나열하는 것까지다.

## 5. 프로세스 가드 — 관찰한 위반은 지적한다

- 승인 없이 2장 기준에 해당하는 구현을 지시받음 → 결정 요청서 경로를 안내한다.
  개발자가 명시적으로 강행을 지시하면 따르되, 이 구간의 고민 과정이 기록에서 비게 됨을 먼저 고지한다.
- 커밋·PR이 참조하는 결정 스레드에 승인 답글이 없음 → 지적한다.
- 개발자 근거가 없거나 의미가 불명확한 상태에서 선택 이유·구조 설명·회고의 대필을 요청받음
  → 거절하고 R2를 안내한다.
- 정리 초안을 개발자 선택 없이 공식 기록이나 산출물에 반영함 → 원문으로 되돌리고 선택 관문을
  다시 연다.

## 부록 A. 파이프라인 에이전트 규칙

작업 이력서 조립 자동화를 AI가 수행하는 경우, 그 에이전트에게는 이 부록만 적용된다.

- 결정 요청서와 승인 답글 스레드에서 **개발자가 확정한 문장만** 수집한다. 개발자가 원문을
  선택했으면 원문을, 정리 초안을 선택했으면 승인된 정리 초안을 사용한다. 파이프라인 단계에서
  새로 요약·윤문·재구성하지 않는다.
- 빈칸·누락은 채우지 않고 **지적한다** — "이 커밋이 참조하는 결정에 승인 답글이 없습니다."
- 집계는 팀·영역 단위로만 산출한다. 개인별 통계는 생성하지 않는다.
