# 백엔드 PR 작성 하네스

PR 초안 작성·제출·갱신을 맡은 작업에 적용한다. 대화에서 초안만 제시할 때도 본문 기준을 적용한다.
로컬 수정이나 문서 정리만 요청받은 작업을
자동으로 푸시·PR 제출까지 확대하지 않는다.

## 브랜치와 변경 범위

- 브랜치·base·병합 조건은 [Git Flow 지침](../../../../docs/Git_Flow_지침.md)을 따른다.
- 제출 전에 현재 브랜치, 최신 원격 base와의 관계, 최종 diff를 확인한다.
  일반 작업은 `develop`, `hotfix/*`는 `main`을 base로 삼는다.
- `hotfix/*`에 아직 main에 없는 develop 변경이 섞이지 않았는지 확인한다.
- 보호 브랜치에 직접 커밋·푸시하지 않는다. 기존 작업의 히스토리를 임의로 재작성하지 않는다.
- 사용자의 다른 변경을 섞지 않는다. 범위가 섞였거나 안전하게 분리할 수 없으면 알린다.
- [커밋 전 게이트](../검증/커밋_전_게이트.md)를 통과한 변경만 제출한다.

## 본문

[본문 템플릿](../../템플릿/백엔드_PR_본문.md)을 복사해 임시 파일에서 작성한다.
템플릿은 필요한 섹션을 고르는 틀이며, 모든 항목을 채우는 양식이 아니다.

### 구성 선택

기능·API·저장 구조·정책을 함께 다루면 `변경 → API → 저장 구조 → 정책` 순서로 쓴다.
변경에 해당하지 않는 섹션은 삭제한다. 작은 수정은 `변경`과 필요한 예시만으로 마무리한다.

| 섹션 | 포함할 내용과 적용 조건 |
| --- | --- |
| 변경 | 핵심 변경과 달라지는 동작을 먼저 설명한다. 독립적인 변경이 여러 개면 짧은 목록으로 나눈다. |
| API | API 추가·변경 시 기능·메서드·경로와 연동에 필요한 요청·응답 계약을 설명한다. |
| 저장 구조 | 데이터 관계·저장 방식이 동작 이해에 중요할 때 마이그레이션, 관계, 제약을 설명한다. |
| 정책 | 기본값·대상·처리 조건·영향 범위·실패 처리·보장 범위가 필요할 때 설명한다. 제목은 `설정과 발송 정책`처럼 기능에 맞게 구체화한다. |

### 작성 기준

- 본문은 `~습니다`체로 쓰고, 제목과 짧은 항목명은 명사구를 사용할 수 있다.
- 대화 없이 이해할 수 있게 기능과 동작을 중심으로 쓴다. 파일·클래스·메서드별 수정 목록으로
  대신하지 않는다. 구현 이유는 동작이나 설계 선택을 이해하는 데 필요한 만큼만 쓴다.
- 구현·테스트에서 확인한 사실과 개발자의 판단을 구분한다. 개발자가 말하지 않은 이유를
  개발자의 결정으로 표현하지 않는다.
- API 목록은 `기능 | 메서드·경로` 표로 쓰고 기능명은 명사구로 표현한다. 필수 헤더·쿼리·본문,
  성공·실패 응답 등 필요한 계약은 표 아래 문장·목록·별도 표로 설명한다.
- 응답 코드·필드·출력 값의 차이는 필요한 범위의 AS-IS / TO-BE 예시로 보여준다.
- 저장 구조는 실제 적용한 기술 용어와 대상을 함께 쓴다. 예를 들어 복합 UNIQUE KEY의 대상 컬럼,
  FK의 삭제 동작, 동시 요청 충돌 시 처리처럼 동작 이해에 필요한 제약을 명시한다.
  관계를 글만으로 이해하기 어려우면 필요한 범위의 스키마 그림을 추가한다.
- 서로 독립적인 정책이 여러 개면 `항목 | 정책` 표로 쓴다. 한두 조건이면 문장이나 목록으로 쓴다.
  조건·이유·적용 범위·불확실성을 생략하거나 구현보다 강한 보장을 표현하지 않는다.
- 사용자 관점의 설명은 제품 용어를 일관되게 쓴다. 기기를 가리킬 때는 `기기`,
  모임의 알림 설정은 `모임별 알림 설정`으로 표현하고, 기술적인 구분이 필요할 때 내부 이름을 쓴다.
- 대안·결정 출처는 선택을 이해하는 데 필요할 때만 추가한다. 긴 처리 흐름·클래스 책임은
  실제로 존재하는 관련 문서에 연결하고, 링크 옆에 확인할 내용을 쓴다.
- 같은 내용을 여러 섹션에서 반복하거나 날짜·승인 이력·`해당 없음`으로 본문을 늘리지 않는다.
- 검증·테스트·CI 결과, 실행 명령, 미검증 안내, 검증 체크리스트는 본문에 추가하지 않는다.
  필요한 검증은 수행하되 결과는 사용자에게 본문 밖에서 보고한다.

## 업로드 전 점검

초안을 보여주기 전과 승인된 본문을 게시하기 직전에 다음을 확인한다.

- 최종 diff와 본문의 동작·API 계약·저장 제약·정책이 일치한다.
- 변경에 필요한 섹션만 남기고, API·정책 표와 예시는 위 기준에 맞게 골랐다.
- 용어가 일관되고 한국어가 자연스럽다. 조건과 이유가 필요한 설명을 짧은 명사구로 줄이지 않았다.
- 안내 주석·선택지 기호·빈 섹션·중복 설명·검증 항목을 제거했다. 템플릿 원본은 덮어쓰지 않았다.

제출할 변경은 셀프 리뷰하고, 명확히 불필요한 코드·구조·테스트가 남아 있는지 확인한다.
적용되는 개인 PR 작성·업로드 지침도 함께 따르고, 필요한 승인 전에 푸시하거나 PR을 게시하지 않는다.
사용자에게 제목·본문 전체와 저장소·head·base·반영 범위를 보여주되, 업로드 범위와 검증 결과는
PR 본문 밖에 안내한다. 승인 후 본문이나 범위가 달라지면 변경된 내용을 보여주고 다시 승인받는다.

## 생성·갱신

GitHub CLI 또는 같은 기능의 인증된 API·연결 도구를 사용한다.

1. 현재 인증 사용자와 PR author를 직접 확인한다. 백엔드 개발자는 `alstj2384`,
   `Yeji-Kim-Erica`, `kjoon418`이다. 다른 계정이면 대신 제출자로 추정하지 않고 확인한다.
2. 업로드 전 점검과 필요한 승인을 마친 뒤 제출할 작업 브랜치를 푸시하고, 그 head의 열린 PR을 조회한다.
3. PR이 없으면 base·head·제목·본문을 명시해 생성한다. 하나면 실제 author를 기준으로 갱신한다.
   둘 이상이면 대상을 확인한다.
4. author를 제외한 백엔드 개발자 두 명을 reviewer로 지정한다.
5. 제목은 Conventional Commits 형식으로 쓴다. 종류는 제목으로 표현하고 label은 추가하지 않는다.
   기존 PR의 label도 비운다.
6. 원격 head·base·제목·본문·reviewer·label을 다시 조회한다. 승인된 제목·본문과 일치하고
   선택한 본문 구조가 유지됐는지 확인한 뒤 PR URL을 보고한다.

CLI를 사용하면 본문은 임시 파일에 실제 줄바꿈으로 저장해 `--body-file`로 전달한다.
인증·권한 오류나 푸시 실패는 그대로 보고하고, 실패를 성공으로 표현하지 않는다.

## 인라인 설명

본문과 diff만으로 파악하기 어려운 선택이 있을 때만 대표 변경 줄에 짧게 설명한다.
선택을 가른 문제·제약과 이유부터 쓰고, 실제 검토한 대안이 있으면 선택을 가른 차이만 비교한다.
관련 결정을 연결할 때는 실제 PR 본문 제목으로 이동하는 링크를 쓴다.
같은 내용을 여러 줄에 반복하거나 각 구현 항목에 코멘트를 의무적으로 만들지 않는다.

기존 자동 코멘트를 갱신할 때는 다음 규칙을 지킨다.

- `<!-- yeobaek-rationale:{commentKey} -->`가 있는 코멘트만 자동 관리 대상으로 삼는다.
  marker가 없는 코멘트와 다른 사용자의 코멘트는 수정·삭제하지 않는다.
- 게시 직전에 원격 head SHA와 diff를 확인한다. 새 코멘트는 현재 diff의 정확한 path·line·side를 사용한다.
- 같은 marker·위치·본문이 있으면 재사용한다. outdated 코멘트는 이력으로 보존한다.
- 응답을 확인하지 못했으면 다시 조회하고, 이미 게시된 코멘트를 중복 전송하지 않는다.
- 위치를 옮길 때는 대체 코멘트의 존재와 동일 head를 확인한 뒤 기존 코멘트를 정리한다.
- 다른 사용자의 현재 자동 코멘트와 계획이 충돌하면 중단하고 확인한다.
