# 병렬 작업 조율 지침 — 멀티 에이전트(팀) 작업 시

> 배경: 2026-08-06 팀 리팩터링 중 조율 사고. 후속 태스크의 워커가 선행 태스크 완료 전에
> 착수하면서 (1) 같은 작업 디렉터리에서 Gradle 데몬·`build/` 출력·Testcontainers가 충돌해
> 양쪽 빌드가 반복 실패했고, (2) git 인덱스 경합으로 한 워커가 스테이징해 둔 파일이 다른
> 워커의 커밋에 섞여 들어가 히스토리 재구성이 필요했다. 이 지침은 그 재발을 막는다.

## 대원칙

**공유 작업 디렉터리에서는 한 시점에 한 워커만 빌드와 git 조작을 수행한다.**
빌드 산출물(`build/`), Gradle 데몬, Testcontainers, git 인덱스는 전부 디렉터리 단위의
공유 상태다. 태스크가 논리적으로 독립이어도 이 공유 상태 때문에 물리적으로는 충돌한다.
Gradle wrapper 잠금이 같은 worktree의 빌드를 기술적으로 직렬화하지만, git 인덱스 조작은
보호하지 않는다.

## 리드(오케스트레이터) 규칙

1. **블록된 태스크는 미리 배정하지 않는다.** 태스크를 워커에게 배정(owner 설정)하는 행위
   자체가 착수 신호가 될 수 있다. 의존관계(blockedBy)가 있는 태스크는 선행 태스크의 완료를
   확인한 뒤에 배정하거나, 배정과 별개로 **리드의 명시적 시작 통지**를 착수 조건으로 건다.
2. **순차 파이프라인이면 워커도 순차 투입한다.** 다음 단계 워커를 미리 살려 두지 않는다.
3. **동시 수정이 꼭 필요하면 git worktree로 격리한다.** 워커별 worktree + 브랜치를 만들어
   빌드·커밋을 분리하고, 병합은 리드가 순차로 수행한다. 서로 다른 worktree의 Gradle 실행은
   각자의 잠금을 사용하므로 병렬 실행할 수 있다. 격리 비용이 아까우면 병렬을 포기한다.
4. git 인덱스 경합 사고 발생 시 전 워커에게 정지를 지시하고, 히스토리 수습은
   리드가 단독으로 수행한다. 워커가 각자 수습하게 두지 않는다.

## 워커 규칙

1. **blockedBy가 남아 있는 태스크는 착수 금지.** 배정되어 있어도, TaskList에서 블록이
   풀린 것처럼 보여도, 리드의 시작 통지가 착수 조건이라면 통지를 기다린다.
2. **git add는 명시적 경로만 넘긴다.** `git add -A`·`git add .`·`git commit -a`처럼
   스테이징 범위가 암묵적인 명령은 공유 디렉터리에서 금지한다.
3. **커밋 직전 `git diff --cached --stat`으로 스테이징 내용을 확인한다.** 자신이 만들지
   않은 파일이 스테이징에 섞여 있으면 커밋하지 말고 리드에게 보고한다.
4. **Gradle 잠금 충돌은 자동 처리한다.** `[YEOBAEK_GRADLE_LOCKED]`를 빌드 실패로 오판하지
   않고 [피드백 루프 하네스의 Gradle 동시 실행 충돌 처리](피드백_루프_하네스.md#6-gradle-동시-실행-충돌-처리)에
   따라 owner 종료를 기다린 뒤 동일 명령을 자동 재실행한다. `build/`, Gradle 데몬, owner 프로세스를
   임의로 정리하거나 강제 종료하지 않는다.
5. **그 밖에 단독 작업 전제가 깨진 정황을 발견하면 즉시 멈춘다.** 낯선 컨테이너, 남의
   워킹트리 변경, git 인덱스 경합을 발견하면 임의로 정리하거나 되돌리지 말고 리드에게 보고 후
   지시를 기다린다.
