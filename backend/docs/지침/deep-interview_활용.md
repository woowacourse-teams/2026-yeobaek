# deep-interview 활용 지침

`deep-interview`는 모호한 요청을 곧바로 계획하거나 구현하지 않고, 개발자의 의도와 AI의
동작을 맞출 수 있는 실행 가능한 요구사항으로 구체화하는 작업 착수 전 명확성 게이트다.
프로젝트에서 사용하는 원문은 [개발동생 deep-interview 스냅샷](../참고/deep-interview/SKILL.md)에
보존하고, 이 문서가 프로젝트 오버라이드를 포함한 운영 규범이다.

## 적용 조건

목표, 범위와 제외 범위, 제약, 완료 기준, 기존 맥락과 영향 범위 중 구현 결과를 바꿀 중요한
미정이 하나라도 있으면 계획이나 구현 전에 시작한다. 예를 들어 “회원가입 좀 개선해줘”처럼
개선 대상과 성공 기준에 따라 결과가 여러 갈래인 요청은 인터뷰 대상이다.

다음 요청은 질문의 가치가 낮으므로 생략한다.

- 단순 오타와 작은 설정 변경
- 원인과 기대 결과가 분명한 명백한 버그 수정
- 지침·명세·코드에 답이 있고 단일 정답으로 구현할 수 있는 작업

## 질문 전 조사

먼저 피드백 루프 하네스, 관련 명세와 지침, 코드를 읽는다. 저장소에서 답할 수 있는 사실은
개발자에게 묻지 않고 직접 확인하며, 질문의 `현재 이해`에 근거 경로와 함께 반영한다.
개발자에게는 사람의 판단이 필요한 불확실성만 묻는다.

## 질문 축과 진행 방식

아래 순서로 살피되, 매 라운드에는 현재 구현 결과에 가장 큰 영향을 주는 불확실성 하나만
고른다.

1. 목표
2. 범위와 제외 범위
3. 제약
4. 완료 기준
5. 기존 맥락과 영향 범위

질문은 한 번에 하나만 하며 다음 형식을 사용한다.

```markdown
현재 이해: {확인된 요구사항 사실과 저장소 근거를 간결하게 요약}
막힌 결정: {지금 풀어야 하는 가장 중요한 불확실성}
질문: {한 가지 질문}
선택지: {필요할 때만 2~3개. 마지막 항목은 `- (직접 입력)`}
```

선택지는 대비되는 예시가 개발자의 판단 기준을 드러내는 데 도움이 될 때만 붙인다.
질문과 선택지는 중립적으로 작성하며, 개발자가 명시적으로 추천을 요구한 경우에만 근거와
함께 추천한다. 답변에서 확인된 요구사항 사실은 다음 라운드의 `현재 이해`에 반영한다.

## 하네스 오버라이드

[피드백 루프 하네스](피드백_루프_하네스.md)의 R1~R4가 외부 스킬 원문보다 우선한다.

- `현재 이해`와 종료 결과에는 목표, 범위, 제약, 완료 기준처럼 합의된 요구사항 사실만
  정리한다.
- 개발자의 선택 이유, 구조 설명, 회고는 AI가 초안·요약·윤문하지 않는다. 기록할 필요가
  있으면 `[개발자 원문]`으로 원문만 인용하거나 `이유 미기재`로 남긴다.
- 인터뷰 답변은 요구사항 맥락일 뿐 정책 또는 R1 결정의 정식 승인 기록이 아니다.
- 아직 승인되지 않은 인터뷰 맥락과 새 사실이 충돌하면 명확화 단계로 돌아가거나 공식
  관문으로 넘긴다. 정책 질의서나 결정 요청서에서 승인된 내용과 충돌할 때만 R4에 따라
  멈추고 재승인을 받는다.

## 종료 조건

다음 항목이 모두 정리된 경우에만 인터뷰를 끝낸다.

- 달성하려는 목표
- 포함 범위와 제외 범위
- 지켜야 할 제약
- 완료 판단 기준
- 기존 맥락과 영향 범위
- 남은 열린 질문의 배정 상태

남은 질문은 반드시 `범위 제외`, `연기`, `정책 관문 대기`, `결정 관문 대기` 중 하나로
분류한다. 현재 구현에 영향을 주는 미분류 질문이 하나라도 있으면 종료하지 않는다.

마지막에는 전체 대화록이 아니라 다음 형식의 `요구사항 명확화 결과`만 전달한다.

```markdown
## 요구사항 명확화 결과

- 확인된 요구사항 사실:
- 범위 제외:
- 연기:
- 저장소 근거:
- 정책 관문 대기:
- 결정 관문 대기:
- 미분류 열린 질문: 없음
```

## 다음 단계와 전달

- 개발자가 자기 언어로 2~3문단의 설계 방향을 설명할 수 있으면 팀 논의와
  [`/grill-me`](그릴_활용.md)로 설계의 구멍을 압박한다. 이미 확인한 요구사항은 다시
  묻지 않는다.
- 글자 수, 형식, 중복, 공백 처리 같은 미시 정책은 존재와 영향만 식별하고
  `정책 관문 대기`로 [정책 질의서](정책_구체화.md)에 넘긴다.
- 스키마, API 계약, 의존성, 구조, 동시성, 실패 처리 등 하네스 2장 항목은
  `결정 관문 대기`로 정식 결정 요청서에 넘긴다.
- 개발자가 인터뷰 중 정책값이나 R1 선택을 자발적으로 말했다면 `[개발자 원문]`으로 해당
  관문 초안에 그대로 옮긴다. 정식 요청에서는 실질 내용을 반복 질문하지 않고 승인 또는
  정정만 받는다.

같은 세션에서는 `요구사항 명확화 결과`를 다음 단계의 입력으로 그대로 사용한다. 세션이
바뀌거나 병렬 에이전트로 넘길 때는 `.omx/context/requirements-{slug}-{timestamp}.md`에
같은 내용을 저장한다. 전달물은 승인 기록이나 공식 명세가 아니며, 정책이나 결정이 공식
관문에서 확정되면 상태만 `정책 확정` 또는 `R1 결정 승인`으로 바꾸고 공식 기록을 참조한다.
단계 상태는 `명확화됨`, `정책 관문 대기`, `결정 관문 대기`, `정책 확정`,
`R1 결정 승인`으로 구분하며 뒤의 두 상태만 구현을 구속한다.

## 대표 동작

- **통과:** 목표와 성공 기준이 여러 갈래인 새 기능 요청 → 가장 큰 불확실성 하나를 질문한다.
- **생략:** “오탈자 한 글자를 고쳐줘” → 인터뷰 없이 진행한다.
- **직접 조사:** 기존 API의 응답 필드가 무엇인지 미정처럼 보임 → 코드와 API 문서를 확인한다.
- **정책 관문:** 닉네임 글자 수가 미정 → 인터뷰에서 값을 정하지 않고 정책 질의서로 넘긴다.
- **결정 관문:** 저장 방식을 JSON 컬럼과 별도 테이블 중 골라야 함 → 결정 요청서 승인 전
  관련 구현을 시작하지 않는다.
- **종료 차단:** 구현에 영향을 주는 질문이 분류되지 않은 채 남음 → 인터뷰를 계속한다.
