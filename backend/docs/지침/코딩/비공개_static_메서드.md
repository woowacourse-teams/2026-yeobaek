# 비공개 `static` 메서드 사용 지침

## 적용 범위

운영 코드와 테스트 코드에서 Java `private` 메서드를 새로 작성하거나 수정할 때 적용한다.
상수와 공개 API의 `static` 여부는 이 지침의 범위가 아니다.

## 기본 원칙

- `private` 메서드는 기본적으로 인스턴스 메서드로 선언한다.
- 인스턴스 상태를 사용하지 않는다는 이유만으로 `static`을 붙이지 않는다.
- `static` 없이 구현할 수 있는 비공개 메서드에는 `static`을 붙이지 않는다.

`static`은 일반적으로 유틸리티 기능이나 정적 호출 문맥을 먼저 떠올리게 한다. 상태에 의존하지 않는다는
사실을 표현하기 위해 모든 비공개 헬퍼에 `static`을 붙이면, 개발자가 선언의 별도 이유를 찾게 되고 코드
작성 시 고려할 기준도 늘어난다. 따라서 익숙한 인스턴스 메서드를 기본으로 두고 정적으로 선언해야 하는
이유가 있을 때만 `static`을 사용한다.

## `static`을 유지하는 경우

다음처럼 정적 호출 문맥이나 프레임워크 계약 때문에 필요한 경우에는 `private static`을 유지한다.

- 정적 팩터리 메서드가 직접 호출하는 비공개 헬퍼
- JUnit 기본 테스트 인스턴스 수명주기에서 사용하는 `@MethodSource` 제공자
- 의도적으로 정적 유틸리티로 설계된 클래스의 비공개 헬퍼

단순히 현재 구현이 인스턴스 필드를 읽지 않는다는 사실은 위 예외에 해당하지 않는다.

## 수정 시 확인

1. 새 비공개 메서드가 정적 호출 문맥에서 호출되는지 확인한다.
2. 정적 호출이 필수가 아니라면 인스턴스 메서드로 작성한다.
3. 기존 `private static` 메서드를 수정할 때도 같은 기준으로 `static` 필요 여부를 다시 확인한다.
4. `static`을 제거하거나 유지하기 위해 메서드 본문, 호출 의미 또는 클래스 구조를 불필요하게 변경하지 않는다.

## 결정 기록

- **결정:** 정적 호출 문맥이 필요하지 않은 비공개 메서드에는 `static`을 붙이지 않는다.
- **근거:** 불필요한 `static`은 일반적인 유틸리티 기능이라는 인상을 먼저 주고, 개발자가 별도 사용 이유를
  찾게 하며, 코드 작성 시 고려할 기준을 늘린다는 2026-09-16 개발자 결정이다.
