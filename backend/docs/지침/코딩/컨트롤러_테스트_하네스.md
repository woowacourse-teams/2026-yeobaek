# 컨트롤러 테스트 하네스

이 문서는 JSON API를 제공하는 `@RestController`의 테스트 범위와 작성 기준을 정의한다.
컨트롤러 테스트는 HTTP 요청을 웹 계층 입력으로 변환하고, 서비스를 정확히 호출하며,
서비스 결과를 API 계약에 맞는 HTTP 응답으로 변환하는지를 검증한다.

클라이언트 계약의 기준은 [API 명세](../../../../docs/API.md)다. 런타임 OpenAPI 문서와 API 명세가
다르면 계약 변경 절차를 먼저 수행하고, 합의된 계약을 기준으로 테스트한다.

## 1. 목적과 적용 범위

이 하네스는 다음 테스트에 적용한다.

- `@RestController`가 제공하는 JSON API
- `@WebMvcTest`, `MockMvc`, `@MockitoBean`을 사용하는 Spring MVC 슬라이스 테스트
- 경로 변수, 쿼리 파라미터, 헤더, JSON 본문의 바인딩
- Spring MVC 또는 Bean Validation으로 웹 계층에 선언한 API 제약
- 컨트롤러와 서비스 사이의 호출 및 인자 전달
- 컨트롤러가 선택하는 상태 코드, 응답 본문, 빈 응답 분기

다음 항목은 이 하네스의 적용 대상이 아니다.

- HTML을 반환하는 `@Controller`
- 잘못된 경로나 지원하지 않는 HTTP 메서드를 거부하는 Spring 자체 동작
- 형태는 올바르지만 비즈니스 규칙에 어긋난 값의 검증
- 인터셉터, argument resolver, 전역 예외 처리기의 공통 동작을 엔드포인트마다 반복하는 테스트
- 기존 컨트롤러 테스트를 이 하네스에 맞게 일괄 개정하는 작업

## 2. 컨트롤러 테스트의 책임과 제외 범위

컨트롤러 테스트는 다음 책임을 검증한다.

1. 의도한 HTTP 메서드와 경로가 컨트롤러 메서드에 연결된다.
2. 요청의 경로 변수, 쿼리 파라미터, 헤더, JSON 본문이 의도한 값으로 바인딩된다.
3. 웹 계층에 선언한 필수성·형식 제약을 위반하면 요청을 거부하고 서비스를 호출하지 않는다.
4. 정상 요청이면 서비스를 정확히 한 번, 정확한 인자로 호출한다.
5. 서비스 반환값을 상태 코드, 헤더, JSON 본문으로 변환한다.
6. 컨트롤러가 직접 선택하는 응답 분기를 각각 검증한다.
7. 컨트롤러 클래스마다 대표 사례 하나로 서비스 예외의 동일 인스턴스가 전파되는지 검증한다.

컨트롤러 테스트는 다음 책임을 검증하지 않는다.

- 서비스가 어떤 비즈니스 규칙을 검사하고 어떤 종류의 예외를 선택하는지
- 예외 메시지의 내용이 비즈니스 상황에 적절한지
- 서비스 예외를 HTTP 상태와 오류 본문으로 변환하는 규칙
- 회원 인증 인터셉터와 argument resolver의 모든 성공·실패 조합
- Spring MVC가 잘못된 경로나 HTTP 메서드를 거부하는지

서비스 예외의 의미와 메시지는 예외를 만드는 서비스 또는 도메인 테스트에서 검증한다.
HTTP 오류 변환은 `GlobalExceptionHandlerTest`에서 검증한다.

## 3. 테스트 환경 구성

프로젝트의 컨트롤러 슬라이스 테스트는 다음 구성을 사용한다.

- 테스트 대상 컨트롤러를 `@WebMvcTest(대상.class)`로 한정한다.
- 공통 `ControllerTest`를 상속해 `MockMvc`와 `MemberRepository` mock을 사용한다.
- 컨트롤러의 서비스 협력 객체를 `@MockitoBean`으로 대체한다.
- 회원 인증이 필요한 정상 요청에서는 `givenValidMember(memberId)`로 인터셉터의 선행 조건을 만든다.
- 요청은 컨트롤러 메서드를 직접 호출하지 않고 `MockMvc`로 보낸다.

```java
@WebMvcTest(ClubController.class)
class ClubControllerTest extends ControllerTest {

    @MockitoBean
    private ClubService clubService;
}
```

`@WebMvcTest`는 MVC 인프라와 관련 웹 컴포넌트를 구성하고 `MockMvc`를 자동 설정한다. 따라서
이 테스트는 단순 POJO 단위 테스트가 아니라 `DispatcherServlet`을 통과하는 웹 슬라이스
테스트다.

## 4. 필수 테스트 시나리오

컨트롤러 테스트 클래스에는 아래 시나리오를 적용한다.

| 시나리오 | 적용 단위 | 필수 검증 |
|---|---|---|
| 정상 요청 | 모든 엔드포인트 | 올바른 메서드·경로, 요청 값, 서비스 1회 호출과 정확한 인자, 상태, 응답 계약 |
| API 제약 위반 | 해당 제약을 선언한 엔드포인트 | 거부 원인, 서비스 미호출 |
| 컨트롤러 응답 분기 | 분기가 있는 엔드포인트 | 각 분기의 상태, 본문, 서비스 호출 |
| 서비스 예외 전파 | 컨트롤러 클래스마다 대표 사례 하나 | 서비스 1회 호출과 정확한 인자, 동일 예외 인스턴스 |

한 엔드포인트의 정상 흐름에 선택 파라미터 유무처럼 서로 다른 바인딩이 있으면 각 바인딩이
서비스에 전달되는 값을 구분해 검증한다. 반대로 같은 공통 컴포넌트가 처리하는 실패를 모든
엔드포인트에 반복하지 않는다.

## 5. 요청 검증 규칙

### 5.1 올바른 메서드와 경로

모든 엔드포인트는 의도한 HTTP 메서드와 경로로 성공하는 긍정 테스트를 작성한다. 이 테스트가
요청 매핑을 검증하므로 잘못된 경로나 지원하지 않는 메서드의 부정 테스트는 작성하지 않는다.

### 5.2 요청 값의 바인딩

요청에 포함된 값이 서비스 호출 인자에 그대로 반영되는지 검증한다.

- 경로 변수: 테스트 데이터와 서비스 인자의 식별자가 같은지 검증한다.
- 쿼리 파라미터: 필수·선택 여부와 전달값을 검증한다.
- 헤더: 컨트롤러가 사용하는 값은 서비스 인자로 전달되는지 검증한다.
- JSON 본문: 필드가 컨트롤러의 의도대로 서비스 인자로 풀리거나 DTO로 전달되는지 검증한다.

단순히 `anyLong()`, `anyString()`으로 스텁이 소비되는지만 확인하지 않는다. 정상 흐름의 마지막에
`verify(service, times(1))`로 실제 호출 횟수와 값을 검증한다. 값 객체나 DTO 전체를 전달하면
동등성 비교가 명확할 때는 `eq(...)`를 사용하고, 필요한 경우 `ArgumentCaptor`로 필드를 확인한다.

### 5.3 웹 계층에 선언한 제약

필수 입력 누락, 타입 불일치, JSON 역직렬화 실패, Bean Validation 위반처럼 컨트롤러 실행 전에
Spring MVC가 거부하는 요청은 서비스 미호출을 검증한다. 엔드포인트 고유 제약의 실패 원인은
확인하되 공통 오류 본문의 직렬화는 반복 검증하지 않는다.

Bean Validation 규칙은 다음 조건을 모두 만족할 때만 컨트롤러 테스트 대상이다.

- 운영 코드에 Bean Validation 의존성이 승인되어 추가되어 있다.
- 요청 DTO 필드나 컨트롤러 파라미터에 실제 제약 어노테이션이 선언되어 있다.
- DTO 검증이 필요하면 컨트롤러 인자에 `@Valid`가 선언되어 있다.

`@Valid` 자체는 필수성이나 길이 제약을 만들지 않는다. `@NotNull`, `@NotBlank`, `@Size` 같은
실제 제약 선언이 있어야 한다. 현재 프로젝트에는 Bean Validation 의존성과 제약 어노테이션이
없으므로, 이 문서는 새 의존성을 전제하거나 검증 코드를 요구하지 않는다. API 명세의 제약이
운영 코드에 아직 선언되지 않았다면 서비스 예외를 대신 스텁해 웹 계층 검증처럼 작성하지 않는다.

형태는 올바르지만 비즈니스적으로 부적절한 값은 서비스 또는 도메인 테스트에서 검증한다.

## 6. 서비스 협력과 예외 전파 검증

### 6.1 정상 흐름

정상 요청은 서비스가 정확히 한 번 호출되었고 모든 인자가 요청과 일치하는지 검증한다.
응답 검증만으로는 컨트롤러가 올바른 협력 호출을 했는지 증명할 수 없다.

```java
verify(clubService, times(1)).create(1L, "교환독서 1기", 1L);
```

`times(1)`은 호출 횟수를 드러내기 위해 명시한다. 모든 테스트에 `verifyNoMoreInteractions()`를
일괄 적용하지 않는다. 테스트와 구현 세부의 결합을 늘리므로 추가 호출이 없어야 하는 것 자체가
명시적 계약일 때만 사용한다.

### 6.2 요청 거부

Spring MVC 바인딩 또는 웹 계층 제약이 컨트롤러 실행 전에 요청을 거부하면 해당 컨트롤러의
서비스가 전혀 호출되지 않아야 한다.

```java
verifyNoInteractions(passageService);
```

### 6.3 서비스 예외 전파

컨트롤러는 서비스 예외의 종류나 내용을 해석하지 않는다. 컨트롤러 클래스마다 대표 서비스
예외 하나를 선택해 다음 두 가지만 검증한다.

- 서비스를 정확히 한 번, 정확한 인자로 호출했다.
- `MvcResult.getResolvedException()`이 서비스가 던진 예외와 동일한 인스턴스다.

HTTP 상태, 오류 `code`, 오류 `message`는 이 테스트에서 검증하지 않는다. 같은 예외 종류별 또는
컨트롤러 메서드별로 전파 테스트를 반복하지 않는다.

## 7. 응답 검증 규칙

정상 JSON 응답은 다음 항목을 검증한다.

- 상태 코드
- JSON 응답이면 호환되는 `Content-Type`
- 계약이 정의한 응답 헤더가 있으면 해당 헤더
- API 명세에 있는 모든 응답 필드

성공 JSON 전체를 문자열 하나로 비교하지 않는다. `jsonPath`로 계약 필드를 개별 검증한다.
이 방식은 어떤 계약 필드가 깨졌는지 바로 보여 주며 JSON 객체의 필드 순서에 결합되지 않는다.

응답 구조별 규칙은 다음과 같다.

- 중첩 객체: 상위 객체의 존재와 모든 하위 필드를 검증한다.
- 컬렉션: 배열 여부, fixture 기준 크기, 각 원소의 모든 필드를 검증한다.
- 문자열 배열: 배열 여부, 크기, 각 원소 값을 검증한다.
- nullable 필드: fixture가 `null`인 사례를 포함하고 JSON `null`을 명시적으로 검증한다.
- 빈 컬렉션: 빈 배열인지 명시적으로 검증한다.
- `204 No Content`: 상태와 빈 본문을 검증하며 JSON `Content-Type`을 요구하지 않는다.

오류 응답의 상태·`code`·`message`는 `GlobalExceptionHandlerTest`에서 검증한다. API 명세상
클라이언트 분기 계약은 `code`지만, 핸들러가 예외 메시지를 바꾸지 않고 전달하는지도 정확한
문자열로 검증한다. 메시지 내용의 비즈니스적 적절성은 예외를 생성하는 계층의 테스트 책임이다.

## 8. 공통 웹 컴포넌트 테스트와의 경계

공통 동작은 그 기능을 구현한 객체의 테스트에서 한 번 검증한다.

| 책임 | 검증할 테스트 |
|---|---|
| 올바른 매핑, 요청 바인딩, 서비스 호출, 정상 응답 | 각 컨트롤러 테스트 |
| 엔드포인트 고유 MVC·Bean Validation 제약과 서비스 미호출 | 해당 컨트롤러 테스트 |
| `X-Member-Id` 누락·형식·회원 존재 확인 | `MemberAuthInterceptorTest` |
| `@AuthMember` 인자 해석 | `AuthMemberArgumentResolverTest` |
| 공통 MVC 예외와 서비스 예외의 HTTP 상태·오류 본문 변환 | `GlobalExceptionHandlerTest` |
| 비즈니스 입력 검증과 예외 메시지 의미 | 서비스 또는 도메인 테스트 |

컨트롤러 정상 테스트가 인증 인터셉터를 통과하도록 `givenValidMember(...)`를 사용하는 것은
환경 구성이다. 이때 인증 정책의 모든 분기를 다시 검증하지 않는다.

## 9. 예제

다음 코드는 현재 프로젝트의 `ControllerTest`, DTO, 컨트롤러 메서드 시그니처를 기준으로 한
테스트 메서드 예제다. 예제 클래스에는 대상 서비스의 `@MockitoBean`이 선언되어 있다고
가정한다.

### 9.1 모임 생성: 요청, 서비스 호출, 전체 성공 계약

`ClubController#create`는 `POST /api/clubs` 요청의 헤더와 JSON 필드를 서비스 인자로 전달하고
`201`과 중첩 객체를 반환한다.

```java
@Test
@DisplayName("모임 생성 요청을 서비스에 전달하고 전체 응답 계약을 반환한다")
void createClub() throws Exception {
    givenValidMember(1L);
    var response = new ClubCreateResponse(
            1L,
            "교환독서 1기",
            "A3F9KQ",
            new ClubBookResponse(1L, "운수 좋은 날", List.of("현진건"), 312));
    given(clubService.create(1L, "교환독서 1기", 1L)).willReturn(response);

    mockMvc.perform(post("/api/clubs")
                    .header("X-Member-Id", "1")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("""
                            {"name":"교환독서 1기","bookId":1}
                            """))
            .andExpect(status().isCreated())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.clubId").value(1))
            .andExpect(jsonPath("$.name").value("교환독서 1기"))
            .andExpect(jsonPath("$.joinCode").value("A3F9KQ"))
            .andExpect(jsonPath("$.book").isMap())
            .andExpect(jsonPath("$.book.bookId").value(1))
            .andExpect(jsonPath("$.book.title").value("운수 좋은 날"))
            .andExpect(jsonPath("$.book.authors").isArray())
            .andExpect(jsonPath("$.book.authors.length()").value(1))
            .andExpect(jsonPath("$.book.authors[0]").value("현진건"))
            .andExpect(jsonPath("$.book.passageCount").value(312));

    verify(clubService, times(1)).create(1L, "교환독서 1기", 1L);
}
```

### 9.2 필수 파라미터 누락: 거부 원인과 서비스 미호출

`PassageController#findPassages`의 필수 `to` 파라미터가 없으면 컨트롤러 메서드가 실행되기
전에 Spring MVC가 요청을 거부한다. 이 테스트는 엔드포인트 고유 사실인 누락 파라미터 이름과
서비스 미호출만 검증한다.

```java
@Test
@DisplayName("to 파라미터가 없으면 서비스를 호출하지 않는다")
void missingToParameter() throws Exception {
    givenValidMember(1L);

    mockMvc.perform(get("/api/clubs/{clubId}/passages", 1L)
                    .header("X-Member-Id", "1")
                    .param("from", "1"))
            .andExpect(result -> {
                var exception = assertInstanceOf(
                        MissingServletRequestParameterException.class,
                        result.getResolvedException());
                assertEquals("to", exception.getParameterName());
            });

    verifyNoInteractions(passageService);
}
```

`400`, `INVALID_REQUEST`, 공통 오류 메시지는 `GlobalExceptionHandlerTest`에서 검증한다.

`BookControllerTest`에서 대표 예외 하나만 선택한다. HTTP 오류 응답으로 변환되는 결과는

### 9.4 마지막 읽기: 컨트롤러 소유 응답 분기

`ProgressController#findLastReading`은 서비스의 `Optional` 결과에 따라 `200`과 `204`를 직접
선택하므로 두 분기를 모두 검증한다.

```java
@Test
@DisplayName("마지막 읽기 기록이 있으면 전체 응답 계약을 반환한다")
void findLastReading() throws Exception {
    givenValidMember(1L);
    var lastReadAt = LocalDateTime.of(2026, 8, 5, 14, 30);
    var response = new LastReadingResponse(
            1L,
            "교환독서 1기",
            new ClubBookResponse(1L, "운수 좋은 날", List.of("현진건"), 312),
            42,
            13,
            lastReadAt);
    given(progressService.findLastReading(1L)).willReturn(Optional.of(response));

    mockMvc.perform(get("/api/members/me/last-reading")
                    .header("X-Member-Id", "1"))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.clubId").value(1))
            .andExpect(jsonPath("$.clubName").value("교환독서 1기"))
            .andExpect(jsonPath("$.book").isMap())
            .andExpect(jsonPath("$.book.bookId").value(1))
            .andExpect(jsonPath("$.book.title").value("운수 좋은 날"))
            .andExpect(jsonPath("$.book.authors").isArray())
            .andExpect(jsonPath("$.book.authors.length()").value(1))
            .andExpect(jsonPath("$.book.authors[0]").value("현진건"))
            .andExpect(jsonPath("$.book.passageCount").value(312))
            .andExpect(jsonPath("$.lastReadPassageSequence").value(42))
            .andExpect(jsonPath("$.progressRate").value(13))
            .andExpect(jsonPath("$.lastReadAt").value("2026-08-05T14:30:00"));

    verify(progressService, times(1)).findLastReading(1L);
}

@Test
@DisplayName("마지막 읽기 기록이 없으면 빈 204 응답을 반환한다")
```

### 9.5 전역 예외 변환: 상태, 코드, 메시지 전달

`GlobalExceptionHandlerTest`는 핸들러를 직접 호출해 예외 변환 책임을 검증할 수 있다. 다음
예제는 상태와 `code`를 확인하고, 임의의 예외 메시지가 응답에 정확히 전달되는지 검증한다.

```java
class GlobalExceptionHandlerTest {

    private final GlobalExceptionHandler handler = new GlobalExceptionHandler();

    @Test
    @DisplayName("잘못된 요청의 상태, 코드, 메시지를 변환한다")
    void handleIllegalArgument() {
        var exception = new IllegalArgumentException("요청 값 검증 실패 원문");

        var response = handler.handleIllegalArgument(exception);
        var body = response.getBody();

        assertNotNull(body);
        assertAll(
                () -> assertEquals(HttpStatus.BAD_REQUEST, response.getStatusCode()),
                () -> assertEquals("INVALID_REQUEST", body.code()),
                () -> assertEquals("요청 값 검증 실패 원문", body.message()));
    }
}
```

예외 메시지가 상황에 적절한지는 이 테스트가 아니라 `IllegalArgumentException`을 만드는 서비스
또는 도메인 테스트에서 검증한다.

## 10. 작성·리뷰 체크리스트

### 테스트 클래스

- [ ] JSON `@RestController`만 대상으로 삼았다.
- [ ] `@WebMvcTest`의 대상 컨트롤러를 명시했다.
- [ ] 컨트롤러의 서비스 협력 객체를 `@MockitoBean`으로 대체했다.
- [ ] 인증이 필요한 정상 요청에 `givenValidMember(...)`를 설정했다.

### 요청과 서비스 협력

- [ ] 모든 엔드포인트에 올바른 HTTP 메서드·경로의 긍정 테스트가 있다.
- [ ] 경로 변수, 쿼리 파라미터, 헤더, JSON 본문의 값이 서비스 인자와 일치한다.
- [ ] 정상 흐름에서 서비스를 정확히 한 번, 정확한 인자로 호출했음을 검증한다.
- [ ] 웹 계층이 거부한 요청에서 서비스 미호출을 검증한다.
- [ ] 비즈니스 유효성 검증을 컨트롤러 테스트에 포함하지 않았다.
- [ ] `verifyNoMoreInteractions()`를 일괄 적용하지 않았다.

### 응답

- [ ] 상태 코드와 해당하는 `Content-Type`·계약 헤더를 검증한다.
- [ ] 성공 응답의 모든 계약 필드를 `jsonPath`로 개별 검증한다.
- [ ] 중첩 객체와 컬렉션의 구조, 크기, 원소 필드를 빠짐없이 검증한다.
- [ ] nullable 필드, 빈 컬렉션, 빈 본문을 계약에 맞게 명시적으로 검증한다.
- [ ] 컨트롤러가 선택하는 모든 응답 분기를 검증한다.
- [ ] 성공 JSON 전체를 문자열 하나로 비교하지 않았다.

### 예외와 공통 컴포넌트

- [ ] 컨트롤러 클래스마다 대표 서비스 예외 전파 테스트가 하나 있다.
- [ ] 대표 예외 테스트에서 동일 예외 인스턴스와 정확한 서비스 호출만 검증한다.
- [ ] 서비스 예외별 HTTP 상태·본문을 컨트롤러 테스트에 반복하지 않았다.
- [ ] 공통 오류 상태·`code`·정확한 `message` 전달은 `GlobalExceptionHandlerTest`에서 검증한다.
- [ ] 인증 인터셉터와 argument resolver의 공통 실패를 엔드포인트마다 반복하지 않았다.
- [ ] 잘못된 경로·HTTP 메서드에 대한 부정 테스트를 작성하지 않았다.
