# 커밋 전 게이트 지침

> 배경: 코드 리뷰 지적 — "사용되지 않는 파라미터가 존재하는 등 코드에 이슈가 존재한다.
> 소나큐브 같은 도구를 활용해, 최종 커밋 전 이슈를 검토해야 한다."
> (예: `ClubService.toMyProgress`의 미사용 `book` 파라미터) (2026-08-05)

## 정적 분석 도구 — PMD + SpotBugs

- **결정 기록:** 2026-08-05 개발자 승인. SonarQube 서버·Error Prone·무도구 대비,
  서버 운영 없이 Gradle 빌드에 통합되어 AI가 커밋 전 직접 실행·수정할 수 있다는 이유로
  PMD + SpotBugs Gradle 플러그인을 채택했다. (새 의존성 — 피드백_루프_하네스 2장 대상)
- **도입 상태: 적용 완료 (2026-08-06).** `build.gradle`에 설정되어 `./gradlew check`로 실행된다.
  도입 시점에 드러난 기존 코드의 위반은 도입 커밋과 분리된 정리 커밋에서 모두 해소했다.
- 실제 설정 (플러그인 버전은 도입 시점 Gradle Plugin Portal·GitHub Releases 기준 최신 안정 버전):

  ```groovy
  plugins {
      id 'pmd'
      id 'com.github.spotbugs' version '6.5.10'
  }

  pmd {
      toolVersion = '7.26.0'
      ruleSets = []
      ruleSetFiles = files('config/pmd/ruleset.xml')
      consoleOutput = true
  }
  ```

  `category/java/bestpractices.xml`, `category/java/errorprone.xml`을 기반으로 하되,
  개별 룰 조정이 필요해 `config/pmd/ruleset.xml`에 커스텀 룰셋으로 구성했다
  (조정 내역은 아래 "제외한 룰 기록" 참고). SpotBugs는 별도 excludeFilter 없이 기본 설정으로 실행한다.

- 규칙 세부 조정(오탐 나는 개별 룰 제외 등)은 이 지침 범위 안에서 수행하되,
  제외한 룰과 이유를 이 문서 하단에 기록한다.

## 게이트 절차 — 모든 커밋 전에 수행한다

1. `./gradlew build` — 컴파일과 전체 테스트 통과.
2. `./gradlew check` — PMD·SpotBugs 이슈 0건.
3. 자가 점검:
   - 미사용 파라미터·필드·임포트·메서드가 없는가.
   - `docs/지침/` 하위 지침(패키지 구조, 도메인 모델링, 정책 구체화)과 대조했는가.
   - 프로덕션 코드 변경에 테스트가 동반되는가 (CLAUDE.md 커밋 조건).
4. 위반 발견 시 수정하고 1번부터 다시 수행한다.

## 억제 금지

- 도구 경고를 `@SuppressWarnings`나 exclude 설정으로 임의로 억제하지 않는다.
  오탐이라고 판단되면 근거와 함께 개발자에게 보고하고, 승인된 억제만 기록을 남기고 적용한다.

## 제외한 룰 기록

`config/pmd/ruleset.xml`에서 다음 4개 룰을 조정했다 (2026-08-06, PMD 7.26.0 도입 시점).
전부 실제 코드 결함이 아니라 이 프로젝트가 따르는 정상적인 관례(MockMvc 슬라이스 테스트,
AssertJ 다중 검증, Spring 테스트 공통 베이스 클래스, Testcontainers 설정 클래스)와
룰의 기본 동작이 구조적으로 충돌해 조정했다.

| 룰 | 조정 | 사유 |
|---|---|---|
| `UnitTestShouldIncludeAssert` | 전체 제외 | `mockMvc.perform().andExpect(...)` 체인이 실제 검증이지만 PMD가 assert 계열 메서드로 인식하지 못해, 컨트롤러 슬라이스 테스트 전반에서 오탐이 발생한다. |
| `UnitTestContainsTooManyAsserts` | 전체 제외 후 `maximumAsserts=5`로 재활성화 | 기본값(1)은 AssertJ로 하나의 결과 객체의 여러 필드를 한 테스트에서 검증하는 이 코드베이스의 정상적인 관례와 충돌한다. 실제 테스트의 최대 assert 수(5)에 맞춰 완전히 끄는 대신 임계값만 완화해, 지나치게 비대한 테스트는 계속 잡아낸다. |
| `AbstractClassWithoutAbstractMethod` | 전체 제외 | `ControllerTest`, `RepositoryTest`처럼 추상 메서드 없이 Spring 테스트 공통 설정(필드, 헬퍼 메서드)만 제공하는 테스트 베이스 클래스는 정상적인 패턴이며 결함이 아니다. |
| `TestClassWithoutTestCases` | 전체 제외 | `TestcontainersConfiguration`이 "Test"로 시작하는 이름 때문에 테스트 클래스로 오인식된다. 실제로는 `@TestConfiguration` 빈 등록 클래스로 테스트 케이스를 가질 필요가 없다. |

### SpotBugs — 참고 (룰 제외 아님)

`CT_CONSTRUCTOR_THROW`(생성자 예외로 인한 파이널라이저 공격 노출)가 `Member`, `Comment` 두 JPA 엔티티에서
발견되었다. SpotBugs 권장 대응(클래스를 `final`로 선언하거나 생성자를 `private`화)은 Hibernate가
지연 로딩 프록시를 만들기 위해 요구하는 "non-final 클래스 + 접근 가능한 no-args 생성자" 조건과 충돌한다.
대신 SpotBugs 문서가 함께 제시하는 세 번째 대응인 "빈 `finalize()`를 `final`로 오버라이드"를 적용해
룰 제외 없이 해결했다 (`protected final void finalize() {}`, `@SuppressWarnings({"deprecation", "removal"})`로
컴파일러의 폐기 경고만 억제). 새로운 도메인 엔티티에서 같은 경고가 발생하면 이 패턴을 그대로 적용한다.
