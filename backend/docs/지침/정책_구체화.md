# 정책 구체화 지침

> 배경: 코드 리뷰 지적 — "비즈니스 정책이 부실하게 기획되어 있다. 기획 단에서 더
> 세부적으로 정리하도록 유도해야 한다." (예: 회원 이름에 글자수 제한이 없음) (2026-08-05)

기존 `피드백_루프_하네스.md`의 멈춤 기준은 스키마·의존성·구조 같은 큰 트레이드오프를
잡는다. 이 지침은 그 그물에 걸리지 않는 **미시 정책**(글자수 제한, 형식, 중복 처리 등)이
임의 결정으로 흘러가는 것을 막는다. 철칙 R1~R4는 여기에도 준용된다.

## 절차 — 기능 착수 전 플랜 단계에서 수행한다

1. **정책 전수 나열.** 이번 기능이 다루는 것을 빠짐없이 나열한다.
   - 모든 입력 필드: 길이·형식·값 범위·필수 여부·공백(트림) 처리
   - 상태 전이와 경계: 중복 요청, 이미 삭제된 대상 참조, 순서가 어긋난 요청
   - 목록 조회: 정렬 기준, 페이징, 최대 건수
2. **명세 대조.** 나열한 항목을 `PRD.md`·`API.md`와 대조해 "확정된 정책"과
   "미정 정책"으로 나눈다.
3. **정책 질의서 제출.** 미정 정책을 **기능 단위로 한 번에 묶어** 제출한다.
   항목 하나마다 개별 결정 요청서를 올리지 않는다 — 관문이 소음이 되면 죽는다.

   ```markdown
   ## 정책 질의: (기능 이름)

   | # | 항목 | 현재 명세 | 질문 / 선택지 | 답 |
   |---|---|---|---|---|
   | 1 | 회원 이름 길이 | 없음 | 상한을 둘까요? 둔다면 몇 자? | |
   ```

4. **기록.** 개발자의 답이 확정되면 `PRD.md`에 반영하고, 관련 문서(`API.md` 등)가
   있으면 함께 갱신한다 (2026-08-05 개발자 결정). 문서 갱신 후 구현·테스트에 반영한다.

## 금지 — 임의 기본값

- **명세에 없는 제한값·기본값을 "상식선"으로 정해 넣지 않는다.** "1000자면 적당하겠지"는
  임의 결정의 다른 이름이다. 반드시 질의서를 거친다.
- 명백히 단일 정답인 항목(예: 식별자는 양의 정수)은 질의 없이 진행하되, 플랜의
  "그냥 진행하는 항목"에 명시해 개발자가 감사할 수 있게 한다 (하네스 4장과 동일).

## 효과

정책 질의서는 결정 요청서의 경량 배치판이다. 기획이 비워 둔 구멍이 구현 시점에
드러나고, 답이 명세 문서에 쌓이면서 기획 자체가 세부적으로 정리된다.
