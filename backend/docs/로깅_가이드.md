# 애플리케이션 로그

## 범위와 결정 원본

[노션 로깅 개선 문서의 로그 설계](https://app.notion.com/p/3e4fb08ea3e68109bcf2e7ea568af0ac)를 적용한다.
회원, 차단, 모임, 독서 진도, 도서·본문, 댓글·신고·조회 기록, 관리자 API와 페이지에 로그를 남긴다.
Better Stack 전송·보관·대시보드 구성은 이번 변경에 포함하지 않는다.

2026-09-29 작업 대화에서 개발자가 확정한 로그 레벨은 다음과 같다.

- 정상 실행과 의도한 4xx 요청 거절: INFO.
- 실패가 복구되어 응답에 성공하는 경우: WARN.
- 서버가 의도하지 않은 실패(현재 5xx 응답): ERROR.

개발자의 명시적 로그 방식 선택 근거 원문:

> 개발자가 외부 의존성을 최소한으로만 신경쓰면서 로그 기능을 완성할 수 있게 만든다. 외부 의존성은 필요성이 느껴질 때 추가해 코드를 개선한다. 외부 의존성을 추가하면 코드 복잡도는 낮아질지언정, 개발자의 코드 이해도가 부족해진다

## 출력과 조회

Spring Boot 내장 Logstash JSON 콘솔 출력을 사용한다. 별도 로깅 의존성을 추가하지 않는다.
기존 SLF4J의 `addKeyValue`로 필드를 기록하며, 타임스탬프·레벨·로거 이름은 JSON 출력에 포함된다.

| 필드 | 의미 |
|---|---|
| `traceId` | 서버가 요청마다 생성하는 ID. 같은 요청의 컨트롤러·서비스·예외 로그를 연결한다. |
| `memberId` | 검증을 통과한 요청 회원의 MDC 값. 개별 로그에 기록한 대상 ID는 해당 작업의 맥락을 나타낸다. |
| `operation` | 실행 작업. `도메인·계층.실제메서드명` 형식을 사용한다. 예: `book.findBooks`, `http.doFilterInternal`. |
| `phase` | `success`, `recovered`, `rejected`, `failure`로 완료 단계를 구분한다. 시작 로그에는 `phase`를 기록하지 않는다. |
| `httpMethod`, `route` | HTTP 메서드와 매핑된 경로 템플릿. 매핑되지 않은 경로는 `unmatched`이다. |
| `status`, `durationMs` | 요청 완료의 HTTP 상태와 처리 시간. 처리 밖으로 전파된 예외는 유효 상태 500을 기록하고 그대로 전파한다. |
| `errorCode`, `reason` | 중앙 예외 처리에서 기록하는 오류 코드와 안전한 거절 사유. |
| `bookId`, `clubId`, `commentId`, 개수·범위 필드 | 각 메서드가 명시적으로 선택한 진단 정보. |

요청 시작부터 `traceId`가 설정된다. 인증 성공 후 `memberId`를 설정하며, 종료 시 필터가
소유한 MDC 값을 복원한다. 현재 동기식 MVC 요청을 대상으로 하며 비동기 실행 전파 기능을 추가하지 않는다.
추적을 위한 HTTP 응답 헤더나 기존 API 응답 계약은 변경하지 않는다.
컨트롤러의 `@AuthMember memberId`는 인증 인터셉터가 검증한 뒤 요청 속성에 저장한 값과 동일하다.
따라서 MDC와 컨트롤러 로그의 `memberId`는 인증 이후 같은 동기 요청 안에서 같은 회원을 가리키며,
필터의 `finally`에서 정리되어 다음 요청으로 전달되지 않는다.

실패율을 집계할 때는 `operation=http.doFilterInternal`의 완료 이벤트를 사용한다.
`status >= 500`은 서버 실패이고, 4xx는 의도한 요청 거절이다.
같은 요청의 예외 설명 이벤트와 메서드 이벤트를 요청 건수로 중복 집계하지 않는다.

## 로그 작성 규칙

- 메서드 시작과 실행 완료는 호출받는 쪽에서 명시적으로 기록한다. 시작 로그는 `phase` 없이 남기고,
  완료 로그에만 결과에 해당하는 `phase`를 기록한다.
- `operation`의 마지막 구간은 로그를 남기는 실제 메서드명과 일치시킨다. 비공개 저장 단계도
  `saveAuthors`, `saveChapters`처럼 실제 비공개 메서드명을 사용한다.
- JPA·SDK 등 외부 구현의 처리 단계는 호출하는 쪽에서 기록한다. 애플리케이션 저장소 래퍼는 자체 로그를 사용한다.
- 메서드의 `success`는 그 메서드 본문이 완료되었음을 뜻한다. 트랜잭션 커밋이나 응답 직렬화까지
  성공했다는 뜻은 아니므로 최종 결과는 HTTP 요청 완료 로그와 함께 확인한다.
- 커스텀 예외에는 불변 `Map<String, String>`으로 안전한 맥락을 전달한다. 예외 응답 로그는
  `GlobalExceptionHandler`가 기록한다. 의도한 거절에는 스택을 출력하지 않고, 예기치 않은 서버 예외에는 스택을 기록한다.
- 기존 재시도·예외 전파 정책은 바꾸지 않는다. 참여 코드 충돌 후 복구와 PostHog 실패 격리 등
  기존에 복구하는 경로는 WARN을 남긴다.
- 관리자 토큰, 참여 코드, 서명 URL, 닉네임, 댓글·도서 본문, 요청·응답 DTO 전체를 로그 필드로 전달하지 않는다.
  URL은 원문이나 쿼리 문자열 대신 매핑된 템플릿을 기록한다.
- 검색 진단을 위해 도서 검색 `keyword`는 값이 `null`인 경우까지 필드 존재를 유지한다.
  그 외 텍스트 본문·닉네임은 기록하지 않는다.
- `resultCount` 등 건수 필드는 실제 컬렉션 크기나 조회·변경 결과에서 계산할 수 있을 때만 기록한다.
  단일 작업이라는 이유로 `1`을 하드코딩하지 않는다.
- 관리자 대시보드는 응답 전체 대신 도서의 ID·상태·모임 수, 모임의 ID·도서 ID·도서 상태·회원/댓글 수,
  회원의 ID·참여 모임 수와 평균·분포만 구조화 요약으로 기록한다.
- 예기치 않은 예외의 스택에는 라이브러리가 생성한 예외 메시지도 포함된다. 민감한 값을
  애플리케이션 예외 메시지에 넣지 않는다.

## 검증

`RequestLoggingFilterTest`는 요청별 traceId와 회원 MDC 격리, 예외 요청의 ERROR 완료를 검증한다.
`GlobalExceptionLoggingTest`, `LogContextExceptionTest`는 중앙 예외 로그 수준과 공통 로그 맥락 계약을 검증한다.
`MemberLoggingTest`는 영속성 작업 실패 후 성공 로그가 남지 않는지 확인하고, `BookLoggingTest`는
검색어의 유무와 관계없이 `keyword`와 `searchUsed` 필드를 유지하는지 확인한다.
`AdminDashboardLoggingTest`는 안전한 식별자·상태·집계만 요약하는지 확인한다.
`PostHogAnalyticsTrackerTest`는 격리된 전송 실패의 WARN 로그를 확인한다.

전체 검증은 백엔드 디렉터리에서 `./gradlew build`로 실행한다.
