# 코어 모듈 스키마 M1 전환 절차

이 문서는 공간·컨텐츠·감상·독서 기록 모듈 스키마로 기존 데이터를 전환하는 운영 절차다.
승인된 방식은 쓰기를 중지하고 이관·검증·애플리케이션 전환을 순서대로 수행하는 M1이다.
이 저장소의 SQL은 운영 DB에 자동 실행되지 않으며, 이 작업 범위에도 운영 실행은 포함되지 않는다.

## 전환 전제

- 기존 애플리케이션과 DB에 쓰는 배치·관리 도구를 모두 중지한다.
- 전환 시작 전에 운영 백업과 복구 리허설을 별도로 완료한다. 스크립트가 만드는
  `core_migration_backup_20261002_*` 테이블은 빠른 대조용이며 운영 백업을 대신하지 않는다.
- MySQL DDL은 각 문장을 자동 커밋한다. 전체 스크립트를 하나의 트랜잭션으로 되돌릴 수 있다고
  가정하지 않는다.
- 개발 환경처럼 `ck_comments_single_space`가 없는 스키마와 과거 배포 SQL로 해당 제약이 있는
  스키마를 모두 처리한다. 존재 여부를 `information_schema`에서 확인하며, 없는 제약을 삭제하려다
  전환이 실패하지 않는다.
- 새 애플리케이션은 스키마 자동 생성이나 변경을 수행하지 않고 `ddl-auto=validate`로 시작한다.

## 실행 순서

1. 쓰기 중지 시각과 운영 백업 식별자를 기록한다.
2. 쓰기 연결이 남아 있지 않은지 확인한다.
3. [2026-10-02-core-modules.sql](2026-10-02-core-modules.sql)을 한 번 실행한다.
4. [2026-10-02-core-modules-verify.sql](2026-10-02-core-modules-verify.sql)을 실행한다.
5. 새 애플리케이션을 `ddl-auto=validate`로 시작하고 읽기·댓글 작성·진도 저장·방문·신고를
   스모크 테스트한다.
6. 검증 결과와 새 애플리케이션 버전을 기록한 뒤 쓰기를 다시 연다.

첫 스크립트는 영속 변경 전에 다음 상태를 거부한다.

- 대상 테이블·대조 백업·새 식별 컬럼 중 하나라도 이미 존재하는 부분 이관 또는 재실행 상태
- 댓글 공간이 없거나 둘인 행, 댓글의 공간과 문장 도서가 다른 행
- 진도 위치와 진도 시각 중 하나만 존재하거나 공간의 도서와 진도 문단의 도서가 다른 행
- 댓글 작성자·조회·신고의 고아 참조
- 공통 식별자 충돌 방지 오프셋이 signed `BIGINT` 범위를 넘는 상태

검사 실패는 오류를 그대로 반환한다. 스크립트는 오류를 삼키거나 기존 대조 백업을 덮어쓰거나
삭제하지 않는다. 실패 후 처음부터 다시 실행하지 말고 아래 실패 처리를 따른다.

## 식별자와 데이터 보존

- `clubs.id`, `public_rooms.id`, `books.id`, `passages.id`, `sentences.id`는 각 타입 테이블에서
  그대로 유지한다.
- 모임과 공개방의 숫자 ID가 같을 수 있으므로 `spaces.id`는 모임 ID 다음에 공개방 ID를
  충돌 없이 배정한다. 원본과 공통 ID의 대응은 각 타입 테이블의 `space_id`가 보존한다.
- 문단과 문장의 숫자 ID가 같을 수 있으므로 `content_locations.id`는 문단 ID 다음에 문장 ID를
  충돌 없이 배정한다. 대응은 `location_id`가 보존한다.
- 책은 현재 유일한 컨텐츠 타입이므로 `contents.id`와 `books.id`가 같다.
- `comments.id`는 `appreciations.id`와 정확히 같다. 작성자와 생성·수정 시각도 그대로 옮긴다.
- 조회와 신고 행은 원본 ID를 유지한다. 조회는 동일 회원·댓글 쌍의 중복을 제거하지 않는다.
- `LEFT` 모임 참여자의 진도, 삭제 상태 도서의 연결과 이력, 방문 시각이 `NULL`인 공개방 활동,
  진도가 없는 공개방 활동을 모두 보존한다.
- 기존 진행·활동·댓글 맥락 컬럼은 이번 expand 단계에서 삭제하지 않는다. 새 애플리케이션이
  사용하지 않도록 두며 제거는 별도 계약으로 진행한다.
- 휴면 `comments`, `comment_views`, `comment_reports`, `public_room_activities`의 기존 모듈 간
  외래 키는 실제 제약 이름을 `information_schema`에서 찾아 제거한다. 그대로 두면 새 구조에서
  감상·회원 데이터를 정해진 순서로 지워도 휴면 복사본이 삭제를 막는다. live 조회·신고 행에는
  회원과 댓글 삭제 `CASCADE`를, live 공개방 활동에는 회원과 공개방 삭제 `CASCADE`를 다시 건다.
  따라서 기존 API의 계정·댓글 삭제처럼 소유 관계가 사라지면 live 휴면 행도 정리된다. 새 앱은
  이 테이블에 새 행을 쓰지 않는다. `core_migration_backup_20261002_*` 대조 백업에는 FK를 걸지 않고
  이관 시점 원본을 그대로 보존한다.

## 실패와 복구

### 첫 SQL 실행 전 또는 사전 검사 실패

영속 변경이 없으므로 원인을 수정한 다음 전체 절차를 다시 시작할 수 있다. 쓰기는 계속 닫아 둔다.

### 첫 SQL 실행 도중 실패

부분 DDL 상태이므로 같은 파일을 재실행하지 않는다. 시작 시점의 운영 백업으로 DB 전체를 복구한
뒤 원인을 수정하고 처음부터 수행한다. `core_migration_backup_20261002_*` 테이블은 조사와 원본 대조를
위해 남기며 임의로 삭제하지 않는다.

### 검증 또는 새 애플리케이션 스모크 실패, 쓰기 재개 전

쓰기를 계속 닫은 채 새 애플리케이션을 내리고 다음 둘 중 하나를 수행한다.

- 새 애플리케이션과 이관 스키마를 수리한 뒤 이관 검증 SQL과 스모크 테스트를 처음부터 다시 통과시킨다.
- 기존 애플리케이션으로 복귀하려면 시작 시점의 전체 운영 백업을 반드시 복원하고, 기존 애플리케이션의
  스키마 검증과 스모크 테스트를 통과시킨 다음 쓰기를 연다.

레거시 컬럼을 남겨 둔 사실은 기존 애플리케이션과 호환되는 롤백을 보장하지 않는다. 새 식별 컬럼의
`NOT NULL`과 루트 FK 등 이관 DDL이 적용된 상태에서는 기존 애플리케이션의 신규 쓰기가 실패할 수 있다.

### 새 애플리케이션에서 쓰기를 재개한 뒤

애플리케이션 버전만 되돌리지 않는다. 새 테이블에만 존재하는 쓰기를 레거시 구조로 역이관하는 별도
절차가 필요하다. 이 저장소는 그 역이관을 제공하지 않으므로 쓰기를 다시 중지하고 보존할 새 데이터와
복구 시점을 정한 다음 별도 승인된 복구 계획을 수행한다.

## 검증 범위

검증 SQL은 원본과 대조 백업의 행 수, 타입별 루트와 타입 테이블의 대응, 공간–컨텐츠 및
위치–컨텐츠 쌍, 댓글 작성자·시각·맥락, 양쪽 공간의 진도, 모든 공개방 활동의 방문 이력,
중복을 포함한 조회 행과 신고 행을 비교한다. 초기 타입(`CLUB`, `PUBLIC_ROOM`, `BOOK`,
`PASSAGE`, `SENTENCE`, `COMMENT`)에 루트만 있고 타입 행이 없는 상태도 실패시킨다.
테스트는 FK 재구성 뒤 canonical 감상 삭제와 `LEFT` 참여 회원 삭제가 성공하고, 삭제 대상의 live
휴면 조회·신고·활동 행은 없어지며 다른 회원 데이터와 대조 백업은 남는 것도 검증한다.

미래 타입 이름은 공통 루트의 `CHECK`나 열거형에 닫아 두지 않는다. 새 타입은 자신의 타입 테이블과
로컬 타입 제약, 루트와의 복합 외래 키를 추가하고 생성 트랜잭션과 무결성 검사로 루트–타입 쌍을
보장한다.
