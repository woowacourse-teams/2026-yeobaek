# 프로토타입 ↔ API.md 대조 조사

> 작성일: 2026-08-07 · 상태: **결정 완료 — API.md 반영됨** (결정 기록은 문서 하단)
> 대상: [`yeobaek-web-prototype`](https://github.com/noeyhoj/yeobaek-web-prototype.git) ↔ [`docs/API.md`](../../../docs/API.md)
> 디자인 프로토타입 기준으로 API.md의 누락·불일치를 조사한 결과다. 각 항목의 처리 방향이 결정되면 API.md 수정안을 작성한다.

## 조사 범위

- 프로토타입 화면 6종: 시작(landing), 홈(home), 모임 참여(join), 모임 만들기(create), 모임 상세(detail), 뷰어(reader) — `app/reading-app.tsx`
- 보조 문서: 전체 화면 플로우(`app/flow/page.tsx`), 화면 스펙(`app/screen-specs/page.tsx`)
- 이미 합의된 변경 요구사항(**페이지 번호 삭제, 이미지 미제공**)에 해당하는 차이는 D절로 분리했다.

## A. API 자체가 누락된 경우

### A-1. 모임 상세 조회 API 없음 — 가장 큰 누락

모임 상세 화면(`reading-app.tsx:321-331`)은 아래 데이터를 표시하지만, 이를 제공하는 API가 없다.

| 상세 화면에 필요한 값 | 현재 API로 얻을 수 있는가 |
|---|---|
| 모임 이름, 책 제목·저자 | `GET /api/clubs`(목록)에서 우회 가능 |
| 내 독서 진행률 ("독서 진행률 35%") | 목록의 `myProgress`로 우회 가능 |
| **초대 코드** (`reading-app.tsx:326`, 복사 기능 포함) | **불가** — `joinCode`는 모임 **생성 응답에만** 존재 (`API.md:114`). 참여자이거나, 생성자라도 재진입하면 초대 코드를 얻을 방법이 전혀 없음 |
| **참여자 목록** (닉네임 + 본인 표시, `reading-app.tsx:327`) | **불가** — 목록 API는 `memberCount`(숫자)만 제공 (`API.md:148`) |

`GET /api/clubs/{clubId}` 형태의 상세 API가 없으면 이 화면 자체를 구현할 수 없다. 초대 코드 공유는 PRD상 핵심 플로우(친구 초대)다.

## B. API는 있으나 값(명세)이 부족한 경우

### B-1. 도서 목록에 소개 문구 없음

모임 만들기 STEP 02의 책 카드가 한 줄 소개를 표시한다 — "삶의 가능성을 다시 바라보는 이야기" 등 (`reading-app.tsx:17-36`의 `note` 필드, 렌더링은 `:313`). `GET /api/books` 응답(`API.md:66-78`)에는 대응 필드가 없다.

### B-2. "이달의 추천 도서" 개념 없음

모임 만들기 화면은 기본적으로 "이달의 추천 도서" 목록을 보여주고, "직접 검색"은 보조 동작이다(`reading-app.tsx:311`). `GET /api/books`는 전체 목록/검색만 정의되어 있어, 추천 목록이 별도 개념인지 전체 목록과 동일한지가 미정이다. (데모 범위에서는 전체 목록 = 추천 목록으로 볼 수도 있으나, 명세에 그 판단이 기록되어 있지 않다.)

### B-3. `joinCode` 형식 미명세

프로토타입은 참여 코드를 **6자리, 영대문자+숫자**로 강제한다 — 입력 시 `toUpperCase().replace(/[^A-Z0-9]/g,"").slice(0,6)` (`reading-app.tsx:297`), "6자리" 안내 문구와 `{n}/6` 카운터. API.md는 "서버 발급, 전역 unique, 영구 고정"만 명시(`API.md:118`)하고 길이·문자 집합 규칙이 없다. 클라이언트 입력 검증 구현에 필요한 값이다.

### B-4. 모임 이름(`name`) 검증 규칙 미명세

프로토타입은 모임 이름을 **20자 제한**으로 입력받는다(`reading-app.tsx:310`, `.slice(0, 20)` + `{n}/20` 카운터). `POST /api/clubs` 요청 명세(`API.md:104-107`)에는 `name`의 길이·공백 규칙이 없다. (회원 `nickname`은 "1~20자, 공백만은 불가"로 명세되어 있는 것과 대비된다.)

## C. API.md 내부 불일치 (변경 요구사항 관련)

### C-1. `imageUrl` 필드 잔존

"이미지 제공 x" 요구사항 및 관리자 업로드 명세("이미지는 데모 범위에서 제외", `API.md:312`)와 달리, 본문 범위 조회 응답에는 `imageUrl` 필드와 "`content`와 `imageUrl` 중 하나 이상 존재" 규칙이 남아 있다(`API.md:181-187`). 업로드 경로가 없으니 이 필드는 항상 `null`일 수밖에 없어, 명세 내부적으로도 모순이다.

## D. 합의된 변경 요구사항으로 설명되는 차이 (조치 불요, 확인용)

- **페이지 번호**: 홈 카드의 "P. 42", 상세의 "P. 48 / 140", 뷰어의 페이지 인디케이터·하단 "P. 42" (`reading-app.tsx:272, 325, 349, 351`) — API는 `sequence`/`passageCount` 기반이며 페이지 개념이 없음. 변경 요구사항과 일치.
- **이미지**: 책 표지(`cover`), 참여자 아바타(`AVATARS`) — API에 대응 필드 없음. 변경 요구사항과 일치.

## E. 역방향 차이 — 프로토타입에는 없지만 API에는 있는 것 (안드로이드와 확인 권장)

| 항목 | 상황 |
|---|---|
| **회원 생성 / 닉네임 입력** | API는 최초 진입 시 `POST /api/members`(닉네임 필수)를 전제하지만, 프로토타입 시작 화면에는 닉네임 입력 단계가 없음 — 온보딩 화면이 디자인에서 빠져 있는 것인지 확인 필요 |
| 댓글 수정·삭제 | API에 존재하나 프로토타입 댓글 드로어에 해당 UI 없음 |
| 목차(chapters) / 챕터 이동 | `GET /api/books/{bookId}`가 목차를 제공하나 뷰어에 챕터 UI 없음 |
| 모임 상세의 "더보기(⋮)" 버튼 | 프로토타입에 버튼만 있고 동작 미정의 — 기능이 생기면 API 영향 가능 |

(뷰어 헤더의 저자 영문 표기 "Hermann Hesse"는 디자인 장식으로 판단해 목록에서 제외했다.)

## 정리

구현을 막는 수준의 누락은 **A-1(모임 상세 조회 — 초대 코드·참여자 목록)** 하나이고, 나머지는 필드 추가(B-1)와 명세 보강(B-2~4), 문서 정리(C-1)다. API 계약 변경은 피드백 루프 하네스 2장 멈춤 기준에 해당하므로, 각 항목의 처리 방향(상세 API 신설 범위, 추천 도서 처리, 소개 문구 채택 여부 등)이 결정된 뒤 API.md 수정안을 작성한다.

## 결정 기록 (2026-08-07, 개발자 답글 원문 인용)

> A-1. 모임 상세 조회 API 구현
> B-1. 도서 한줄 소개는 프로토타입에서 제외
> B-2. 이달의 추천 도서 기능 없음 - 사용자는 검색 기능을 활용해야만 책을 선택할 수 있음 (MVP 범위 밖이라 판단)
> B-3. 클라이언트 단에서 joinCode 입력을 검증할 필요 없음.
> B-4. 모임 이름 검증 규칙도 명세에 포함
> C-1. imageUrl는 스펙에서 제거
> E-닉네임. 실제 흐름에서는 닉네임을 입력받을 것

이유 (후속 답글 원문 인용):

> A-1. 유저 플로우에 반드시 필요한 기능이라 구현 요청
> B-3. 사용자는 어차피 공유받은 값을 그대로 입력할거라, 클라이언트 단에서 추가적인 검증이 UX상 불필요
> B-4. 사용자 입장에서 모임 생성을 요청했을 때 가서야 '모임 이름은 20글자 까지만 가능해요'라는 에러를 보는게 아니라, 애시당초 에러를 보지 못하게 모임 이름을 입력할 때 제한하는게 UX상 바람직함
> C-1. imageUrl을 스펙에 포함하게 되면, 클라이언트 코드에서 imageUrl가 있을 때 어떻게 처리할지 로직을 짜야 하는데, MVP에서 불필요한 작업이고, imageUrl 처리 방법이 언제든 변할 수 있기 때문에 YAGNI 원칙에 위배

### API.md 반영 내역 (사실 기록)

| 결정 | 반영 |
|---|---|
| A-1 | `GET /api/clubs/{clubId}` 신설 — 초대 코드, 참여자 목록(닉네임 + `mine`), `myProgress` 포함. 엔드포인트 요약에 추가 |
| B-1 | API 변경 없음 (프로토타입 요소 제외) |
| B-2 | API 변경 없음 (`GET /api/books?keyword` 검색으로 충당, 추천 개념 미도입) |
| B-3 | API 변경 없음 (`joinCode` 형식 미명세 유지, 클라이언트 검증 없음) |
| B-4 | `POST /api/clubs`의 `name`에 검증 규칙 명세 — 1~20자, 공백만 불가 (프로토타입 20자 제한 및 `nickname` 규약과 동일한 형식) |
| C-1 | 본문 범위 조회 응답에서 `imageUrl` 필드 제거, "`content`는 항상 존재"로 개정 |
| E-닉네임 | API 변경 없음 (`POST /api/members` 기존 명세로 충당됨을 확인) |

- A-1, B-3, B-4, C-1의 이유는 후속 답글로 기록되었다. B-1, E-닉네임은 선택만 있고 이유가 기록되지 않았다 (하네스 4장에 따라 그대로 진행).
- B-4의 구체 규칙(1~20자, 공백만 불가)은 결정 답글에 명시되지 않아, 프로토타입의 20자 제한과 기존 `nickname` 규약 형식을 따랐다.
