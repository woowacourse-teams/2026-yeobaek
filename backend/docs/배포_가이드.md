# 배포 가이드

EC2에서 앱과 MySQL을 Docker Compose로 실행한다. GitHub Actions가 이미지를 Docker Hub에
발행하면 EC2의 Runner가 받아 배포한다. 스키마는 Flyway와 Hibernate `validate`로 관리하고,
HTTPS는 호스트의 Nginx와 Let's Encrypt로 제공한다.

## 구성 개요

```
GitHub (main push, 서버 빌드·실행 입력 변경)
  ├─ build 잡 (GitHub 호스티드): gradle build(게이트) → 이미지 빌드 → Docker Hub 푸시
  └─ deploy 잡 (EC2 셀프 호스티드 러너, 라벨 ec2-prod): 새 앱 시작 → SHA 확인 → Nginx 전환 → 이전 앱 종료
       └─ EC2:
            ├─ yeobaek-app-blue / yeobaek-app-green (Spring Boot, 127.0.0.1:8080 / 8081)
            ├─ yeobaek-mysql (볼륨 mysql-data에 데이터 영속)
            ├─ nginx (호스트 설치) ── HTTPS(443) → yeobaek_app upstream → 현재 앱
            └─ EC2 instance role ── Presigned PUT 서명 권한
                 └─ S3 yeobaek/book-covers/* (익명 읽기, 서명된 쓰기만 허용)
```

| 항목 | 개발 | 운영 |
| --- | --- | --- |
| 배포 브랜치 | `develop` | `main` |
| 러너 라벨 | `ec2-dev` | `ec2-prod` |
| 서버 배포 경로 | `~/yeobaek-dev` | `~/yeobaek` |
| Compose 프로젝트 | `yeobaek-dev` | `yeobaek` |
| Nginx 설정 | `/etc/nginx/conf.d/yeobaek-dev.conf` | `/etc/nginx/conf.d/yeobaek.conf` |
| 헬스체크 | `https://yeobaekdev.duckdns.org/health` | `https://yeobaek.duckdns.org/health` |
| Spring 프로필 | `prod,dev` | `prod` |

배포 트리거는 [개발 워크플로](../../.github/workflows/backend-dev.yml)와
[운영 워크플로](../../.github/workflows/backend-prod.yml)에서 확인한다.
공통 실행 조건과 기록은 [공용 배포 안내](../infra/deploy/README.md)를 참고한다.

## 2. EC2 최초 세팅 (1회)

개발·운영 모두 Amazon Linux 2023 ARM64와 `ec2-user`를 기준으로 한다.
이미 설치된 서버에서는 버전과 서비스 상태를 확인하고 설치 단계를 건너뛴다.

```bash
# EC2에서 Docker 설치 및 서비스 활성화
sudo dnf install -y docker
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"   # 적용하려면 SSH 재접속
```

재접속 후 `docker info`와 `docker compose version`을 확인한다.
Compose 플러그인이 없다면 모든 사용자와 Runner가 사용할 수 있는 경로에 설치한다.
아래는 팀에서 사용하는 버전이며, 수동 설치한 플러그인은 자동 업데이트되지 않는다.

```bash
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -fSL https://github.com/docker/compose/releases/download/v5.6.0/docker-compose-linux-aarch64 \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
docker compose version
mkdir -p ~/yeobaek
```

참고: [AWS Docker 설치](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-docker.html),
[Docker Compose 플러그인 설치](https://docs.docker.com/compose/install/linux/).

```bash
# 작업 PC의 저장소 루트에서 운영 서버로 복사
scp -i <키> backend/infra/prod/docker-compose.prod.yml <user>@<host>:~/yeobaek/docker-compose.yml
scp -i <키> backend/infra/prod/otel-collector.yaml <user>@<host>:~/yeobaek/otel-collector.yaml
```

운영 파일은 다음과 같이 배치한다. 환경 파일 예시에는 비밀값을 넣지 않으며,
기존 서버에서는 필요한 키만 반영하고 실제 파일 전체를 빈 예시로 덮어쓰지 않는다.

| 저장소 파일 | 운영 서버 위치/역할 |
|---|---|
| [`docker-compose.prod.yml`](../infra/prod/docker-compose.prod.yml) | `~/yeobaek/docker-compose.yml` |
| [`otel-collector.yaml`](../infra/prod/otel-collector.yaml) | `~/yeobaek/otel-collector.yaml` |
| [`.env.example`](../infra/prod/.env.example) | `~/yeobaek/.env` 작성 참고; Compose 치환용 |
| [`otel.env.example`](../infra/prod/otel.env.example) | `~/yeobaek/otel.env` 작성 참고; Collector 전용 |

`.env`에는 Docker Hub·DB·관리자·S3·PostHog·Firebase 값을 설정한다.
`FIREBASE_CREDENTIALS_FILE`은 운영 서버에 실제 존재하는 서비스 계정 JSON의 절대 경로여야 한다.
Compose는 해당 파일을 읽기 전용으로 `/run/secrets/firebase-admin.json`에 연결하며,
파일이 없을 때 디렉터리를 자동 생성하지 않는다.

Collector의 `otel.env`에는 `MYSQL_MONITOR_PASSWORD`와
앱 소스용 `BETTER_STACK_APP_OTLP_ENDPOINT`·`BETTER_STACK_APP_SOURCE_TOKEN`,
인프라 소스용 `BETTER_STACK_INFRA_OTLP_ENDPOINT`·`BETTER_STACK_INFRA_SOURCE_TOKEN`을 설정한다.
개발과 변수 이름은 같지만 값은 각 환경의 Better Stack 소스에 맞춘다.
운영 서버에는 운영 앱·인프라 소스에서 확인한 URL과 토큰을 설정한다.
endpoint는 `/v1/logs` 등의 경로를 붙이지 않은 OTLP base URL을 사용한다.
`otel.env`의 키는 Collector YAML의 환경변수 참조와 일치해야 한다.

운영 Collector는 호스트·MySQL·`yeobaek` DB의 SQL digest 메트릭을 인프라 소스로,
앱 로그·메트릭·트레이스를 앱 소스로 전송한다. 개발의 `yeobaek_load_test`는 운영 수집 대상에 포함하지 않는다.
`otel_monitor` MySQL 계정과 필요한 권한은 별도로 준비한다. Compose가 이 계정을 생성하지는 않는다.
Collector 0.161.0의 SQL Query receiver 이름은 `sql_query/mysql_digest`를 사용한다.

개발·운영 Compose의 MySQL 시작 옵션은 `events_statements_cpu`를 활성화해
재시작 후에도 쿼리별 CPU 시간을 측정한다. 옵션은 MySQL이 시작될 때 적용되므로,
파일을 수정하는 것만으로 실행 중인 DB의 설정이 바뀌지는 않는다.
실행 중인 MySQL에서 CPU 계측이 꺼져 있다면 관리자 계정으로 다음 SQL을 실행해 재시작 없이 켤 수 있다.

```sql
UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES'
WHERE NAME = 'events_statements_cpu';

SELECT NAME, ENABLED
FROM performance_schema.setup_consumers
WHERE NAME IN (
  'global_instrumentation', 'thread_instrumentation',
  'statements_digest', 'events_statements_cpu'
);
```

해당 consumer들이 `YES`인지 확인하고, 앱 요청 발생 후 `yeobaek`의 digest 통계에서
`SUM_CPU_TIME`이 증가하는지와 Better Stack의 `mysql.query.cpu.total` 수신을 확인한다.
CPU 시간은 활성화 이후부터 측정하며, 이전 구간의 값을 복구하지 않는다.
SQL로 바꾼 consumer 상태는 재시작 후 유지되지 않으므로 시작 옵션도 함께 관리한다.
서버의 Compose 파일을 수정하는 것만으로 실행 중인 MySQL이 재시작되지는 않는다.
자동 배포는 새 앱 서비스만 시작하므로, MySQL의 Compose 시작 옵션은 DB 재시작이 가능한 시점에 별도로 적용한다.
재시작 후 위 조회로 활성화 상태를 다시 확인한다.
컨테이너가 재생성돼도 같은 Compose 프로젝트와 `mysql-data` 볼륨을 사용하면 데이터는 유지되며,
백업 복원은 필요하지 않다. DB가 다시 준비될 때까지 연결은 잠시 끊긴다.
볼륨 삭제나 프로젝트·볼륨 이름 변경은 이와 다르므로 일반 배포에서 수행하지 않는다.
시작 옵션은 [MySQL Performance Schema 옵션](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-options.html)을 참고한다.

서버에서 실제 값을 채운 뒤, 기동 전에 구성을 검사한다. 출력에 비밀값을 노출하지 않도록
Compose는 `config --quiet`로 검사한다. Collector의 `validate`는 설정 검사이며 실제 수집·전송 검증은 아니다.

```bash
cd ~/yeobaek
chmod 600 .env otel.env
docker compose config --quiet
docker compose run --rm --no-deps otel-collector validate --config=/etc/otelcol-contrib/config.yaml
```

PostHog는 기본적으로 `POSTHOG_ENABLED=false`로 둔다. 실제 사용자가 없는 운영 환경에서 내부 테스트 계정으로 백엔드 이벤트 수신을 검증할 때만 `true`로 바꾸고, US Cloud의 프로젝트 API 키를 `POSTHOG_API_KEY`에 설정한다. `POSTHOG_HOST`는 `https://us.i.posthog.com`을 사용한다. 값이 비어 있는 상태에서 활성화하면 잘못된 운영 배포를 막기 위해 애플리케이션 시작이 실패한다. API 키는 Compose 파일이나 저장소에 커밋하지 않는다. 실제 사용자 유입 전에는 다시 비활성화하거나 국외 이전 동의 기능을 먼저 구현한다.

새 EC2의 최초 기동(이후는 CI가 수행):

```bash
cd ~/yeobaek && docker compose pull app-blue mysql otel-collector && docker compose up -d app-blue mysql otel-collector
curl http://127.0.0.1:8080/api/books -H 'X-Member-Id: 1'   # 400(MEMBER_NOT_FOUND)이면 정상 기동
```

### 셀프 호스티드 러너 등록 (배포 잡 실행용, 1회)

1. 저장소 **Settings → Actions → Runners → New self-hosted runner** → 배포 대상 Graviton EC2에
   맞는 Linux ARM64를 선택하고,
   안내되는 다운로드·`./config.sh` 명령을 EC2에서 그대로 실행한다.
   `config.sh`가 라벨을 물으면 **`ec2-prod`를 추가**한다 (배포 잡의 `runs-on: [self-hosted, ec2-prod]`와 매칭).
2. systemd 서비스로 등록해 재부팅에도 유지되게 한다:
   ```bash
   sudo ./svc.sh install && sudo ./svc.sh start
   ```
3. 러너 실행 유저는 docker 그룹에 속해 있어야 한다 (위 Docker 설치 단계의 `usermod` 적용 후 서비스 재시작).
4. public 저장소이므로 **Settings → Actions → General**에서 "Require approval for all outside collaborators"를
   켜 두고, `pull_request` 트리거 워크플로에는 셀프 호스티드 라벨을 사용하지 않는다.

### 도서 표지 S3 생성 (1회)

[`infra/prod/book-cover-s3.yml`](../infra/prod/book-cover-s3.yml)은 다음 리소스를 만든다.

- ACL을 끄고 암호화·버전 관리를 활성화한 S3 버킷
- `${StoragePrefix}/book-covers/*`에 한정한 익명 `GetObject` 정책
- 관리자 웹 origin의 `PUT`만 허용하는 CORS
- 기존 EC2 instance role에 `${StoragePrefix}/book-covers/*` `PutObject`만 부여하는 인라인 정책

AWS CLI가 배포 대상 계정·리전에 로그인된 환경에서 실행한다.

```bash
aws cloudformation deploy \
  --stack-name yeobaek-book-covers \
  --template-file backend/infra/prod/book-cover-s3.yml \
  --parameter-overrides \
    AdminOrigin=https://<서비스-도메인> \
    AppInstanceRoleName=<EC2-instance-role-name> \
    StoragePrefix=yeobaek \
  --capabilities CAPABILITY_IAM

aws cloudformation describe-stacks \
  --stack-name yeobaek-book-covers \
  --query 'Stacks[0].Outputs'
```

출력된 `CoverBucketName`, `CoverBucketRegion`, `CoverPublicBaseUrl`, `CoverStoragePrefix`를 위 `.env`에
기록하고 앱을 재기동한다. `BOOK_COVER_S3_PREFIX`를 생략하면 애플리케이션은 `yeobaek`을 사용한다.
access key는 저장하지 않는다. 컨테이너가 EC2 instance metadata를 통해 role
자격증명을 읽을 수 있어야 한다.

Docker bridge 안의 AWS SDK가 EC2 role 자격증명을 IMDSv2로 읽으려면 metadata 응답이 컨테이너까지
한 홉 더 이동할 수 있어야 한다. AWS가 컨테이너 환경에 권장하는 것처럼 기존 인스턴스의 metadata
응답 hop limit을 2로 설정하고 IMDSv2만 허용한다.

```bash
aws ec2 modify-instance-metadata-options \
  --instance-id <EC2-instance-id> \
  --http-endpoint enabled \
  --http-tokens required \
  --http-put-response-hop-limit 2
```

참고: [AWS EC2 instance metadata 접근 고려사항](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html)

계정 또는 AWS Organizations 수준에서 S3 Block Public Access를 강제하고 있으면 버킷 수준 설정보다
우선한다. 이 경우 공개 읽기 정책을 적용할 수 있도록 해당 계정 정책을 먼저 확인해야 한다.
`${BOOK_COVER_S3_PREFIX}/book-covers/*`에는 공개해도 되는 표지 이외의 객체를 저장하지 않는다.

## 3. nginx + Let's Encrypt (호스트 설치, 1회)

도메인의 A 레코드를 EC2 퍼블릭 IP로 연결하고 80·443 포트가 열려 있는 상태에서 진행한다.
이미 HTTPS가 설정돼 있다면 아래 신규 설정 파일 작성·발급은 건너뛰고,
`nginx -t`, 인증서 상태와 갱신 타이머를 확인한다. 기존 설정을 덮어쓰지 않는다.
Amazon Linux의 `/etc/nginx/nginx.conf`가 `/etc/nginx/conf.d/*.conf`를 포함하는지 확인한다.
배포 중 기존 worker의 종료를 확인할 수 있도록 Nginx의 전역 `error_log`는 `/var/log/nginx/error.log notice`로 설정한다.

```bash
sudo dnf install -y nginx certbot python3-certbot-nginx
sudo tee /etc/nginx/conf.d/yeobaek.conf <<'EOF'
upstream yeobaek_app {
    server 127.0.0.1:8080;
}

server {
    listen 80;
    server_name <도메인>;

    location / {
        proxy_pass http://yeobaek_app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
sudo nginx -t && sudo systemctl enable --now nginx
sudo systemctl reload nginx

# 신규 HTTPS 발급: 443 서버 블록·리다이렉트를 Certbot이 구성한다.
sudo certbot --nginx -d <도메인>
```

인증서 자동 갱신은 timer/cron으로 관리한다. 다음 명령으로 인증서와 설치된 timer를 확인한다.
기존에 별도 갱신 timer/cron을 운영한다면 중복 등록하지 않고 그 작업을 확인한다.

```bash
sudo certbot certificates
systemctl list-unit-files '*certbot*.timer'
# 패키지의 certbot-renew.timer가 존재하는 경우 활성화한다.
sudo systemctl enable --now certbot-renew.timer
systemctl list-timers --all '*certbot*'
sudo certbot renew --dry-run
```

다른 이름으로 설치됐다면 실제 unit 이름을 사용한다. timer가 없다면
[AWS의 Amazon Linux 2023 Certbot 설정 안내](https://repost.aws/articles/ARnkXnIN5GQ-G5GySZTH9P_w/install-certbot-on-amazon-linux-2023-al2023)에 따라
갱신 작업을 등록한다. `renew --dry-run` 성공과 다음 timer 실행 시각을 모두 확인한다.
`/etc/letsencrypt/renewal/*.conf`와 hook이 참조하는 경로가 해당 서버에 존재하는지 확인한다.

## 4. 스키마 변경

개발·운영 서버 모두 EC2 Amazon Linux 2023의 Docker Compose 환경을 기준으로 한다.
애플리케이션을 시작하면 Flyway가 미적용 버전을 실행하고, 성공한 뒤 Hibernate `validate`가 매핑을 검사한다.
일반 배포에서 SQL이나 별도 Java 실행기를 수동으로 실행하지 않는다.

### 파일과 이력

- SQL: `src/main/resources/db/migration/V<버전>__<설명>.sql`
- Java: `src/main/java/db/migration/V<버전>__<설명>.java` (`BaseJavaMigration`)
- 실행 이력: 대상 DB의 `flyway_schema_history`
- 적용한 파일은 수정하지 않고 다음 버전을 추가한다. Java 마이그레이션도 동일하다.
- `local`만 `db/local/V1.1__local_seed.sql`을 추가한다. 서버에서는 공통 마이그레이션만 실행한다.

스키마 변경과 데이터 보충은 앱의 버전별 Flyway 마이그레이션으로 적용한다.
`docs/migrations/`의 수동 SQL은 과거 작업 기록이며 일반 배포에서 실행하지 않는다.

### 서버 선택

다음 명령은 기존 접속 경로로 대상 EC2에 접속한 뒤 같은 Bash 셸에서 실행한다.
개발 서버는 `~/yeobaek-dev`, 프로젝트 이름 `yeobaek-dev`를 사용한다.
운영 서버는 `~/yeobaek`, 프로젝트 이름 `yeobaek`을 사용한다.

```bash
set -euo pipefail
# 개발 서버
cd "$HOME/yeobaek-dev"
COMPOSE=(docker compose -p yeobaek-dev -f docker-compose.yml)
# 운영 서버에서는 위 두 줄 대신:
# cd "$HOME/yeobaek"
# COMPOSE=(docker compose -p yeobaek -f docker-compose.yml)

"${COMPOSE[@]}" ps
MYSQL_CONTAINER=$("${COMPOSE[@]}" ps -q mysql)
test -n "$MYSQL_CONTAINER"
docker inspect --format '{{.Name}} {{.State.Status}}' "$MYSQL_CONTAINER"
```

이 문서의 DB 명령은 앱이 해당 Compose의 `mysql` 서비스에 연결하는 구성을 전제로 한다.
`YEOBAEK_DATABASE_URL`로 외부 DB를 지정했다면 실제 대상에 맞춰 연결 정보를 변경한다.
DB 백업과 복원 경로를 확인하고 데이터 변경 동안 기존 앱과 진행 중인 업로드를 중단한다.

### 기존 DB의 최초 baseline 및 실패 복구 도구

빈 DB는 V1부터 자동 실행한다. 기존 DB에 Flyway 이력이 없다면 먼저 V1과 실제 스키마가
일치하는지 확인하고 **명시적으로 버전 1을 baseline**한다. `baseline-on-migrate=false`를 유지한다.
V1과 다른 스키마에는 이 baseline 명령을 그대로 적용하지 않는다.

최초 baseline과 장애 시 `info`·`repair`에만 공식 Flyway CLI를 사용한다.
배포할 커밋에서 `backend/`의 `./gradlew jar`로 만든
`build/libs/backend-0.0.1-SNAPSHOT-plain.jar`를 서버의
`$HOME/yeobaek-migrations/backend-migrations.jar`로 전달한다.
앱과 **같은 커밋**의 일반 JAR이어야 하며, `BOOT-INF`에 중첩된 실행 JAR로 대체하지 않는다.
SQL과 Java 마이그레이션 클래스가 모두 같은 classpath에 있어야 한다.
현재 앱 의존성과 같은 Flyway 12.4.0 CLI를 사용한다. 버전을 올리면 앱과 도구를 함께 확인한다.

```bash
MIGRATION_JAR="$HOME/yeobaek-migrations/backend-migrations.jar"
test -f "$MIGRATION_JAR"
# 비밀번호를 명령 인자에 넣지 않고 컨테이너 환경에서 읽는다. 셸 추적(set -x)은 사용하지 않는다.
export FLYWAY_PASSWORD
FLYWAY_PASSWORD=$(docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' "$MYSQL_CONTAINER" \
  | sed -n 's/^MYSQL_ROOT_PASSWORD=//p')
test -n "$FLYWAY_PASSWORD"
trap 'unset FLYWAY_PASSWORD' EXIT

flyway_admin() {
  docker run --rm --network "container:$MYSQL_CONTAINER" \
    --env FLYWAY_PASSWORD \
    --mount "type=bind,src=$MIGRATION_JAR,dst=/flyway/jars/backend-migrations.jar,readonly" \
    redgate/flyway:12.4.0 \
    '-url=jdbc:mysql://127.0.0.1:3306/yeobaek?allowPublicKeyRetrieval=true' -user=root \
    -locations=classpath:db/migration "$@"
}

flyway_admin info
# 이력이 없는 기존 V1 스키마에서만 한 번:
# flyway_admin -baselineVersion=1 baseline
```

DB 포트를 외부에 공개하지 않는다. 임시 CLI 컨테이너는 종료 시 삭제된다.
작업 후 `unset FLYWAY_PASSWORD`를 실행한다. CLI의 baseline/repair를 앱 시작 시 자동 실행하지 않는다.
MySQL DDL은 구문별로 커밋될 수 있으므로 실패 시 실제 적용된 테이블·컬럼·제약과 Flyway 이력을 확인한다.
`repair`는 데이터 복구 기능이 아니며, 원인 수정과 실제 DB 상태 확인 후에만 실행한다.
SQL을 임의로 적용하거나 성공 이력을 직접 기록하지 않는다.

참고: [Flyway CLI](https://documentation.red-gate.com/flyway/reference/usage/command-line),
[Java 마이그레이션](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/java-based-migrations),
[repair](https://documentation.red-gate.com/flyway/reference/commands/repair).

## 5. 배포 이후

- **서버·DB 헬스체크**: `GET https://<도메인>/health`로 서버와 DB의 상태를 확인한다.
  정상이면 `200 OK`, DB 통신에 실패하면 `503 Service Unavailable`을 반환한다.
- **호스트 공유**: 발급된 `https://<도메인>`을 안드로이드 팀과 공유하고 `API.md` 0장의 Base path 항목을 갱신한다.
- **실제 책 투입**: `https://<도메인>/admin` 에서 [인제스트_가이드.md](../../docs/인제스트_가이드.md) 절차로 업로드한다.
- **표지 smoke test**: 관리자 페이지에서 JPEG·PNG·WebP 중 1개를 업로드해 S3 PUT이 성공하고,
  도서 응답의 `coverImageUrl`을 인증 없이 열 수 있는지 확인한다. CORS 실패 시 CloudFormation의
  `AdminOrigin`이 브라우저 주소의 origin과 정확히 같은지 확인한다.
- **수동 배포(폴백)**: 현재 운영 버전과 대상 커밋을 확인한 후, 대상 SHA를 `DEPLOYED_COMMIT_SHA` 빌드 인자와
  이미지 태그에 모두 지정해 `linux/arm64` 이미지를 발행한다. 운영 러너와 동일한 환경 변수로 공용 배포
  스크립트에 이미지 주소와 SHA를 전달한다.
- **로그 확인**: 현재 upstream이 8080이면 `docker logs -f yeobaek-app-blue`, 8081이면 `docker logs -f yeobaek-app-green`.
- **PostHog 사용자 API 이벤트 확인**: 내부 테스트 계정으로 사용자 API를 호출한 뒤 US Cloud 프로젝트의 Activity에서 `backend_` 접두사 이벤트를 확인한다. 이벤트 목록과 속성은 [`README.md`](../README.md#posthog-백엔드-사용자-api-이벤트)를 따른다.

## 주의

- MySQL 데이터는 도커 볼륨 `mysql-data`에 있다. `docker compose down -v`와 MySQL 볼륨 삭제는
  **데이터를 삭제**하므로 일반 배포에서 금지한다.
- CloudFormation 스택과 버킷은 `Retain` 정책이라 스택 삭제만으로 표지 객체가 제거되지 않는다.
  버킷·객체를 실제로 지우는 작업은 별도 검토 없이 수행하지 않는다.
