# 배포 가이드

> M8 배포 구성 결정 (2026-08-06): EC2 1대 + 같은 인스턴스의 Docker MySQL ·
> GitHub Actions → Docker Hub → EC2 pull 방식 · `ddl-auto=update`(데모 한정) · nginx + Let's Encrypt HTTPS

## 구성 개요

```
GitHub (main push, 서버 빌드·실행 입력 변경)
  ├─ build 잡 (GitHub 호스티드): gradle build(게이트) → 이미지 빌드 → Docker Hub 푸시
  └─ deploy 잡 (EC2 셀프 호스티드 러너, 라벨 ec2-prod): docker compose pull && up -d
       └─ EC2:
            ├─ yeobaek-app   (Spring Boot, 127.0.0.1:8080)
            ├─ yeobaek-mysql (볼륨 mysql-data에 데이터 영속)
            ├─ nginx (호스트 설치) ── HTTPS(443) → 127.0.0.1:8080
            └─ EC2 instance role ── Presigned PUT 서명 권한
                 └─ S3 book-covers/* (익명 읽기, 서명된 쓰기만 허용)
```

자동 배포는 `backend/src/main/**`, Gradle 빌드·런타임 설정(`build.gradle*`, `settings.gradle*`,
`gradle.properties`, `gradle/**`), Gradle 래퍼 실행 파일(`gradlew`), `backend/Dockerfile`, 배포
워크플로가 변경될 때 실행한다. `backend/src/test/**` 변경은 배포물에 영향을 주지 않고 OpenAPI
스펙도 springdoc이 런타임에 생성하므로 자동 배포 경로에서 제외한다. 일반 문서, 로컬 개발 설정 등
배포 산출물과 무관한 변경도 실행하지 않는다.

보안 그룹이 SSH 인바운드를 특정 IP로 제한하고 있어 Actions에서 SSH 접속이 불가하다.
대신 EC2에 상주하는 셀프 호스티드 러너가 아웃바운드 HTTPS로 GitHub에서 배포 잡을 받아 실행한다
(보안 그룹 인바운드 규칙 추가 불필요).

- 관련 파일: `backend/Dockerfile`, `backend/deploy/docker-compose.prod.yml`, `backend/src/main/resources/application-prod.properties`, `.github/workflows/backend-deploy.yml`

## 1. GitHub 시크릿 (저장소 Settings → Secrets and variables → Actions)

| 시크릿 | 값 |
|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub 계정명 (이미지: `<계정>/yeobaek-backend`) |
| `DOCKERHUB_TOKEN` | Docker Hub Access Token (Read & Write) |

SSH 관련 시크릿(`EC2_HOST`, `EC2_USER`, `EC2_SSH_KEY`)은 셀프 호스티드 러너 전환으로 더 이상 사용하지 않는다.

## 2. EC2 최초 세팅 (1회)

```bash
# Docker 설치 (Ubuntu 기준)
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER   # 재로그인 필요

# 배포 디렉터리
mkdir -p ~/yeobaek
# 로컬에서 compose 파일 복사
scp -i <키> backend/deploy/docker-compose.prod.yml <user>@<host>:~/yeobaek/docker-compose.yml
```

`~/yeobaek/.env` 작성 (compose가 읽는다. 값은 팀 비밀 채널로 공유):

```
DOCKERHUB_USERNAME=<계정>
DB_PASSWORD=<강한 비밀번호>
ADMIN_TOKEN=<강한 토큰>
BOOK_COVER_S3_BUCKET=<CloudFormation CoverBucketName 출력>
BOOK_COVER_S3_REGION=<CloudFormation CoverBucketRegion 출력>
BOOK_COVER_PUBLIC_BASE_URL=<CloudFormation CoverPublicBaseUrl 출력>
```

최초 기동(이후는 CI가 수행):

```bash
cd ~/yeobaek && docker compose pull && docker compose up -d
curl http://127.0.0.1:8080/api/books -H 'X-Member-Id: 1'   # 400(MEMBER_NOT_FOUND)이면 정상 기동
```

### 셀프 호스티드 러너 등록 (배포 잡 실행용, 1회)

1. 저장소 **Settings → Actions → Runners → New self-hosted runner** → Linux x64를 선택하고,
   안내되는 다운로드·`./config.sh` 명령을 EC2에서 그대로 실행한다.
   `config.sh`가 라벨을 물으면 **`ec2-prod`를 추가**한다 (배포 잡의 `runs-on: [self-hosted, ec2-prod]`와 매칭).
2. systemd 서비스로 등록해 재부팅에도 유지되게 한다:
   ```bash
   sudo ./svc.sh install && sudo ./svc.sh start
   ```
3. 러너 실행 유저는 docker 그룹에 속해 있어야 한다 (위 Docker 설치 단계의 `usermod` 적용 후 서비스 재시작).
4. public 저장소이므로 **Settings → Actions → General**에서 "Require approval for all outside collaborators"를
   켜 두고, `pull_request` 트리거 워크플로에는 셀프 호스티드 라벨을 사용하지 않는다.

### 도서 표지 S3 생성 (1회)

[`deploy/book-cover-s3.yml`](../deploy/book-cover-s3.yml)은 다음 리소스를 만든다.

- ACL을 끄고 암호화·버전 관리를 활성화한 S3 버킷
- `book-covers/*`에 한정한 익명 `GetObject` 정책
- 관리자 웹 origin의 `PUT`만 허용하는 CORS
- 기존 EC2 instance role에 `book-covers/*` `PutObject`만 부여하는 인라인 정책

AWS CLI가 배포 대상 계정·리전에 로그인된 환경에서 실행한다.

```bash
aws cloudformation deploy \
  --stack-name yeobaek-book-covers \
  --template-file backend/deploy/book-cover-s3.yml \
  --parameter-overrides \
    AdminOrigin=https://<서비스-도메인> \
    AppInstanceRoleName=<EC2-instance-role-name> \
  --capabilities CAPABILITY_IAM

aws cloudformation describe-stacks \
  --stack-name yeobaek-book-covers \
  --query 'Stacks[0].Outputs'
```

출력된 `CoverBucketName`, `CoverBucketRegion`, `CoverPublicBaseUrl`을 위 `.env`에 기록하고 앱을
재기동한다. access key는 저장하지 않는다. 컨테이너가 EC2 instance metadata를 통해 role
자격증명을 읽을 수 있어야 한다.

Docker bridge 안의 AWS SDK가 EC2 role 자격증명을 IMDSv2로 읽으려면 metadata 응답이 컨테이너까지
한 홉 더 이동할 수 있어야 한다. AWS가 컨테이너 환경에 권장하는 것처럼 기존 인스턴스의 metadata
응답 hop limit을 2로 설정하고 IMDSv2만 허용한다.

```bash
aws ec2 modify-instance-metadata-options \
  --instance-id <EC2-instance-id> \
  --http-endpoint enabled \
  --http-tokens required \
  --http-put-response-hop-limit 2
```

참고: [AWS EC2 instance metadata 접근 고려사항](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html)

계정 또는 AWS Organizations 수준에서 S3 Block Public Access를 강제하고 있으면 버킷 수준 설정보다
우선한다. 이 경우 공개 읽기 정책을 적용할 수 있도록 해당 계정 정책을 먼저 확인해야 한다.
`book-covers/*`에는 공개해도 되는 표지 이외의 객체를 저장하지 않는다.

## 3. nginx + Let's Encrypt (호스트 설치, 1회)

도메인의 A 레코드를 EC2 퍼블릭 IP로 연결해 둔 상태에서:

```bash
sudo apt update && sudo apt install -y nginx certbot python3-certbot-nginx
sudo tee /etc/nginx/sites-available/yeobaek <<'EOF'
server {
    listen 80;
    server_name <도메인>;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/yeobaek /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

# HTTPS 발급 (443 서버 블록·리다이렉트를 certbot이 자동 구성, 갱신 타이머 자동 등록)
sudo certbot --nginx -d <도메인>
```

## 4. 배포 이후

- **호스트 공유**: 발급된 `https://<도메인>`을 안드로이드 팀과 공유하고 `API.md` 0장의 Base path 항목을 갱신한다.
- **실제 책 투입**: `https://<도메인>/admin` 에서 [인제스트_가이드.md](../../docs/인제스트_가이드.md) 절차로 업로드한다.
- **표지 smoke test**: 관리자 페이지에서 JPEG·PNG·WebP 중 1개를 업로드해 S3 PUT이 성공하고,
  도서 응답의 `coverImageUrl`을 인증 없이 열 수 있는지 확인한다. CORS 실패 시 CloudFormation의
  `AdminOrigin`이 브라우저 주소의 origin과 정확히 같은지 확인한다.
- **수동 배포(폴백)**: CI가 죽었을 때 — 로컬에서 `./gradlew bootJar` 후 `docker buildx build --platform linux/arm64 -t <계정>/yeobaek-backend:latest --push backend`, EC2에서 `docker compose pull && up -d`. **EC2가 Graviton(arm64)이므로 반드시 arm64로 빌드해야 한다** (amd64 이미지는 exec format error로 기동 실패).
- **로그 확인**: `docker logs -f yeobaek-app`

## 주의

- `ddl-auto=update`는 데모 한정 결정이다. 컬럼 삭제·타입 변경은 반영되지 않으며, 데이터 안전성이 중요해지는 시점에 `none` + 수동 DDL로 전환을 재논의한다.
- MySQL 데이터는 도커 볼륨 `mysql-data`에 있다. `docker compose down -v`는 **데이터를 삭제**하므로 금지.
- 개발용 시드(`DevDataSeeder`)는 `local` 프로파일 한정이라 운영에 투입되지 않는다.
- CloudFormation 스택과 버킷은 `Retain` 정책이라 스택 삭제만으로 표지 객체가 제거되지 않는다.
  버킷·객체를 실제로 지우는 작업은 별도 검토 없이 수행하지 않는다.
