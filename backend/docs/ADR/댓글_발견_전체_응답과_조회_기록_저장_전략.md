# ADR: 댓글 발견의 전체 응답과 조회 기록 저장 전략

## 상태

확정 (2026-09-07 개발자 작업 대화). PR #149의 댓글 발견 정책을 구현하면서 아래 결정을 추가했다.
이 문서의 결정 근거 원문은 개발자 답변을 보존한다. 구현 설명은 해당 결정을 코드와 연결하는 설명이다.

## 맥락

[PR #149](https://github.com/woowacourse-teams/2026-yeobaek/pull/149)는 현재 진도 안쪽의 새 댓글 수,
댓글이 달린 문장 목록, 상세 조회와 확인 상태 전환을 정의했다. 새 댓글을 우선 배치하는 UX는
유지한다. 회원별 상태는 `NEW`와 `VIEWED`이며 목록 조회는 상태를 변경하지 않는다.

초안의 커서 계약은 문장 목록·순서·집계·가림 상태를 탐색 시작 시점으로 고정했다. 이를 구현하려면
탐색별 스냅샷 저장 위치와 수명, 정리 방식을 결정해야 했다. 개발자는 현재 4GB 메모리 서버를 사용하며,
모임당 문장 데이터가 당장은 수천 개 미만일 것으로 예상했다. 이 규모와 동시 최초 조회가 드물다는
판단은 실측 결과가 아니라 개발자의 현재 가정이다.

## 1. 문장 목록은 전체 응답한다

### 검토한 선택지

- 커서와 MySQL 스냅샷: 탐색별 결과를 보존할 수 있지만 DB 저장·정리 작업이 추가된다.
- 커서와 서버 메모리 스냅샷: DB 저장을 줄이지만 메모리 상한과 만료 관리가 필요하며 앱 재시작에 영향을 받는다.
- Redis 스냅샷: 공유·TTL 기능을 사용할 수 있지만 별도 저장소 운영과 메모리 예산, 유실 처리가 추가된다.
- 전체 응답: 한 번의 요청에서 목록 전체를 반환하며, 클라이언트가 받은 결과를 탐색 동안 유지한다.

### 결정

`GET /api/clubs/{clubId}/commented-sentences?currentPassageId={passageId}`는 보이는 댓글이 있는
문장을 모두 반환한다. `cursor`, `size`, `nextCursor`와 서버 스냅샷·만료 처리를 도입하지 않는다.
`새 댓글 → 미래 문장 → 확인함` 및 그룹 내 최근 댓글 시각·문장 ID 내림차순 정렬은 유지한다.

클라이언트는 받은 목록을 탐색 동안 유지한다. 그동안 차단·작성자 계정 삭제·댓글 변경·상세 조회가
발생해도 이미 받은 목록은 갱신하지 않아도 된다. 새 목록 요청과 댓글 상세 요청에는 현재 가시성·인가를
적용한다. 계정 삭제 시 서버 데이터 삭제 계약은 유지하며, 클라이언트에 이미 전달된 과거 집계만 예외다.

### 개발자 결정 근거 원문

> 당장은 한 모임에 문장 데이터가 수천개 미만일 것이라 예상된다
>
> 당장은 구현이 간단한 전체 응답 방식을 선택하고, 네트워크 비용이 문제가 된다면 하위호환을 유지한 채로 페이지네이션이 적용된 새 API를 제공한다.

이 결정은 앞선 서버 스냅샷 비용 감수 결정을 대체한다. 새 댓글 우선 UX의 근거는 유지한다.

> 새 댓글을 위에 배치하는 현재 UX가 중요하니, 탐색별 스냅샷 비용을 감수한다.

이미 전달한 목록에 차단·삭제를 즉시 반영하지 않는 근거는 다음과 같다.

> 차단/삭제를 즉각 반영해야 할 정도로 민감한 정보가 아니다. 스냅샷 동안에는 과거 집계를 보여주더라도 무방하다.

### 결과와 재검토 조건

응답 크기는 댓글이 달린 서로 다른 문장 수와 문장 길이에 따라 증가한다. 전체 집계·정렬과 응답 생성
비용은 남는다. 네트워크 비용이 문제가 되면 기존 API를 유지하고 페이지네이션을 적용한 새 API를 제공한다.
현재 API에서 조용히 목록을 자르거나 임의 상한을 추가하지 않는다.

## 2. VIEWED 기록만 저장한다

### 검토한 선택지

- 확인한 회원·댓글 조합만 저장하고 기록이 없으면 `NEW`로 판단한다.
- 회원·댓글 조합마다 `NEW`와 `VIEWED` 상태를 모두 저장한다.

### 결정

회원과 댓글을 참조하는 `comment_views` 기록은 확인 사실만 표현한다. 기록이 하나라도 있으면
`VIEWED`, 없으면 `NEW`다. 본인 댓글 작성 시 확인 기록을 함께 저장한다. 댓글 상세 조회에서는
응답에 포함되는 댓글 중 아직 확인하지 않은 댓글의 기록을 응답 생성과 같은 트랜잭션에서 저장한다.
기존 GET 상세 API에도 같은 전환을 적용하고 deprecated 호환 API로 유지한다.

기존 댓글은 본인 작성 여부와 관계없이 기록이 없으면 `NEW`다. 신규 가입 시 초기화하지 않으며,
모임 탈퇴 시에는 확인 기록을 유지한다. 회원 계정 또는 댓글 삭제 시 연결된 기록은 함께 삭제한다.

### 개발자 결정 근거 원문

> 별도의 초기화 로직이 필요 없고, 레코드가 필요한 만큼만 생성되는 이점이 있음.
>
> B 방식을 선택한다면 확장을 고려하는건데, B 선택지가 유용할 확장 가능성이 낮으며, 필요할 때 확장하더라도 비용이 크지 않다 판단.

위 원문의 B 방식은 회원·댓글별 `NEW/VIEWED` 행을 모두 생성하는 선택지다.

### 결과와 재검토 조건

확인한 조합만큼 기록과 인덱스가 증가한다. 안 읽은 댓글 집계는 확인 기록이 없는 댓글을 대상으로 한다.
새로운 상태나 확인 이력이 필요해지면 저장 모델을 다시 검토한다.

## 3. 사전 중복 검사만 수행하고 동시 중복은 허용한다

### 검토한 선택지

- MySQL UPSERT와 유니크 제약으로 중복을 방지한다.
- 관련 요청을 잠금으로 직렬화한다.
- 유니크 제약 충돌 후 트랜잭션을 재시도한다.
- 사전 존재 검사로 일반적인 재조회 중복을 막고 동시 최초 조회에서 생기는 중복은 허용한다.

### 결정

확인 기록을 먼저 조회하고 없는 조합만 저장한다. 회원·댓글 조합의 유니크 제약,
명시적 잠금, UPSERT 또는 중복 충돌 재시도를 추가하지 않는다.
동시 요청이 모두 기록 부재를 관찰하면 동일 조합의 행이 여러 개 저장될 수 있다.

조회·집계는 확인 기록의 존재 여부로 판단하므로 중복 행이 댓글 수·안 읽은 댓글 수·정렬·가림 상태를
바꾸지 않게 한다. 댓글을 조회할 때마다 무조건 기록을 추가하는 방식은 사용하지 않는다.

### 개발자 결정 근거 원문

> 중복 레코드가 생긴다고 해서 데이터 무결성 문제가 발생하는 것도 아니며, "한 사용자가 같은 댓글을 동시에 최초 조회한다"라는 동시성 상황이 극히 드물게 발생할거라 추측한다.
>
> 중복 처리 검증 로직은 두되, 동시성까지는 고려하지 않는다.
> 이로 인해 중복 데이터가 많이 쌓이는지를 추후에 측정하여, DB 단에서도 중복 레코드를 막을지 결정한다.

### 결과와 재검토 조건

중복 데이터의 저장·인덱스·삭제 비용은 감수한다. 조회 코드는 단건 또는 유일한 관계를 가정하지 않는다.
물리적 행 수와 서로 다른 회원·댓글 조합 수의 차이로 중복 누적을 측정할 수 있다. 중복이 많이 쌓이면
DB 제약 도입을 재검토한다.
