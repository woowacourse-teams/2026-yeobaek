# ADR: 도서 표지를 S3 공개 객체로 제공

## 상태

확정. 최초 기록 2026-08-26, 논의 근거 보강 2026-08-31 (개발자).

관련 이슈: [P-123](https://linear.app/yeobaek/issue/P-123)

관련 계약: 상위 저장소의 [`API.md`](../../../docs/API.md)

## 해결해야 할 문제

도서 정보를 보여줄 때 표지도 함께 제공해야 한다. 서버는 관리자가 올린 표지 이미지를
안전하게 보관하고, 도서 정보를 포함하는 API에서 클라이언트가 렌더링할 수 있는 URL을
응답해야 한다.

번역 도서 데이터와 표지는 여백의 자산이다. 따라서 다음 기준을 같이 고려해 저장소와 제공
방식을 결정해야 한다.

- 내구성과 가용성
- 저장 용량과 요청·전송량에 따른 비용
- 공개·비공개 접근 제어
- 백업, 모니터링, 수평 확장을 포함한 운영 부담
- 현재 AWS 인프라와의 결합도
- 도입 학습 비용과 향후 마이그레이션 비용
- DB 레코드와 이미지 객체 사이의 정합성

## 결정

### S3에 이미지를 저장한다

표지 이미지는 AWS S3에 저장한다. 도서 본문과 메타데이터를 담는 DB에는 이미지 바이트를
저장하지 않는다.

객체 스토리지는 EC2 파일 시스템과 독립적이므로 인스턴스 교체·배포에 영향을 받지 않고,
서버를 여러 인스턴스로 확장해도 같은 이미지를 제공할 수 있다. S3는 이미 사용 중인 AWS
생태계와 IAM을 그대로 활용할 수 있고 우아한테크코스에서 인프라 비용을 지원한다. 다른
플랫폼의 계정·자격 증명·권한 체계를 추가로 운영할 만큼 더 큰 이점이 현재는 없다.

정확한 비용 비교는 저장량, 요청 수, 인터넷 전송량이 쌓이기 전에는 어렵다. 현재 가정만으로 다른
서비스로 복잡도를 늘리지 않고, 운영 데이터가 쌓이면 비용을 다시 비교한다.

### DB에는 전체 URL이 아닌 객체 키만 저장한다

- `books.cover_image_key`에 S3 객체 키만 저장한다.
- 응답 URL은 애플리케이션 설정의 공개 base URL과 객체 키를 조합해 만든다.
- 객체 키는 원본 파일명 중복으로 인한 덮어쓰기를 방지하기 위해 UUID를 사용한다.
- 표지를 교체할 때는 같은 키를 덮어쓰지 않고 새 키를 발급한다.

전체 URL을 저장하면 DB 값을 그대로 응답할 수 있지만, 버킷·리전이 바뀌거나 CloudFront를 붙일 때
기존 레코드를 모두 바꿔야 한다. 하나의 버킷만 사용할 가능성이 높고 URL 조합 로직도 복잡하지
않으므로, 제공 경로를 변경할 수 있도록 키만 저장한다.

### 표지는 공개 객체로 제공한다

표지는 비회원도 조회할 수 있는 공개 데이터이다. 권한이 필요한 데이터가 아니므로 Presigned GET URL로
불필요하게 보호하지 않고, S3 공개 URL로 제공한다. 이로써 URL 발급과 만료 갱신 로직 없이
브라우저·모바일 이미지 캐시를 활용한다.

외부 핫링크와 대량 수집을 URL 자체로 막을 수 없다는 점은 수용한다. 현재는 이 위험보다 공개 데이터에
맞는 단순한 접근 모델과 캐시 이점의 우선순위가 높다. 문제가 실제 운영 비용이나 가용성에 영향을
줄 때 CloudFront, WAF, 요청 제한을 다시 검토한다.

공개 읽기와 달리 쓰기는 관리자만 할 수 있다. 버킷의 익명 쓰기·삭제는 허용하지 않고,
애플리케이션이 관리자에게 Presigned PUT URL을 발급한다.

### 클라이언트가 S3 업로드를 마친 뒤 도서를 생성한다

1. 관리자 클라이언트가 서버에 Presigned PUT URL을 요청한다.
2. 서버가 UUID 기반 객체 키와 Presigned PUT URL을 발급한다.
3. 클라이언트가 S3에 표지를 직접 업로드한다.
4. 업로드가 성공한 뒤에만 객체 키를 포함해 도서 생성 API를 호출한다.

이 순서는 표지가 없는 임시 도서를 먼저 만들지 않으면서, 관리자에게는 하나의 도서 등록 흐름으로
보인다. 다만 S3 업로드 후 DB의 도서 생성이 실패하면 어떤 도서와도 연결되지 않은 고아 객체가
남는다. DB와 S3를 하나의 트랜잭션으로 묶지 않고 이 가능성을 수용한다. 고아 객체 정리는 실제
저장량과 비용이 문제가 될 때 정책과 자동화를 결정한다.

표지 없음을 허용하는 현재 도메인 계약에 따라 `cover_image_key`는 nullable이다. 그러나 nullable은
“도서를 먼저 만든 뒤 표지를 업로드”하기 위한 중간 상태로 도입한 것이 아니다.

### 업로드·저장·응답 계약

- 업로드 URL은 `POST /api/admin/book-covers/upload-url`로 발급하며 10분간 유효하다.
- JPEG, PNG, WebP만 허용하고 용량은 1바이트 이상 5 MiB 이하로 제한한다. 확장자는
  원본 파일명이 아니라 서버가 검증한 MIME으로 결정한다.
- 객체 키 형식은 `${storage.s3.prefix}/book-covers/{소문자 UUID}.(jpg|png|webp)`다.
- prefix는 `BOOK_COVER_S3_PREFIX`로 변경할 수 있고 기본값은 `yeobaek`이다. DB 키 길이 제한을
  지키기 위해 슬래시로 시작하거나 끝나지 않는 1~26자 경로만 허용한다.
- 불변 키와 장기 캐시를 사용하기 위해 업로드 객체에
  `Cache-Control: public,max-age=31536000,immutable`을 저장한다.
- Presigned URL 응답은 S3 PUT 시 반드시 보낼 `Content-Type`, `Cache-Control` 등의 헤더를
  함께 제공한다.
- 서버는 제출된 키의 형식만 검증하고 S3 `HeadObject`는 호출하지 않는다. S3 지연과 장애를
  DB 트랜잭션에 끌어들이지 않는다.
- 표지를 교체·제거하거나 도서를 삭제해도 요청 안에서 S3 객체를 삭제하지 않는다.
- 삭제된 도서의 표지 교체·제거는 `BOOK_NOT_AVAILABLE`로 거부한다.
- 도서 정보를 포함하는 응답에는 nullable `coverImageUrl`을 넣고, 내부 객체 키는 일반 사용자
  응답에 노출하지 않는다.

### 애플리케이션과 인프라 계약

- AWS SDK for Java v2의 BOM과 `s3` 모듈을 사용한다.
- `S3Presigner`는 애플리케이션 단위 빈으로 재사용하고 종료 시 닫는다.
- 운영 자격 증명은 EC2 instance profile의 기본 자격 증명 체인을 사용하고 access key를
  설정 파일에 저장하지 않는다.
- bucket, region, public base URL, prefix는 애플리케이션 설정으로 주입한다.
- 버킷은 ACL을 사용하지 않고 저장 암호화와 버전 관리를 활성화한다.
- S3 CORS는 관리자 웹 origin의 `PUT`과 Presigned PUT에 필요한 헤더만 허용한다.

### CDN은 지금 도입하지 않는다

CloudFront를 붙이면 사용자와 가까운 edge에서 이미지를 제공하고 S3 요청과 인터넷 전송 부하를
줄일 수 있다. 반면 현재는 실제 트래픽과 지연 실측이 없어 CDN 도입 가치가 설정·비용
복잡도보다 큰지 판단할 수 없다. 운영 데이터가 없는 상태에서 미리 도입하지 않고 백로그로
남긴다. 나중에 CloudFront를 붙여도 DB는 변경하지 않고 공개 base URL만 바꿀 수 있다.

### 자동화 테스트는 AWS와 분리하고 실제 연동은 QA에서 검증한다

- S3 연동 서비스의 단위 테스트는 Mockito로 AWS SDK 경계를 대역한다.
- 로컬과 일반 CI의 자동화 테스트는 실제 AWS 자격 증명과 버킷에 의존하지 않는다.
- 운영 인프라에 반영하기 전 QA에서 실제 S3 업로드·공개 조회·CORS를 smoke test한다.

초기에는 `develop`/`main` push마다 실제 S3 테스트를 실행하려 했다. 이 방식은 연동 문제를 배포
전에 자동으로 발견할 수 있다.
그러나 CI에 AWS 자격 증명과 권한을 제공해야 하고, 네트워크나 AWS의 일시 장애가 배포 게이트를
깨뜨릴 수 있다. 서비스가 성숙하지 않은 현재는 이 운영 부담보다 자동 검증의 편익이 크다고 보지
않는다. 코치 피드백을 반영해 최종적으로 QA 검증을 선택했다. S3 연동 스펙은 초기에 한 번 QA하고,
이후 확장할 때마다 같은 실제 흐름을 확인한다.

직접 만든 Fake는 가벼지만 S3 스펙과 버킷·IAM 정책을 검증하지 못한다. LocalStack이나
MinIO는 AWS SDK를 사용하는 통합 테스트를 자동화할 수 있지만 추가 의존성·설정·운영 비용이
발생한다. 현재 범위에서는 둘 다 도입하지 않는다.

## 검토한 선택지

### 이미지 저장 방식

| 선택지 | 이점 | 제외한 이유 |
| --- | --- | --- |
| S3·BaaS·미디어 전문 CDN | 내구성이 높고 인스턴스와 독립적으로 확장할 수 있다. | 채택. DB와 저장소 정합성은 별도로 관리한다. |
| Imgur API | API 호출로 HTTPS URL을 받을 수 있어 구현이 단순하다. | 서비스 자산을 외부 미디어 사이트의 정책과 지속 가능성에 의존한다. |
| EC2 파일 시스템 | 구현과 URL 제공이 단순하다. | 인스턴스 교체·배포 시 손실 위험이 크고 수평 확장과 접근 제어가 어렵다. |
| DB BLOB | 도서 레코드와 하나의 DB 트랜잭션으로 관리할 수 있다. | DB 크기와 조회·백업 부담을 늘리고 URL 제공과 캐시를 서버가 직접 구현해야 한다. |

### 객체 스토리지 제공자

| 선택지 | 장점 | 단점·보류 이유 |
| --- | --- | --- |
| AWS S3 | 기존 AWS·IAM을 활용하고 지원받는 인프라 비용을 사용할 수 있다. | 채택. 저장량·요청·전송량에 따라 과금되고 초기 IAM·버킷 설정 학습이 필요하다. |
| GCP Cloud Storage | 저장 단가와 Google 네트워크, 가용성 선택지를 검토할 수 있다. | AWS와 다른 프로젝트·결제·IAM을 관리하고 크로스 클라우드 전송 비용을 고려해야 한다. |
| Cloudflare R2 | 인터넷 전송 비용을 줄일 수 있다. | 다른 계정과 자격 증명을 추가로 운영해야 한다. |
| NCP Object Storage | S3 API와 호환되고 한국어 안내를 활용할 수 있다. | 사용량에 따라 바로 과금되고 기존 AWS 생태계와 별도로 운영해야 한다. |
| Firebase Storage | 초기 설정과 프론트엔드 직접 업로드 구성이 쉽다. | 현재는 관리자 표지 업로드만 필요해 BaaS 이점이 작고, 비용과 플랫폼 결합도가 높아진다. |
| Google Drive | 팀 내부 파일 공유에 적합하다. | 상용 서비스의 이미지 제공 인프라로는 API 호출 제한과 제공 성능이 적합하지 않다. |

### 도서 생성과 이미지 업로드 순서

| 선택지 | 트레이드오프 |
| --- | --- |
| 서버가 multipart 요청으로 도서와 표지를 함께 받기 | 클라이언트 API는 하나지만 서버가 파일 전송 부하를 감당하고 S3·DB 실패 정책을 같이 처리해야 한다. |
| S3 업로드 → 도서 생성 | 표지를 없는 중간 도서를 만들지 않지만 도서 생성 실패 시 S3 고아 객체가 남는다. 채택한다. |
| 도서 생성 → S3 업로드 → 표지 연결 | S3 고아 객체는 줄지만 표지가 없는 중간 도서 상태와 추가 API 호출이 필요하다. |

## 영향

### 긍정적 영향

- 서버 인스턴스의 배포·교체·수평 확장과 이미지 저장 수명을 분리한다.
- DB가 이미지 바이트 저장과 전송을 담당하지 않는다.
- 공개 URL과 불변 키로 클라이언트 캐시를 단순하게 활용한다.
- 향후 CloudFront를 도입해도 DB 레코드를 마이그레이션하지 않고 base URL만 변경할 수 있다.

### 부정적 영향과 수용한 위험

- DB와 S3는 하나의 트랜잭션이 아니므로 완전한 원자성을 보장하지 않는다.
- S3 업로드 후 도서 생성·표지 교체가 실패하면 고아 객체가 남을 수 있다.
- 공개 표지는 외부 핫링크와 대량 수집에 노출된다.
- S3 버킷, IAM, CORS, 암호화, 버전 관리와 비용 모니터링이 새로운 운영 책임이 된다.
- 자동화 테스트는 버킷·IAM·CORS를 포함한 실제 AWS 구성을 검증하지 않으므로 QA 확인을 놓치면
  구성 문제를 늦게 발견할 수 있다.

## 한계와 후속 작업

- 고아 객체 탐지·정리 정책과 자동화는 백로그다.
- CloudFront 도입은 트래픽, 비용, 지연 실측 데이터가 쌓인 뒤 재검토한다.
- 핫링크·대량 다운로드가 비용이나 가용성 문제를 만들면 CDN, WAF, 요청 제한을 검토한다.
- 이미지 리사이징, 썸네일 파생본, 바이러스 검사, 실제 바이트 signature 검사는 현재 범위에 포함하지 않는다.
- 실제 S3 연동 자동화는 QA 누락이 반복되거나 연동 변경이 잦아질 때 다시 검토한다.

## 향후 재검토 신호

- S3 전송 비용이나 원거리 지연이 유의미해진다.
- 외부 핫링크나 대량 수집이 비용·가용성 문제를 만든다.
- 표지를 비공개로 다뤄야 하는 권리·계약 요구가 생긴다.
- 고아 객체의 저장량이 운영상 무시할 수 없는 수준이 된다.
- 원본 외에 여러 해상도·포맷 파생본을 제공해야 한다.
- QA에서 버킷·IAM·CORS 구성 문제를 반복해 놓친다.
