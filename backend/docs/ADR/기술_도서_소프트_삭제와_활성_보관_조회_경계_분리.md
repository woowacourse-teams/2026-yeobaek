# ADR: 도서 소프트 삭제와 활성·보관 조회 경계 분리

## 상태

확정. 결정 근거 기록 2026-08-24 (개발자).

관련 계약: 상위 저장소의 [`PRD.md`](../../../docs/PRD.md),
[`API.md`](../../../docs/API.md)

## 맥락

관리자가 더 이상 제공할 수 없는 도서를 삭제하더라도, 해당 도서를 읽던 모임과 사용자가
작성한 댓글을 함께 제거하면 안 된다. 반대로 삭제된 도서의 본문과 그 본문을 이용하는 기능은
사용자에게 계속 제공할 수 없다.

현재 `Book`에는 삭제 상태가 없고, 사용자 조회와 관리자 조회가 같은 `BookRepository`의
무제한 `findById`·`findAll`을 사용한다. 삭제된 도서를 보존하면서 사용자 경로에서만 확실히
제외하려면 도서 생명주기와 조회 경계를 함께 정의해야 한다.

## 결정

### 데이터 보존과 상태

- `books` 행에 문자열 enum `status`를 추가한다.
- 새 도서는 `status=ACTIVE`로 생성한다.
- 기존 행이 있는 `ddl-auto=update` 환경에서도 안전하게 열을 추가할 수 있도록 DB 기본값도
  `ACTIVE`로 선언한다.
- 관리자 삭제는 `status=DELETED`로 바꾸는 소프트 삭제다.
- 도서, 작가-도서 매핑, 목차, 본문, 모임, 모임 회원, 진도, 댓글은 삭제하지 않는다.
- 복구 기능과 삭제 시각·사유 기록은 이번 범위에 포함하지 않는다.

### 관리자 API

- `DELETE /api/admin/books/{bookId}`를 제공한다.
- 성공은 `204 No Content`다.
- 물리적으로 존재하지 않는 도서는 `BOOK_NOT_FOUND`, 이미 삭제된 도서는
  `BOOK_NOT_AVAILABLE`로 실패한다.
- 관리자 페이지는 삭제 전 도서명이 포함된 확인 창을 한 번 표시한다.
- 삭제된 도서는 관리자 작품 목록에 남기고 삭제 상태를 표시하며, 삭제 버튼은 비활성화한다.

### 사용자 API 상태

- 모임 응답의 도서 객체에 `status`를 추가한다.
- 상태 값은 `ACTIVE`, `DELETED`다.
- 일반 도서 목록·검색은 활성 도서만 반환한다.
- 삭제된 도서의 직접 상세, 본문, 진도, 댓글 조회·작성·수정·삭제는
  `BOOK_NOT_AVAILABLE`로 실패한다.
- 삭제된 도서를 읽던 기존 모임은 목록·상세에서 유지하며 `status=DELETED`를 반환한다.
- 마지막 읽기 기록도 삭제된 도서를 건너뛰지 않고 `status=DELETED`와 함께 유지한다.
- 삭제된 도서의 모임에는 새로 참여할 수 없으며, 삭제된 도서로 새 모임을 만들 수 없다.

### 활성·보관 조회 경계

- 사용자용 활성 도서 조회와 관리자·보관용 전체 도서 조회를 repository 계층에서 분리한다.
- 사용자 비즈니스 계층에는 활성 도서 조회 계약만 제공한다.
- 관리자 삭제, 관리자 작품 목록, 관계 보존 확인에는 삭제된 도서를 포함하는 보관 조회
  계약을 사용한다.
- 원시 Spring Data JPA 저장소는 repository 패키지 밖에서 직접 사용할 수 없게 숨긴다.
- 삭제된 도서와 서지 정보가 같은 도서는 새 ID로 다시 업로드할 수 있다. 기존 모임과 댓글은
  삭제된 이전 도서에 계속 연결된다.

## 검토한 선택지

### 소프트 삭제 상태

- `deleted` boolean
- nullable `deletedAt`
- `BookStatus` enum을 DB에 저장

### 관리자 삭제 계약

- `DELETE /api/admin/books/{bookId}`
- `PATCH /api/admin/books/{bookId}`와 `{ "deleted": true }`
- `POST /api/admin/books/{bookId}/deletion`

### 사용자 상태 계약

- `available` boolean
- `status` enum
- 모임 응답별 `readable` boolean

### 조회 경계

- 하나의 repository에서 활성 조건과 도메인 상태 검사를 명시
- Hibernate 전역 필터
- 사용자용 활성 조회와 관리자용 보관 조회 경계 분리

## 개발자 결정 근거 원문

아래 내용은 결정 과정에서 기록된 개발자 답변을 수정하지 않고 인용한 것이다.

### 모임과 사용자 데이터 보존

> **결정: 모임이 바로 삭제되는게 UX에 치명적**
>
> - 안내 없이 모임이 삭제되면 사용자 입장에서 혼란스럽다.
> - 더 이상 이용할 수 없는 상태가 됐음을 안내해야 한다.

> **결정: 사용자의 자산을 동의 없이 제거하면 서비스 신뢰도에 큰 영향을 준다.**
>
> - 열심히 의논한 내용이 사용자 동의도 없이 없어지는 게 말이 안 된다?
> - 언제든지 타의에 의해 자신의 감상이 사라질 수 있으면, 서비스의 핵심 경험에 대한 사용자의 신뢰가 유지되지 않는다.

### `deleted` boolean

> 현재 상태로는 삭제 시점이나 삭제 사유 등의 추가 정보를 저장할 필요가 없으며, 이후에 필요해지면 확장하기 쉬운 요소라고 생각하므로, 우선은 단일 boolean으로 처리.

이 선택은 이후 도메인과 API의 상태 구조를 통일하기로 하면서 아래 결정으로 대체됐다.

### 도메인 영속 상태도 enum으로 통일

> `Book.deleted`도 확장을 고려해서 지금 Enum 구조로 통일하도록 하자.

### `DELETE /api/admin/books/{bookId}`

> 외부 계약 상으로 '삭제'라는 의도를 표현하는게 중요하고, 이 삭제가 소프트 딜리트인지 하드 딜리트인지는 서버 내부 정책으로 숨긴다.

### `status` enum

> API 스펙은 만일 변경해야 할 때 파급이 너무 크기 때문에, 유연하게 구성하는게 바람직하다.
> 또한, Enum 대신 boolean을 선택해서 얻을 수 있는 이점이 크지 않다. (Enum을 표현하는 클래스가 하나 생기는 것 정도가 차이점)
> 따라서, 확장에 유리한 Enum을 선택한다.
>
> 단, "이용 가능성"인 availability보단, 확장을 고려해서 "상태"임을 표현하는 프로퍼티명을 사용한다.

### `ACTIVE`, `DELETED`

> 미래에 생명주기 상태가 추가되었을 때 이를 클라이언트에게 표시하기도 쉽고, 서버 내부 구현으로만 감추고 ACTIVE, DELETED만 내려줄 수도 있다.
> 즉, 선택지가 생겨 유연해진다.

### 활성·보관 조회 경계 분리

> 사용자용 조회(활성 레코드만 조회)와 관리자용 조회(비활성 레코드도 포함해서 조회)를 Repository 계층에서 추상화해서 제공해야, 비즈니스 계층의 코드 가독성을 향상시키고, 휴먼 에러(ex\_ 사용자가 호출하는 메서드인데 비활성 레코드를 필터링하는 로직을 넣지 않음)를 방지하기 쉽다.

### 엔티티 상태 전이와 SpotBugs 예외

> B안의 "레포지토리가 비즈니스 규칙(ACTIVE -> DELETED)를 표현한다"가 유지보수에 아주 좋지 않은 코드이므로, A안을 선택한다.
>
> SpotBugs가 보내준 경고는, JPA의 특수성 때문에 발생한 상황이니, 예외로 두어 경고하지 않게 만든다.

### 중복 삭제 요청

> 관리자 기능이니, 멱등성보다는 단순하고 직관적으로 구현

## 영향

- `Book`이 삭제 상태 전이와 이용 가능성 검사를 책임진다. `BookArchiveRepository`는 삭제 시
  행 잠금을 획득해 동시 중복 삭제를 직렬화한다.
- `AuthorBook`, `Chapter`, `Club`은 같은 `Book` 엔티티 참조를 의도적으로 공유하므로 해당
  생성자의 `EI_EXPOSE_REP2`만 SpotBugs 검사에서 제외한다.
- 사용자 서비스는 활성 조회 경계를 사용하고, 보존 데이터가 필요한 경로는 보관 조회 경계를
  명시적으로 사용한다.
- Android는 모임 도서의 `status`를 처리해야 한다. Android 구현은 별도 작업이다.
- `API.md`, Swagger, 관리자 페이지와 관련 테스트가 같은 계약을 유지해야 한다.

## 한계와 후속 작업

- 도서 복구 기능은 제공하지 않는다.
- 삭제 시각과 삭제 사유는 저장하지 않는다.
- 보존된 댓글을 사용자에게 다시 보여주는 화면·API는 후속 논의로 남긴다.
- Android에서 `DELETED` 상태를 표시하고 읽기 진입을 차단하는 작업은 이 변경에 포함하지 않는다.
- 운영 환경은 Hibernate `ddl-auto=update`를 사용하므로 `status` 열에 DB 기본값 `ACTIVE`를
  선언한다. 명시적 마이그레이션 체계로 전환할 때도 기존 `books` 행을 `ACTIVE`로 초기화하는
  DDL을 함께 관리해야 한다.

## 향후 재검토 신호

- 삭제 시각·사유 또는 변경 이력을 감사해야 한다.
- 도서 복구가 필요하다.
- `ACTIVE`, `DELETED` 외의 도서 생명주기 상태가 필요하다.
- 보관 도서 조회 요구가 관리자 목록을 넘어 별도 검색·감사 기능으로 확장된다.
- Hibernate `ddl-auto` 대신 명시적 스키마 마이그레이션 도구를 도입한다.
