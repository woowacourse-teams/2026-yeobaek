# ADR: 문장 단위 댓글을 위해 Passage와 Sentence 분리

## 상태

확정. 결정 근거 기록 2026-08-31 (개발자).

관련 이슈: [P-126](https://linear.app/yeobaek/issue/P-126/%EB%AC%B8%EB%8B%A8%EC%9D%B4-%EB%84%88%EB%AC%B4-%EA%B8%B4-%EA%B2%BD%EC%9A%B0-%ED%99%94%EB%A9%B4-%ED%95%98%EB%82%98%EB%A5%BC-%EB%8B%A4-%EC%B0%A8%EC%A7%80%ED%95%A8)

관련 계약: 상위 저장소의 [`PRD.md`](../../../docs/PRD.md),
[`API.md`](../../../docs/API.md), [`인제스트_가이드.md`](../../../docs/인제스트_가이드.md)

## 맥락

P-126에서 기존 문단 단위 댓글은 문단이 길 때 댓글 대상 범위가 너무 넓고 화면 하나를 모두
차지할 수 있다는 문제가 제기됐다. 문단, 한 문장, 여러 문장, 여러 단어 선택 방식을 실제
교환독서 경험자에게 검증한 결과, 한 문장 탭 방식을 기본 댓글 작성 단위로 선택했다.

기존 모델은 `Passage`가 문단 원문을 직접 보관하고 `Comment`가 `Passage`를 참조한다. 문장 단위로
댓글을 작성하고 조회하려면 문단과 문장을 별도 식별할 수 있어야 하며, 본문 응답·댓글 API·관리자
인제스트 형식과 기존 데이터 전환 정책을 함께 바꿔야 한다.

문장을 별도 행으로 저장할 때 제공된 책을 기준으로 100권은 약 85만 개, 1,000권은 약 851만 개의
문장 레코드가 예상됐다. 이 정도 행 수 자체보다 불필요한 인덱스, 비효율적인 조회와 문장별 개별
저장이 실질적인 리스크라는 초기 검토를 바탕으로 조회·저장 방식을 결정했다.

## 결정

### 도메인 모델과 스키마

- `Passage`는 문단을 나타내는 컨테이너로 유지하고 `Sentence`를 1:N으로 소유한다.
- 문장은 항상 하나의 문단에 속하며, 문단 없는 개별 문장은 의미를 갖지 않는다.
- `Comment`는 `Passage` 대신 `Sentence`와 N:1 관계를 맺는다.
- `Passage`와 `Sentence`의 관계에는 `cascade = CascadeType.ALL`, `orphanRemoval = true`를 적용한다.
- 문장 순서는 문단 안에서 1부터 시작하는 dense `sequence`로 저장한다.
- DB에 `UNIQUE (passage_id, sequence)` 제약을 두어 같은 문단 안의 문장 순서 중복을 차단한다.
- 문단 원문 필드는 제거하고 API는 `sentences[].content`만 반환한다.

### 본문과 댓글 수 조회

- 본문 범위 조회는 문단과 문장을 fetch join으로 한 번에 조회한다.
- 문장별 댓글 수는 본문 조회 결과에 실제로 포함된 sentence ID 목록을 `IN` 조건으로 전달해
  별도 `GROUP BY` 쿼리로 집계한다.
- 댓글 FK가 만드는 기본 인덱스만 사용한다. 댓글 집계를 위한 추가 복합 인덱스는 미리 만들지 않는다.

### 문장 원문과 Android 표시 범위

- 문장 사이의 공백과 개행은 앞 문장의 `content` 끝에 포함해 입력 그대로 저장한다.
- 서버는 문장 `content`의 앞뒤 공백을 제거하지 않는다.
- 한 문단의 문장을 `sequence` 순서로 연결하면 분리 전 문단 원문이 복원되어야 한다.
- Android는 본문 자체의 공백과 개행을 렌더링한다. 댓글이 달린 문장을 밑줄이나 하이라이트로
  표시할 때만 문장 끝의 공백과 줄바꿈을 시각적 표시 범위에서 제외한다.

### 관리자 인제스트와 저장

- 관리자 인제스트 JSON에서 문단을 `passages[].sentences[].content`로 미리 분리한다.
- 기존 `passages[].content` 형식은 지원하지 않는다.
- 서버는 문단 배열 순서로 책 전체 `passage.sequence`를, 각 문단의 문장 배열 순서로
  `sentence.sequence`를 부여한다.
- 문장 저장은 `Passage`의 JPA cascade를 사용하고 별도 배치 저장 최적화를 적용하지 않는다.
- 문단당 문장 수에는 별도 상한을 두지 않는다.

### 기존 데이터 전환

- 기존 문단 원문과 문단 댓글 데이터는 마이그레이션하지 않고 폐기한다.
- 이 breaking version을 사용자 유입 전에 배포할 때 운영 DB 전체를 한 번 초기화한다.
- 새 스키마로 재기동한 뒤 새 인제스트 형식으로 도서를 다시 업로드한다.

## 검토한 선택지

### 댓글 작성 단위

1. 현재 문단 단위 유지
2. 한 문장 탭
3. 여러 문장 선택
4. 여러 단어 선택

실험 결과 한 문장 탭을 기본 방식으로 선택하고, 다른 범위 선택은 후속 확장 가능성으로 남겼다.

### 본문에서 문장을 조회하는 방식

1. 문장을 별도 쿼리로 일괄 조회한 뒤 애플리케이션에서 문단별 그룹화
   - 개별 쿼리가 단순하고 join 결과의 중복 전송이 없다.
   - 서비스가 그룹화와 순서 조립을 직접 수행해야 한다.
2. 문단과 문장을 fetch join으로 한 번에 조회
   - 완성된 문단 객체 그래프를 조회할 수 있다.
   - join 결과의 상위 데이터 중복, 복잡한 JPQL과 fetch join 결합이 생긴다.
3. 지연 로딩과 Hibernate batch fetch 사용
   - 도메인 객체 순회 코드는 단순하다.
   - 성능이 전역 설정에 의존하고 설정 변경에 따른 성능 하락을 코드에서 확인하기 어렵다.

### 문장 생명주기

1. `CascadeType.PERSIST`만 적용
2. `CascadeType.ALL`과 `orphanRemoval = true` 적용
3. cascade 없이 `SentenceRepository`에서 직접 저장

문장은 문단 없이 의미를 갖지 않는다는 도메인 규칙을 표현하기 위해 2번을 선택했다.

### 댓글 수 집계 범위

1. 실제 조회된 sentence ID 목록을 `IN` 조건으로 전달
2. 문단 sequence 범위로 간접 집계
3. 본문 fetch join 쿼리에 댓글 집계까지 결합

다른 순서 불변식에 의존하지 않고 실제 응답 대상 문장의 댓글을 집계하기 위해 1번을 선택했다.

### 문장 경계 표현

1. 공백과 개행을 문장 `content`에 포함
2. 문장을 trim하고 클라이언트가 공백을 삽입
3. 문장 `content`와 구분자를 별도 저장

원문을 바꾸지 않고 줄바꿈 같은 예외를 보존하기 위해 1번을 선택했다.

### 문장 순서 유일성

1. `UNIQUE (passage_id, sequence)`로 DB에서도 강제
2. 인제스트 애플리케이션에서만 순서 보장

안정성을 유지하기 위해 1번을 선택했다.

### 추가 댓글 인덱스

1. FK 인덱스만 사용하고 실제 문제를 측정한 뒤 추가
2. `comments(sentence_id, club_member_id)` 복합 인덱스 추가
3. 모임 기준 복합 인덱스까지 함께 설계

실제 데이터와 실행계획 없이 추가 인덱스를 미리 도입하지 않기 위해 1번을 선택했다.

### 인제스트 저장 최적화

1. JPA cascade 저장을 사용하고 별도 최적화를 적용하지 않음
2. Hibernate JDBC batching 도입
3. 문장을 JDBC로 직접 일괄 저장

빈도가 낮은 관리자 작업이므로 1번을 선택했다.

### 문단당 문장 수

1. 별도 상한을 두지 않음
2. 최대 문장 수를 정해 인제스트에서 거부
3. 저장은 허용하되 본문 API에서 일부 문장만 반환

책 원문을 훼손할 수 있는 제약을 두지 않기 위해 1번을 선택했다.

### 기존 데이터 전환

1. 기존 데이터를 폐기하고 DB 전체 초기화 후 재인제스트
2. 기존 문단 원문과 댓글을 새 문장 구조로 마이그레이션
3. 구·신 스키마를 함께 유지

사용자 유입 전이라는 조건에서 1번을 선택했다.

### 문장 분리 시점

1. 인제스트 JSON에서 문장을 미리 분리
2. 서버가 문단 원문을 문장으로 분리
3. 기존 형식과 새 형식을 모두 허용

기존 인제스트 형식을 유지하지 않고 인제스트 과정에서 문장을 미리 분리하는 1번을 선택했다.

## 개발자 결정 근거 원문

아래 내용은 결정 과정에서 기록된 개발자 답변을 수정하지 않고 인용한 것이다.

### 한 문장 탭

> **한 문장 탭 방식 선택**
> 교환독서 경험자 8명 중 7명이 실제로 문장 단위의 코멘트를 사용하고 있으며, 5명은 문장 기반 탭 방식을 가장 선호했다. 특히 한 문장 탭은 가장 불편한 방식으로 선택한 응답자가 한 명도 없어, 사용자의 기존 습관과 부합하면서 거부 위험이 가장 낮은 기본 방식으로 판단했다.

### 기존 데이터 폐기

> **A. 기존 데이터를 폐기하고 재인제스트 — 권장**
>
> 아직 사용자 모집 전이라 기존 데이터 폐기가 가능하니, 비용이 가장 적은 A안 선택.

### 문단과 문장 fetch join

> - 결론:&#x20;
>   - 3번(지연 로딩과 Hibernate batch fetch 사용) 방식은 한 기능이 전역 설정에 의존한다는 점 때문에, 유지보수를 어렵게 할거라 예상되어 배제한다
>   - 결국 성능 차이는 적기 때문에, 코드 가독성을 중점으로 1번과 2번 중 어떤 방식이 바람직한지로 결정한다
>   - 우리 서비스에서 독립적인 개별 문장은 의미를 갖지 않고, 항상 문단 단위로 같이 사용된다\
>     → 문단 단위로 문장을 한 번에 조회하는게 자연스러우니, 해당 흐름에 더 가까운 2번 방식(문단과 문장을 fetch join으로 한 번에 조회)을 선택한다

### Passage가 문장 생명주기 소유

> B안으로 결정
>
> "문장은 항상 문단에 속한다", "문단 없는 개별 문장은 의미를 갖지 않는다"라는 도메인 규칙을 가장 잘 표현하는게 B안이므로, B 선택.
> A안을 선택한다면 문단을 삭제해도 문장을 남겨야 하는 경우가 있을 때 이점이 있는데, 도메인 규칙상 그런 상황이 없을거라 판단.

### 실제 sentence ID로 댓글 수 집계

> A안으로 결정
>
> 실제 클라이언트가 한 번에 문단 10개 이상을 요청할 일은 적을거라 판단되어서, A 방식이 부담이 될 가능성이 매우 낮다고 판단.
> 따라서, 순서(sequence)같은 다른 요구사항에 의존하지 않고 항상 안정적으로 "문장에 달린 댓글을 조회한다"를 이뤄낼 수 있는 A안 선택.

### 원문 공백과 Android 표시 범위

> A로 결정
> B는 책 원문을 수정할 수도 있으며, 문장과 문장 사이에 줄바꿈이 필요하거나 하는 예외 상황에 대응할 수 없다.
> 단, 클라이언트 개발자는 댓글이 달린 문장을 사용자에게 표시할 때, 맨 뒤 공백이나 줄바꿈은 제외하고 표시해야 한다

### 문장 순서 UNIQUE 제약

> A로 결정
>
> 메모리 부담이나 성능 이슈는 사소하기 때문에, 굳이 안정성을 포기하면서까지 B를 선택할 이유가 적다.
> 성능이 부담된다면 그때 다른 대안을 고려한다.

### 추가 댓글 인덱스 유보

> A. FK 인덱스만 사용하고 추가 인덱스는 측정 후 도입 — 권장
>
> 미리 추측해서 구비하는게 아니라, 실제 데이터가 쌓여서 문제가 될 때 EXPLAIN ANALYZE와 응답 시간을 근거로 인덱스를 추가하는게 바람직하다.

### 인제스트 저장 최적화 유보

> A. JPA cascade 저장을 사용하고 별도 최적화는 하지 않음 — 권장
>
> 빈도가 낮은 관리자 작업이니, 지금 당장 최적화할 필요성이 낮음
> 추후에 실제 성능이 문제가 된다면, 측정을 통해 근거를 만들어 최적화.

### 문단당 문장 수 상한 없음

> ### A. 별도 상한을 두지 않음 — 권장
>
> 문단당 문장 수가 많아졌을 때 실제 문제가 생기면 대안을 마련한다.
>
> 책의 원문을 훼손할 수 있는 제약 규칙은 두지 않는다.

### 운영 DB 전체 1회 초기화

> ### A. 배포 시 DB 전체를 한 번 초기화 — 권장
>
> 사용자 유입 전이니 가장 단순하고 문제 발생 여지가 없는 A 선택

### 인제스트 과정에서 문장 분리

> 선택지 A: 인제스트 JSON에서 문장을 미리 분리
>
> 기존 인제스트 형식을 반드시 유지해야만 하는 이유가 없으니, 변경을 굳이 피해야 할 이유가 없음.
> 따라서 두 형식을 허용하는 C는 유지보수 비용이 가장 크니 논외.
> 또한, 문단을 문장으로 분리하는 비용이 서버보다 인제스트 과정에서 수행할 때 더 적다 판단.

## 영향

- `passages`는 문단 원문을 보관하지 않고 `sentences`가 문장 원문을 보관한다.
- `comments`의 대상 FK가 passage에서 sentence로 바뀐다.
- 본문 API는 각 passage 안에 `sentences[]`를 반환하고 문단 원문과 문단 전체 댓글 수를 반환하지 않는다.
- 댓글 목록과 작성 API는 sentence ID를 경로에 사용한다. 댓글 수정·삭제 경로는 유지한다.
- 본문 조회는 문단과 문장을 fetch join하고, 문장별 댓글 수는 실제 sentence ID 목록으로 별도 집계한다.
- 관리자 인제스트, 가이드와 업로드 UI는 문장이 미리 분리된 새 JSON 형식을 사용한다.
- Android는 문장 단위 댓글 대상과 문장별 `commentCount`를 사용하고, 댓글 시각 표시 범위에서만
  문장 끝 공백과 줄바꿈을 제외해야 한다.
- 배포 시 운영 DB 전체가 한 번 삭제되므로 회원·모임·도서·진도·댓글을 모두 다시 만들거나
  재인제스트해야 한다.

## 한계와 후속 작업

- 기존 문단 원문과 댓글 데이터는 새 구조로 옮기지 않는다.
- 기존 `passages[].content` 인제스트 형식은 지원하지 않는다.
- 댓글 집계용 추가 복합 인덱스는 도입하지 않는다. 실제 데이터에서 문제가 생기면
  `EXPLAIN ANALYZE`와 응답 시간을 근거로 추가한다.
- Hibernate JDBC batching이나 JDBC 직접 저장을 도입하지 않는다. 관리자 인제스트 성능이 실제로
  문제가 될 때 측정 후 최적화한다.
- 문단당 문장 수 상한을 두지 않는다. 실제 문제가 발생하면 원문 보존 조건을 유지하는 대안을 마련한다.
- 본문 범위 조회는 fetch join으로 문장 N+1을 방지한다. 추가 조회 경로에서 N+1이 관찰되면
  실제 쿼리와 응답 시간을 측정한 뒤 대응한다.
- 여러 문장이나 여러 단어 범위에 댓글을 작성하는 기능은 이번 결정에 포함하지 않는다.

## 향후 재검토 신호

- 댓글 데이터가 쌓인 뒤 문장별 댓글 수 집계 응답 시간이 문제가 된다.
- `EXPLAIN ANALYZE`에서 현재 FK 인덱스만으로 댓글 집계 병목이 확인된다.
- 관리자 도서 인제스트 시간이 운영에 문제가 된다.
- 정상적인 책에서도 문단당 문장 수 때문에 응답 크기나 `IN` 파라미터 수 문제가 발생한다.
- 본문 범위 조회 이외의 경로에서 문장을 조회하며 N+1이 관찰된다.
- 기존 데이터를 보존해야 하는 사용자 유입 이후에 같은 형태의 breaking schema 변경이 필요하다.
- 여러 문장 또는 여러 단어 범위 댓글을 제품 요구사항으로 지원하게 된다.
