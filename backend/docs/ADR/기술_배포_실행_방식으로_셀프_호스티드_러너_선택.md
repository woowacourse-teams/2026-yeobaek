# ADR: 배포 실행 방식으로 EC2 셀프 호스티드 러너 선택

## 상태

확정. 결정 근거 기록 2026-08-10 (개발자).

## 맥락

CI/CD 파이프라인(GitHub Actions)은 이미지 빌드·Docker Hub 푸시 후 EC2에 SSH로
접속해 `docker compose pull && up -d`를 실행하는 구조였다. 그러나 EC2 보안
그룹이 SSH(22번 포트) 인바운드를 특정 IP로만 제한하고 있어, GitHub 호스티드
러너(동적 IP)에서의 SSH 접속이 다음과 같이 실패했다:

```
ssh: connect to host *** port 22: Connection timed out
Error: Process completed with exit code 255.
```

22번 포트 인바운드 개방은 애초에 불가능한 상황이므로 선택지가 아니다. 빌드는
GitHub Actions에서 수행하되, EC2에서의 pull & 재기동을 **인바운드 규칙 변경
없이** 어떤 경로로 트리거할지 결정해야 한다.

## 검토한 선택지 (2026-08-10 개발자 기록)

### 선택지 A: AWS Systems Manager (SSM) Run Command

EC2에 설치된 SSM 에이전트가 AWS 서버와 443 포트(아웃바운드)로 통신해 명령
(특정 스크립트 실행)을 전달받아 실행한다.

- **장점**
  - AWS IAM으로 통제됨
  - 실행 스크립트를 그대로 사용 가능
- **단점**
  - EC2에 SSM 에이전트 실행 필요
  - IAM Role 설정 필요
  - 모니터링이 까다로움 (스크립트에 오류가 나면 AWS 콘솔로 들어가서 로그 확인)

### 선택지 B: Self-Hosted GitHub Runner

사내망에 직접 러너용 인스턴스를 띄워서, GitHub Actions 워크플로우를 인스턴스
위에서 실행한다. 러너는 아웃바운드 HTTPS로 GitHub에 폴링해 잡을 받아온다.

- **장점**
  - 기존 SSH 방식(배포 스크립트)을 그대로 쓸 수 있음
  - 도커 이미지 빌드 캐시나 의존성 파일들을 러너 서버에 남겨둘 수 있음
    → 빌드 속도가 매우 빠름
  - 배포 로그가 GitHub Actions 화면에서 그대로 보임 (모니터링 용이)
- **단점**
  - 러너 역할을 할 EC2 서버를 관리해야 함

## 결정

**Self-Hosted GitHub Runner(B)를 사용한다.**

두 선택지 모두 인바운드 규칙 변경 없이 아웃바운드 통신만으로 동작하지만,
SSM(A)은 IAM Role·에이전트 설정이 선행되어야 하고 실패 시 AWS 콘솔을 오가며
로그를 확인해야 한다. 셀프 호스티드 러너(B)는 기존 배포 스크립트를 그대로
쓰면서 실행 결과가 GitHub Actions 화면에 남아, 1인 백엔드·데모 임박 일정에서
도입·운영 비용이 가장 낮다.

별도 러너 인스턴스를 두지 않고 **배포 대상 EC2에 러너를 상주**시켜 관리
대상 서버 증가를 피했고, 워크플로는 `build`(GitHub 호스티드: 테스트·이미지
빌드·푸시)와 `deploy`(`runs-on: [self-hosted, ec2-prod]`: pull & 재기동)
두 잡으로 분리했다. 설정 절차는 [배포_가이드.md](../배포_가이드.md)를 따른다.

## 한계·트레이드오프

- 러너 프로세스가 배포 대상 EC2에 상주하므로 인스턴스 리소스를 일부 사용하고,
  러너가 죽으면 배포 잡이 큐에 대기한다 (systemd 서비스 등록으로 재부팅·크래시
  복구).
- 셀프 호스티드 러너는 포크 PR 코드 실행 위험이 있으므로, `pull_request`
  트리거 워크플로에 셀프 호스티드 라벨을 사용하지 않고 outside collaborator
  실행 승인 설정을 유지해야 한다.
- 빌드 잡은 여전히 GitHub 호스티드 러너에서 수행하므로 빌드 캐시 이점은
  현재 구성에서는 활용하지 않는다. 빌드 속도가 문제가 되면 빌드 잡의 셀프
  호스티드 이전을 재검토한다.
- IAM 기반 통제·단기 자격증명이 필요해지는 시점에는 SSM(A)으로의 전환을
  재검토한다.
