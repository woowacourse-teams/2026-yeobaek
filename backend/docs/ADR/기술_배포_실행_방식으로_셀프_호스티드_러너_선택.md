# ADR: 배포 실행 방식으로 EC2 셀프 호스티드 러너 선택

## 상태

확정. 결정 근거 기록 2026-08-10 (개발자).

## 맥락

CI/CD 파이프라인(GitHub Actions)은 이미지 빌드·Docker Hub 푸시 후 EC2에 SSH로
접속해 `docker compose pull && up -d`를 실행하는 구조였다. 그러나 EC2 보안
그룹이 SSH(22번 포트) 인바운드를 특정 IP로만 제한하고 있어, GitHub 호스티드
러너(동적 IP)에서의 SSH 접속이 다음과 같이 실패했다:

```
ssh: connect to host *** port 22: Connection timed out
Error: Process completed with exit code 255.
```

22번 포트 인바운드 개방은 애초에 불가능한 상황이므로 선택지가 아니다. 빌드는
GitHub Actions에서 수행하되, EC2에서의 pull & 재기동을 **인바운드 규칙 변경
없이** 어떤 경로로 트리거할지 결정해야 한다.

## 검토한 선택지 (2026-08-10 개발자 기록)

### 선택지 A: AWS Systems Manager (SSM) Run Command

EC2에 설치된 SSM 에이전트가 AWS 서버와 443 포트로 통신해 명령(특정 스크립트
실행)을 전달받아 실행한다.

- **장점**
  - AWS IAM으로 통제됨
  - 실행 스크립트를 그대로 사용 가능
- **단점**
  - EC2에 SSM 에이전트 실행 필요
  - IAM Role 설정 필요
  - 모니터링 까다로움 (스크립트에 오류가 나면 AWS 콘솔로 들어가서 로그 확인)

### 선택지 B: Self-Hosted GitHub Runner

사내망에 직접 러너용 인스턴스를 띄워서, GitHub Actions 워크플로우를 인스턴스
위에서 실행한다.

- **장점**
  - 기존 SSH 방식을 그대로 쓸 수 있음
  - 도커 이미지 빌드 캐시나 의존성 파일들을 러너 서버에 남겨둘 수 있음
    → 빌드 속도가 매우 빠름
- **단점**
  - 러너 역할을 할 EC2 서버를 관리해야 함 → 용량 관리 등 유지보수 필요
  - 러너용 EC2 인스턴스를 켜두어야 하니 서버 비용 발생
- **단점 해소 방안**
  - Jobs를 분리해서, 무거운 작업(빌드)은 GitHub 서버의 러너에서 실행하고,
    가벼운 작업만 우리 서버에서 실행할 수 있음

### 선택지 C: AWS CodeDeploy

GitHub Actions에서 애플리케이션 버전을 S3에 업로드하면, EC2에 설치된
CodeDeploy 에이전트가 S3에서 파일을 내려받아 배포한다.

- **장점**
  - 모니터링 쉬움
  - 롤백 쉬움
  - 향후 무중단 배포로 확장할 때 유리함
- **단점**
  - 러닝 커브가 높음 (appspec.yml 작성, S3 버킷 필요, IAM 설정 등)
    → 단순 도커 배포로 쓰기에는 오버엔지니어링

### 선택지 D: Watchtower

서버가 스스로 새로운 이미지를 감지하고 업데이트한다.

- **장점**
  - CI/CD 스크립트가 필요 없어짐
  - 외부와 EC2 사이의 통신이 필요 없어지니, 방화벽 문제 없어짐
- **단점**
  - 컨테이너를 내리고 새 이미지를 띄우는 작업 말고는 수행하기 어려움
  - 모니터링 어려움

## 결정

**Self-Hosted GitHub Runner(B)를 사용한다.**

선택한 이유 (2026-08-10 개발자 기록):

1. 기존 GitHub Actions처럼 배포 성공/실패 여부를 쉽게 모니터링할 수 있다.
2. 기존에 만들어둔 CI/CD 스크립트를 그대로 활용할 수 있다 → 작업량과 러닝
   커브가 적다.
3. Self-Hosted Runner 자체는 매우 가벼운 프로세스다 → 무거운 작업은 깃허브
   서버의 러너에게 위임하면, 기존 인스턴스의 부담은 거의 늘어나지 않는다
   → 새로운 인스턴스를 띄울 필요 없다.
4. 롤백 기능을 지원하지 않지만, 필요시 스크립트나 다른 기능을 활용해 롤백을
   구현할 수 있다.

워크플로는 `build`(GitHub 호스티드 러너: 테스트·이미지 빌드·푸시)와
`deploy`(`runs-on: [self-hosted, ec2-prod]`: pull & 재기동) 두 잡으로
분리했으며, 러너는 배포 대상 EC2에 상주시킨다. 설정 절차는
[배포_가이드.md](../배포_가이드.md)를 따른다.

## 한계·트레이드오프

1. 도커 빌드 작업을 GitHub 서버에서 수행하니, 캐싱 이점은 얻을 수 없다.
2. 러너가 깃허브 서버로 443 연결을 맺고 기다리는 롱 폴링 방식을 사용한다
   → 단, 아주 적은 양의 패킷만 오가니 네트워크 대역폭 부담은 적다.
3. 러너가 정상 동작하는 걸 GitHub가 보장하지 않으니, 장애 발생 시 고려해야
   하는 요소가 추가된다.

## 신경써야 할 부분

1. 서버에서 도커 이미지를 계속 다운로드하다 보면, 이전 버전의 이미지가 디스크
   용량을 차지한다 → 예전 도커 이미지를 청소하는 스크립트를 배포 파이프라인에
   포함해야 한다.
