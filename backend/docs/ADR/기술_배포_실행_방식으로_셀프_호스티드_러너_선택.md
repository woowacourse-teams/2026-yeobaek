# ADR: 배포 실행 방식으로 EC2 셀프 호스티드 러너 선택

## 상태

확정. 결정 근거 기록 2026-08-10 (개발자).

## 맥락

CI/CD 파이프라인(GitHub Actions)은 이미지 빌드·Docker Hub 푸시 후 EC2에 SSH로
접속해 `docker compose pull && up -d`를 실행하는 구조였다. 그러나 EC2 보안
그룹이 SSH(22번 포트) 인바운드를 특정 IP로만 제한하고 있어, GitHub 호스티드
러너(동적 IP)에서의 SSH 접속이 다음과 같이 실패했다:

```
ssh: connect to host *** port 22: Connection timed out
Error: Process completed with exit code 255.
```

빌드는 GitHub Actions에서 수행하되, EC2에서의 pull & 재기동을 어떤 경로로
트리거할지 결정해야 한다. 이 결정은 보안 그룹 정책·시크릿 관리·운영 부담을
좌우한다.

## 검토한 선택지 (2026-08-10 개발자 기록)

### 선택지 A: 보안 그룹에 SSH 인바운드 개방

GitHub 호스티드 러너가 SSH 접속할 수 있도록 보안 그룹을 조정한다.

- 러너 IP가 동적이므로 사실상 `0.0.0.0/0` 개방, 또는 워크플로마다 AWS API로
  현재 러너 IP를 규칙에 추가했다가 제거하는 방식이 필요하다.

### 선택지 B: EC2 셀프 호스티드 러너

EC2에 GitHub Actions 러너를 상주시키고, 배포 잡(`deploy`)만 이 러너에서
실행한다. 러너는 아웃바운드 HTTPS로 GitHub에 폴링해 잡을 받아온다.

- 빌드 잡(테스트·이미지 빌드·푸시)은 기존대로 GitHub 호스티드 러너가 수행
- 인바운드 규칙 변경이 전혀 필요 없음

### 선택지 C: AWS SSM Send-Command

GitHub Actions가 OIDC로 AWS 역할을 assume한 뒤 `aws ssm send-command`로
EC2에 배포 명령을 내린다. SSH도 러너 상주도 필요 없다.

## 트레이드오프 비교 (2026-08-10 개발자 기록)

### 공격면 (보안 그룹 변경 여부)

- A는 SSH 전면 개방 시 공격면이 크게 늘고, IP 동적 추가/제거 방식은 AWS
  자격증명을 Actions에 부여해야 하며 실패 시 규칙이 남는 청소 문제가 있다.
- B·C는 인바운드 규칙을 전혀 건드리지 않는다. SSH 제한 정책을 그대로 유지한다.

### 도입 비용

- B는 EC2에서 러너 등록 스크립트 실행 + systemd 등록이면 끝난다 (수십 분).
- C는 OIDC 공급자 등록·IAM 역할·정책 설계가 선행되어야 한다. 1인 백엔드·데모
  임박 일정에서는 부담이 크다.

### 운영 부담

- B는 러너 프로세스가 EC2에 상주한다. 러너가 죽으면 배포 잡이 큐에 대기하므로
  러너 생존을 신경 써야 한다 (systemd 등록으로 완화).
- C는 상주 프로세스가 없어 운영 부담이 가장 적다.

### 시크릿 관리

- A는 SSH 개인키(`EC2_SSH_KEY`) 전문을 GitHub 시크릿에 보관해야 한다.
- B는 SSH 관련 시크릿(`EC2_HOST`, `EC2_USER`, `EC2_SSH_KEY`)이 모두 불필요해진다.
- C는 장기 자격증명 없이 OIDC 단기 토큰만 사용한다 (가장 우수).

## 결정

**EC2 셀프 호스티드 러너(B)를 사용한다.**

보안 그룹의 SSH 제한 정책을 유지하면서(A 탈락), 현재 팀 규모와 일정에서
도입 비용이 가장 낮은 선택지다. C(SSM)는 보안·운영 면에서 더 우수하지만
OIDC·IAM 설계 비용이 지금 시점에는 과하다. 러너 운영이 부담이 되는 시점에
C로의 전환을 재검토한다.

워크플로는 `build`(GitHub 호스티드)와 `deploy`(`runs-on: [self-hosted,
ec2-prod]`) 두 잡으로 분리했다. 설정 절차는
[배포_가이드.md](../배포_가이드.md)를 따른다.

## 한계·트레이드오프

- 러너가 EC2에 상주하므로 인스턴스 리소스를 일부 사용하고, 러너가 죽으면
  배포가 큐에 걸린다 (systemd 서비스 등록으로 재부팅·크래시 복구).
- 셀프 호스티드 러너는 포크 PR 코드 실행 위험이 있으므로, `pull_request`
  트리거 워크플로에 셀프 호스티드 라벨을 사용하지 않고 outside collaborator
  실행 승인 설정을 유지해야 한다.
- 배포 잡이 GitHub 장애의 영향을 받는다 (SSH 방식도 동일).
