# ADR: API 문서화로 REST Docs + Swagger 조합 선택

## 상태

대체됨 (2026-08-14). [기술_API_문서화를_Swagger로_전환](기술_API_문서화를_Swagger로_전환.md) 참조.
결정 근거 기록 2026-08-07 (개발자).

## 맥락

클라이언트 개발자에게 제공할 API 문서의 작성 도구를 선택해야 한다.

## 검토한 선택지 (2026-08-07 개발자 기록)

### 선택지 A: Spring REST Docs

- 문서를 테스트에서 만든다.
- 프로덕션 코드가 깨끗하다.
- 템플릿으로 스니펫을 직접 조립해야 한다.
- 결과물이 정적 HTML이라 Try it out이 없다.

### 선택지 B: Swagger

- 별도 세팅 없이 기본 스펙이 설정된다.
- Try it out으로 호출해 볼 수 있다.
- 산출물이 OpenAPI 스펙이라 외부에서 사용할 수 있다.
- 어노테이션이 잘못되어도 알 수 없다.
- 프로덕션 코드가 더러워진다.

### 공통 관찰

- Swagger나 REST Docs 모두 부가적인 설명이 관리 포인트로 추가되어야 하는 건 같다.

## 결정 과정 (2026-08-07 개발자 기록)

**판단 기준:** API 문서의 최종 사용자는 클라이언트 개발자이므로, 합의 후 결정한다.
(Try it out을 실제로 사용하는가? 산출물을 OpenAPI로 외부에서 활용하는가? 등)

1. **Try it out 필요 여부** — 클라이언트 개발자에게 직접 물어보았고, 지원해 주지
   않는다면 직접 구현해서 쓸 정도로 필요했다는 답변을 받았다. → Try it out이
   지원되는 방향으로 결정.
2. **REST Docs + Swagger vs Swagger 단독** — REST Docs는 컨트롤러 테스트(MockMvc)의
   내용을 바탕으로 작성된다. 컨트롤러 테스트를 어차피 작성할 예정이라면, REST Docs를
   활용하고 생성된 문서를 Swagger로 서빙하는 형태를 사용하자.
3. **컨트롤러 테스트를 작성해야 하는가** — 파라미터 누락 등의 문제를 잡기 위해서
   작성해야 한다.

## 결정

**REST Docs + Swagger 조합을 사용한다.**

- 문서 내용은 컨트롤러 테스트(MockMvc) 기반의 REST Docs로 작성한다.
- 생성된 문서를 Swagger(UI)로 서빙해 Try it out을 제공한다.

## 한계·트레이드오프

- **REST Docs 문서를 Swagger로 변환하는 라이브러리가 Spring Boot 4.1에서는
  안정적으로 지원하지 않을 수 있다.** 일단 적용해 보고 문제가 생기면 조치하기로
  결론 내렸다 (2026-08-07 개발자 기록).
- 두 도구를 조합하므로, Swagger 단독 대비 초기 세팅 비용(REST Docs 스니펫 →
  OpenAPI 변환·서빙 구성)이 든다.
- 부가적인 설명이 관리 포인트로 추가되는 비용은 어느 선택지든 동일하게 감수한다.
