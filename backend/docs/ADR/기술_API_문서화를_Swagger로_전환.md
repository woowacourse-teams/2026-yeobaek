# ADR: API 문서화를 Swagger(springdoc)로 전환

## 상태

확정. 결정 근거 기록 2026-08-14 (개발자).
[기술_API_문서화로_REST_Docs와_Swagger_조합_선택](기술_API_문서화로_REST_Docs와_Swagger_조합_선택.md)(2026-08-07)을 대체한다.

## 맥락

2026-08-07 결정에 따라 REST Docs(restdocs-api-spec)로 문서를 생성하고 Swagger UI로
서빙하는 조합을 운영해 왔다. 운영 경험을 바탕으로 문서화 도구를 재검토했다.

## 검토한 선택지 (2026-08-14 개발자 기록)

### RestDocs

- 테스트에 통과된 API만 문서화되니 신뢰도가 높다.
- 프로덕션 코드를 오염시키지 않는다.

### Swagger

- 별도 설정 없이도, 파라미터의 타입들이 문서에 반영된다.
  (RestDocs는 별도로 지정해줘야 타입이 반영됨)
- 별도 설정 없이도, 경로 변수가 문서에 반영된다.
  (RestDocs는 경로 변수임을 명시하지 않으면 엔드포인트로 취급됨)
- 가독성이 좋지 않은 테스트를 만들 필요 없다.

## 결정 과정 (2026-08-14 개발자 기록)

**우선 기준:** RestDocs는 타입, 경로변수 등 다양한 요소를 개발자가 일일이
지정해줘야 하는 게 불편하다(문서화가 불편하다).

## 결정

**Swagger(springdoc)로 전환한다.**

- restdocs-api-spec 의존성·openapi3 태스크·사전 생성 스펙 서빙 설정을 제거한다.
- springdoc이 런타임에 OpenAPI 스펙(`/v3/api-docs`)을 생성하고, `/docs`는
  Swagger UI로 리다이렉트한다.
- 부가 설명은 컨트롤러·DTO의 `@Operation`, `@Parameter`, `@Schema` 어노테이션으로
  작성한다.

구현: 커밋 4ca2018 (refactor: API 문서화를 REST Docs에서 springdoc(Swagger)으로 전환).

## 한계·트레이드오프 (2026-08-14 개발자 기록)

- Swagger를 위한 애노테이션은 프로덕션 코드를 오염시키지만, 일부는 '주석' 역할을
  하며 가독성 향상에도 기여한다.
- RestDocs가 주던 "테스트에 통과된 API만 문서화된다"는 신뢰도는 잃는다.
  어노테이션이 잘못되어도 문서 오류를 알 수 없다.
