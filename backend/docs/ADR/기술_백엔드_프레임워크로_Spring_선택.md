# ADR: 백엔드 프레임워크로 Spring 선택

## 상태

확정. 결정 근거 기록 2026-08-07 (개발자).

## 맥락

백엔드 API 서버를 구축할 프레임워크를 선택해야 한다. 프레임워크는 프로젝트 전반의
코드 구조·의존성·팀 협업 방식을 결정하는 비가역적 선택이므로, 검토한 선택지와
결정 근거를 기록한다.

## 검토한 선택지 (2026-08-07 개발자 기록)

### 선택지 A: Spring (Java)

- 검증된 라이브러리를 손쉽게 사용할 수 있다. 검증된 라이브러리에서 제공하는 기능을
  직접 만들 필요가 없다.
- 모든 백엔드 팀원이 Spring 구조를 이해하고 있다 → 코드리뷰 및 장애 발생 시 원인
  파악이 수월하다.

### 선택지 B: 다른 프레임워크 (FastAPI, Django, NextJS 등)

- Spring은 프레임워크 내부 구현에 대한 러닝 커브가 높다.
- Spring은 간단한 기능 구현에도 많은 코드(컨트롤러, DTO, 서비스, 레포지토리 등)가
  필요하다.

## 결정

**Spring을 사용한다.**

## 근거 (2026-08-07 개발자 기록)

- Spring의 최대 문제점은 '높은 러닝커브'인데, 이미 모든 백엔드 팀원은 Spring 지식을
  일정 이상 갖춘 상태이다.
- 강력하고 다양한 엔터프라이즈 기능을 제공하는 Spring 대비, 다른 프레임워크를 선택해
  얻을 수 있는 이점이 적다.

## 한계·트레이드오프

- 간단한 기능 구현에도 여러 계층(컨트롤러, DTO, 서비스, 레포지토리)의 코드가
  필요하다는 비용은 그대로 감수한다.
