# ADR: 컨트롤러 테스트를 웹 계층 책임으로 한정

## 상태

확정. 결정 근거 기록 2026-08-21 (개발자).

구현 지침: [컨트롤러 테스트 하네스](../지침/코딩/컨트롤러_테스트_하네스.md)

## 맥락

프로젝트의 JSON API 컨트롤러는 `@RestController`로 구현되어 있다. 컨트롤러 슬라이스
테스트는 공통 [ControllerTest](../../src/test/java/yeobaek/backend/support/ControllerTest.java)를
상속하고, `@WebMvcTest`, `MockMvc`, `@MockitoBean`을 사용한다. 서비스 예외의 HTTP 응답
변환은 [GlobalExceptionHandler](../../src/main/java/yeobaek/backend/support/GlobalExceptionHandler.java)가
담당한다.

기존 컨트롤러 테스트에는 성공 상태와 일부 JSON 필드, 일부 오류 상황에 대한 검증이 있었지만,
요청 값을 서비스에 전달하는 방식과 서비스 호출 여부, 성공 응답 필드의 검증 범위를 저장소 전체에
적용할 하나의 기준은 없었다. 이 ADR의 `개발자 결정 근거 원문`에 인용한 개발자 답변 자체가
이 결정의 근거 기록이다.

## 결정

### 적용 범위와 테스트 구성

- JSON API를 제공하는 `@RestController`만 이 결정의 대상으로 삼는다.
- 컨트롤러 테스트는 `@WebMvcTest`, `MockMvc`, `@MockitoBean`을 사용하는 Spring MVC
  슬라이스 테스트로 작성한다.
- 모든 엔드포인트에 의도한 HTTP 메서드와 경로를 사용하는 긍정 테스트를 작성한다.
- 잘못된 경로나 지원하지 않는 HTTP 메서드를 거부하는 Spring MVC 자체 동작은 엔드포인트마다
  반복 검증하지 않는다.

### 요청과 서비스 협력

- 정상 요청에서는 서비스를 정확히 한 번 호출하고, 경로 변수, 쿼리 파라미터, 헤더, JSON
  본문에서 얻은 값이 정확한 서비스 인자로 전달되는지 검증한다.
- Spring MVC 바인딩이나 웹 계층에 선언한 API 제약 때문에 요청이 거부되면 서비스를 호출하지
  않았는지 검증한다.
- 필수성, 타입, 형식처럼 API 계층에 선언한 제약만 컨트롤러 테스트에서 검증한다. 형태는
  올바르지만 비즈니스적으로 부적절한 값은 서비스 또는 도메인 계층의 테스트 대상으로 둔다.

### 응답

- 성공 응답은 상태 코드, 해당하는 `Content-Type`과 계약 헤더, API 계약에 명시된 모든 JSON
  필드를 개별 assertion으로 검증한다.
- 컨트롤러가 서비스 결과에 따라 상태나 본문을 직접 선택하면 각 응답 분기를 검증한다.
- 성공 JSON 전체를 하나의 문자열 기대값과 비교하거나 대표 필드만 표본으로 확인하지 않는다.

### 공통 웹 컴포넌트와 예외

- 인터셉터, argument resolver, 전역 예외 처리기와 같은 공통 웹 컴포넌트의 동작은 그 책임
  객체의 테스트에서 한 번 검증한다. 각 컨트롤러 테스트는 엔드포인트 고유 제약만 검증한다.
- 컨트롤러 클래스마다 대표 서비스 예외 하나를 사용해 서비스를 정확히 호출했는지와 서비스가
  던진 동일 예외 인스턴스가 전파되는지만 검증한다.
- 서비스 예외의 HTTP 상태와 오류 응답의 `code`, 정확한 `message` 전달은
  `GlobalExceptionHandlerTest`의 검증 대상으로 둔다. 메시지가 비즈니스 상황에 적절한지는
  예외를 생성하는 서비스 또는 도메인 계층의 테스트에서 검증한다.

### 하네스 구조

- 하네스는 작성 절차가 아니라 책임 경계를 먼저 설명하는 구조로 유지한다.
- 구체적인 규칙, 예제와 체크리스트는
  [컨트롤러 테스트 하네스](../지침/코딩/컨트롤러_테스트_하네스.md)를 따른다.

## 개발자 결정 근거 원문

아래 내용은 결정 과정에서 기록된 개발자 답변을 수정하지 않고 인용한 것이다.

### 서비스 호출과 미호출

> 서비스 전달까지 검증
>
> 근거: 계층형 아키텍처를 고려했을 때, 서비스를 제대로 호출하는 것 까지 컨트롤러 계층의 책임으로 판단할 수 있으니, 이 책임 역시 테스트하는 것이 마땅하다.

> 미호출까지 검증한다.
>
> "서비스를 제대로 호출하는 것"에는, "호출하지 않아야 할 상황이면 호출하지 않는다"까지 포함된 개념이다.

### 응답 필드와 오류 메시지

> 계약에 명시된 모든 필드를 개별 검증한다.
>
> "에러 메시지가 적절하냐"는, 예외를 던지는 측에서 적절한 메시지의 예외를 던지는지를 검증해야 하는거고, 컨트롤러는 단순히 서비스가 돌려준 것을 그대로 응답으로 잘 넘겨주냐를 책임지므로, 메시지가 상황에 적절한지 검증하진 않지만, 메시지를 검증한다.

### 대상과 라우팅 검증 범위

> JSON @RestController만 포함

> 올바른 메서드·경로의 긍정 테스트만 작성
>
> 근거: 잘못된 메서드/경로를 거부하는건 Spring이 제공하는 검증된 기능이니, 따로 검증하진 않는다.

### API 제약과 비즈니스 검증의 경계

> @Valid 등 컨트롤러 계층 검증이 선언된 필드만 포함
>
> API 스펙상 어떤 값이 필수적인 값인지, 어떤 형태로 주어야 하는지는 컨트롤러 계층이 표현해야 한다.
>
> 이렇게 컨트롤러 계층(API 스펙에서 표현하는 제약조건)의 책임인 검증이라면 컨트롤러 테스트에서 처리한다.
>
> 하지만 API 스펙에서 처리하지 않는 값 검증(형태는 올바르나 비즈니스적으로 부적절한 값)은 서비스와 도메인 레이어에서 처리할 것이니, 컨트롤러 계층의 테스트에서 책임지지 않는다.

### 공통 컴포넌트의 테스트 책임

> 인터셉터·예외 처리기 등 공통 컴포넌트 테스트에서 한 번만 검증하고, 각 컨트롤러는 고유 제약만 검증
>
> 해당 기능을 수행하는 객체가 존재할텐데, 그렇다면 해당 객체의 테스트 코드에서 검증할 일이다.

### 서비스 예외 전파와 HTTP 변환의 경계

> 컨트롤러 테스트는 서비스 호출과 동일 예외가 전파됐는지만 검증하고, HTTP 상태·본문은 GlobalExceptionHandlerTest에서 검증
>
> 근거: 해당 기능은 결국 GlobalExceptionHandler에서 수행하는 것이니, 해당 객체의 책임으로 두고 거기서 테스트하는게 바람직하다.

> 컨트롤러 클래스마다 대표 예외 하나만 작성
>
> 계층의 책임 상, 컨트롤러는 서비스의 내부 구현을 모른다.
>
> 즉, 서비스가 어떤 예외를 던질지는 컨트롤러 테스트의 관심사가 아니다.

### 책임 중심 문서 구조

> A 승인
>
> 구현 절차는 언제든지 바뀔 수 있지만, 이렇게 구현하고자 한 목적과 철학은 쉽게 바뀌지 않는다.
>
> 따라서, A 형태가 장기적인 문서 유지보수에 유리하다.

## 영향

- 새 JSON `@RestController` 테스트와 기존 테스트의 개정 작업은
  [컨트롤러 테스트 하네스](../지침/코딩/컨트롤러_테스트_하네스.md)의 책임 경계와 체크리스트를
  적용한다.
- 컨트롤러 테스트는 요청 매핑, 바인딩, 서비스 협력과 컨트롤러가 선택하는 정상 응답에 집중한다.
- 공통 인증 동작은 해당 인터셉터와 argument resolver 테스트가, 공통 HTTP 오류 변환은
  `GlobalExceptionHandlerTest`가 담당한다.
- 후속 요청에 따라 하네스에서 승인된 예제 다섯 개를 소스 테스트로 반영한다. 기존
  [ClubControllerTest](../../src/test/java/yeobaek/backend/club/controller/ClubControllerTest.java),
  [PassageControllerTest](../../src/test/java/yeobaek/backend/book/controller/PassageControllerTest.java),
  [BookControllerTest](../../src/test/java/yeobaek/backend/book/controller/BookControllerTest.java),
  [ProgressControllerTest](../../src/test/java/yeobaek/backend/club/controller/ProgressControllerTest.java)를
  보완하고,
  [GlobalExceptionHandlerTest](../../src/test/java/yeobaek/backend/support/GlobalExceptionHandlerTest.java)를
  추가한다. 기존 컨트롤러 테스트 전체의 일괄 개정은 범위에 포함하지 않는다.

## 한계

- HTML을 반환하는 `@Controller`에는 적용하지 않는다.
- 컨트롤러 테스트만으로 서비스와 도메인의 비즈니스 유효성 규칙을 증명하지 않는다.
- 컨트롤러 클래스당 대표 예외 하나만 검증하므로 모든 서비스 예외의 HTTP 변환을 증명하지
  않는다. 그 변환은 `GlobalExceptionHandlerTest`의 책임이다.
- API 명세의 제약이 운영 코드의 MVC 또는 Bean Validation 선언으로 표현되지 않았다면,
  컨트롤러 테스트에서 해당 제약을 웹 계층 동작으로 검증할 수 없다.

## 향후 재검토 신호

- HTML `@Controller`에도 공통 테스트 하네스가 필요해진다.
- Spring MVC가 아닌 다른 웹 스택이나 테스트 도구로 전환한다.
- 컨트롤러가 서비스 예외를 직접 해석하거나 변환하는 책임을 갖게 된다.
- API 제약과 비즈니스 제약의 소유 계층이 변경된다.
- 인터셉터, argument resolver 또는 전역 예외 처리기의 책임 경계가 변경된다.
- API 계약의 기준 문서나 응답 계약 검증 방식이 변경된다.
