# 여백 백엔드 개발 계획 — 첫 데모까지

> 기반 문서: [`docs/PRD.md`](../../docs/PRD.md)
> 전제: 백엔드 단독 계획 · 첫 데모까지 2주 · 백엔드 1인 · 배포 포함
>
> 이 문서는 첫 데모를 준비할 때 작성한 역사적 계획이다. 이후 확정된 기술 결정은 관련 ADR을 기준으로 한다.

## 1. 목표

첫 데모에서 PRD의 풀 플로우가 배포된 서버 위에서 동작한다:
회원 생성 → 모임 생성/참여코드 참여 → 본문 읽기 → 진도 저장/이어읽기 → 문단 댓글 → 홈(마지막 읽던 책).

전략은 **"풀 플로우를 얕게"** — 기능 하나를 깊게 파는 대신 여섯 기능 전부를 최소 스펙으로.
각 기능의 엣지 케이스·검증 고도화는 데모 이후로 미룬다.

## 2. 확정된 계획 결정

| 결정 | 내용 |
|---|---|
| 범위 | 백엔드 단독. 안드로이드 일정은 이 계획에서 다루지 않음 |
| 데모 컷라인 | 풀 플로우를 얕게 (엔드포인트 약 10개) |
| 콘텐츠 인제스트 | 로컬 LLM으로 규격 JSON 생성 → 관리자 페이지에서 서버 업로드. PRD 미해결 항목 해소 (PRD 3.3 반영) |
| 하네스 절차 | 스키마·API 결정은 계약 문서(`docs/PRD.md`, `docs/API.md`)로 갈음, 커밋에서 참조 |
| 테스트 | 스프링 기본 스택(webmvc-test, data-jpa-test)으로 단위 + 슬라이스 테스트. 테스트 DB는 Testcontainers(MySQL) — H2와 운영 DB 간 기능 괴리를 피하기 위한 M1 결정으로, "새 테스트 의존성 추가 없음"에서 변경 |
| 배포 | 첫 데모에 포함. 실서버 + MySQL에 안드로이드 앱이 실제로 붙는다 |
| 일정 압박 시 희생 순위 | 1순위: 관리자 페이지 (업로드 API는 사수) → 2순위: 홈 화면 API → 코어 플로우(회원·모임·읽기·진도·댓글)는 사수 |

## 3. 마일스톤

### 1주차 — 코어 도메인

| # | 작업 | 내용 |
|---|---|---|
| M1 | 스키마 · 엔티티 | PRD 4장 스키마 그대로 JPA 엔티티 전체 작성, MySQL 연결 설정. 개발용 소량 시드(하드코딩 문단 수십 개) 투입 |
| M2 | 회원 | 닉네임 입력 → 회원 생성 → ID 발급 API. 가장 얇은 슬라이스로 개발 리듬(구현→테스트→커밋) 형성 |
| M3 | 콘텐츠 조회 | 도서 목록/상세, 목차, 본문(문단) 조회 API |
| M4 | 모임 | 모임 생성(+참여코드 발급), 코드로 참여, 내 모임 목록 API |

### 2주차 — 소셜 + 운영

| # | 작업 | 내용 |
|---|---|---|
| M5 | 진도 · 홈 | 최근 열람 본문 갱신, 이어읽기 조회, 진도율 계산(최근열람.순서 ÷ 본문개수), 전 모임에서 마지막 읽던 책 조회 |
| M6 | 댓글 | 본문 단위 작성·조회·수정·삭제 (평면, 하드 삭제) |
| M7 | 인제스트 | 규격 JSON 포맷 정의 → 업로드 API(고정 관리자 토큰) → 관리자 페이지(최소 UI) → LLM 생성 가이드 문서화 |
| M8 | 배포 · 통합 | 서버+MySQL 배포, 실제 책 1권 투입, 안드로이드 통합 지원, 버퍼 |

인제스트를 2주차 후반에 두는 이유: 개발 중에는 하드코딩 시드로 충분하고, 실제 책이 필요한 시점은 데모 직전이다.
인제스트를 앞에 두면 일정 압박 시 잘리는 것이 코어 플로우(댓글 등)가 되지만, 이 순서면 잘리는 것이 관리자 페이지가 된다.

## 4. 하네스 대조 (피드백_루프_하네스 4장 — 멈출 지점 / 그냥 진행 항목)

### 검토한 결정 지점 (계획 작성 당시)

- **스키마·데이터 모델**: PRD 4장에서 확정 완료. 커밋에서 PRD 참조로 갈음하기로 했다.
- **API 계약**: `docs/API.md`로 구현 전 초안을 확정했다 (회원 식별 `X-Member-Id` 헤더, 본문 순서 범위 페이징, 에러 응답 규약 포함). 안드로이드와 공유하는 계약 문서이며, 변경 시 문서를 먼저 갱신하고 합의하기로 했다.
- **API 문서화 전략**: 당시에는 RestDocs + restdocs-api-spec 도입을 미확정 항목으로 두었다. 이 계획은 이후 폐기되었고, 현재는 springdoc이 런타임에 OpenAPI 스펙을 제공하는 Swagger 방식으로 확정되었다. ([ADR: API 문서화를 Swagger로 전환](ADR/기술_API_문서화를_Swagger로_전환.md))
- **인제스트 규격 JSON 포맷**: 당시 미확정 — M7 착수 시 결정 요청 대상으로 두었다.
- **관리자 페이지 기술 선택** (Thymeleaf/정적 HTML 등, 의존성 추가 가능성): 당시 미확정 — M7 착수 시 결정 요청 대상으로 두었다.
- **배포 구성** (서버 환경, DB 호스팅, 배포 방식): 당시 미확정 — M8 착수 시 결정 요청 대상으로 두었다.
- 성능·동시성 전략: 당시 데모 규모에서는 다루지 않기로 했다.

### 결정 요청서 제출 대상 (계획 작성 당시)

이 계획 작성 당시 결정 요청서 제출 대상은 4건 (API 문서화 의존성, 인제스트 규격, 관리자 페이지 기술, 배포 구성)이었다. 각 마일스톤 착수 시점에 제출하고, 승인 전 해당 부분 구현에 착수하지 않기로 했다 (R1). 개발자의 승인 답글을 결정 기록으로 삼고, 구현 커밋은 해당 결정 스레드(또는 계약 문서 PRD·API.md)를 참조하기로 했다. 이 목록은 현재의 미확정 상태를 나타내지 않으며, 후속 결정은 관련 ADR·계약 문서·배포 가이드를 기준으로 한다. API 문서화 결정은 이후 위 ADR로 해소되었다.

### 임의 진행 항목과 그 사유

- 패키지 배치, 클래스·메서드 명명, DTO 구조: 명백한 단일 정답 수준의 구현 세부 (하네스 2장 예외)
- 개발용 하드코딩 시드 데이터: 프로덕션에 노출되지 않는 개발 편의 장치

## 5. 리스크

- **1인 + 2주 + 하네스 절차**: 결정 요청→승인 대기가 병목이 될 수 있다. 마일스톤 착수 전날 결정 요청을 미리 제출해 대기 시간을 겹치기로 흡수한다
- **관리자 페이지**: 코어 플로우와 시간을 경쟁하는 항목임을 명시한다. 밀리면 업로드 API + 로컬 HTTP 클라이언트로 데모 콘텐츠를 투입한다
- **무인증 서비스의 관리자 엔드포인트**: 배포 서버에 열리므로 고정 관리자 토큰 헤더로 최소 방어한다 (M7에서 상세 결정)
