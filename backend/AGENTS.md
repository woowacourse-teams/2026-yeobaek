# Project Context for AI Agents

이 문서는 이 프로젝트에서 작업하는 모든 AI 에이전트를 위한 핵심 컨텍스트와 지침입니다. 사용하는 에이전트나 도구와 관계없이 코드를 작성하거나 수정하기 전에 반드시 이 문서의 규칙을 우선적으로 적용하세요.

이 파일을 에이전트 공통 지침의 단일 원본으로 사용합니다. 특정 에이전트와의 호환을 위한 진입점에는 지침을 중복해서 작성하지 않고 이 파일을 참조합니다.

## Project Overview (프로젝트 개요)
- **프로젝트명:** 여백
- **목적:** 온라인 교환독서 플랫폼
- **주요 대상:** 독서를 즐기며 E-book에 거부감이 없는 20~30대 여성

## Tech Stack & Environment (기술 스택)
- **Mobile:** Kotlin & Jetpack Compose
- **Backend/API:** Java & Spring Boot
- **Database:** MySQL

## 에이전트 행동 지침
- **작업 착수 전 `docs/지침/README.md`를 확인하고, 현재 작업에 해당하는 지침을 모두 읽습니다.** 이 색인을 지침 탐색의 중앙 진입점으로 사용합니다.
- **`docs/지침/프로세스/피드백_루프_하네스.md`는 모든 작업에서 반드시 읽고 준수합니다.** 특정 작업이 아닌 모든 작업에 상시 적용되는 프로토콜입니다.
- 새 기능이나 모호한 요청은 `docs/지침/프로세스/deep-interview_활용.md`의 명확성 게이트를 적용합니다.
    - 목표, 포함·제외 범위, 제약, 완료 기준, 기존 맥락·영향 범위 중 구현 결과를 바꿀 중요한 미정이 있으면 `deep-interview`를 시작하고, 종료 조건을 충족하기 전에는 계획이나 구현으로 넘어가지 않습니다.
    - 코드·문서에서 확인할 수 있는 사실은 개발자에게 묻지 않고 직접 조사합니다.
    - 단순 오타, 명백한 버그, 작은 설정 변경, 단일 정답인 구현처럼 구체적이고 저위험인 요청은 `deep-interview`를 생략합니다.
- 그 외 지침은 `docs/지침/README.md`의 작업별 라우팅에 따라 적용합니다.
    - 지침을 추가·이동·삭제할 때는 목적에 맞는 하위 디렉터리에 배치하고, 같은 변경에서 `docs/지침/README.md`의 라우팅을 갱신합니다.
- **백엔드 변경을 포함하는 쓰기 작업은 종료 전에 `docs/지침/프로세스/백엔드_PR_작성_하네스.md`를 읽고 실행합니다.** 검증을 마친 작업 브랜치를 커밋·푸시한 뒤, 해당 지침에 따라 PR을 자동으로 생성하거나 현재 브랜치의 열린 PR을 갱신합니다.
- 코드를 작성하거나 수정할 때, 반드시 해당 지침을 기반으로 수행해야 합니다.

## 디렉터리 접근 제한
- 기본적으로 `backend/` 디렉터리(현재 디렉터리) 내부만 수정한다.
- `android/` 디렉터리 내부 파일을 **허락 없이 수정하는 것은 절대 금지**한다.
    - `android/` 내부 수정 없이는 목적을 달성할 수 없는 경우, 반드시 사용자에게 이유를 설명하고 명시적인 허락을 받은 뒤에만 수정한다.
- `android/` 디렉터리 내부 파일을 맥락 및 세부 구현 파악을 위해 수정 없이 읽는 것은 허용한다.

## 버전 관리
- 버전 관리(git)는 현재 디렉터리(`backend/`)가 아니라 상위 디렉터리(`2026-yeobaek/`)에서 시작한다.
    - 즉, git 명령은 `backend/`가 아닌 상위 디렉터리를 저장소 루트로 간주하고 그 기준으로 수행한다.
- 커밋은 다음 조건을 충족하도록 나눈다.
    - 서비스가 온전히 동작해야 한다.
    - 1 ~ 2개의 문장으로 표현할 수 있어야 한다.
    - 작업 단위마다 하나의 커밋으로 모은다.
    - 작성한 프로덕션 코드에 대한 테스트를 작성해야 하며, 테스트가 통과되어야 한다.
- 커밋 메시지는 the AngularJS commit conventions를 기반으로 작성한다.
- 예시는 다음과 같다.
    - "feat: 회원 가입 구현"
    - "fix: 상품 구매 로직의 버그 해결"
    - "test: 주문 시나리오에 대한 E2E 테스트 작성"
- 위 지침을 준수하는 선에서 커밋을 자동으로 수행한다.

## 지침 및 명세서 개선
- 다음과 같은 상황에서 지침 및 명세서 개선을 요청할 수 있습니다.
    - 지침을 지키는 과정에서 코드 품질 저하가 우려되는 상황.
    - 도메인 명세서 자체에 모순, 문제점, 개선점이 존재하는 상황.
    - 사용자의 요구사항을 처리할 때 참고할 수 있는 지침이 존재하지 않는 상황
- 다음과 같은 상황에서는 지침 및 명세서를 자동으로 개선합니다.
    - 사용자와의 합의를 통해, 도메인 명세나 기술 스펙 자체가 달라진 상황.
- 기존 지침대로 수행했을 때와 새로운 지침을 적용했을 때를 비교해 트레이드 오프를 명확히 제시해서 요청해야 합니다.

## 반문
- 다음과 같은 상황에서는 스스로 추측한 후 작업을 진행하는 게 아니라, `docs/지침/프로세스/deep-interview_활용.md`와 관련 공식 관문에 따라 불확실성을 구체화합니다.
    - 사용자가 요구사항을 모호하게 제시하여, 어떤 작업을 수행해야 할지 확실히 알 수 없는 상황.
    - 요구사항대로 수행하면, 기존 지침이나 명세를 위반하게 되는 상황.
